## 문제 상황

Git 저장소를 가볍게 유지하면서 큰 모델 파일의 버전을 코드 커밋과 연결하고 싶습니다. Git LFS는 Git에는 작은 포인터를 저장하고 실제 대용량 파일은 LFS 저장소에 보관합니다.

## 개념과 동작 원리

### Git LFS의 포인터 구조

```text
version https://git-lfs.github.com/spec/v1
oid sha256:<파일 내용 식별자>
size <바이트 크기>
```

Git 이력에는 이 작은 텍스트가 들어가고 실제 파일은 LFS 객체 저장소로 전송됩니다. 체크아웃할 때 LFS 클라이언트가 포인터를 보고 실제 파일을 내려받습니다. 포인터만 있다고 파일을 읽을 수 있는 것은 아니며 저장소 접근 권한과 객체가 모두 필요합니다.

### 일반 Git과 무엇이 다를까요?

| 구분      | 일반 Git 대용량 파일      | Git LFS                            |
| --------- | ------------------------- | ---------------------------------- |
| Git 이력  | 실제 내용을 blob으로 보관 | 포인터 텍스트를 보관               |
| 실제 파일 | Git 객체 저장소           | LFS 저장소                         |
| 복원 조건 | Git 객체가 있어야 함      | 포인터와 LFS 객체가 모두 있어야 함 |
| 주요 용도 | 코드·작은 파일            | 저장소에 연결할 큰 바이너리        |

### DVC와의 차이

Git LFS와 DVC 모두 Git에 작은 메타데이터를 남기고 실제 대용량 파일을 별도로 보관할 수 있습니다. DVC는 데이터셋 캐시, 데이터 원격, 파이프라인 단계와 재실행 판단까지 ML 데이터 흐름에 맞춘 기능을 제공합니다.

## 비교와 한계

- 포인터를 커밋해도 실제 파일을 LFS 저장소에 올리지 않으면 복원할 수 없습니다.
- 저장 용량과 전송량은 사용하는 LFS 서비스의 제한을 확인해야 합니다.
- 전처리 단계와 파라미터 의존성은 LFS 포인터만으로 표현되지 않습니다.

## 전체 과정과 연결

Git LFS는 큰 바이너리를 Git 커밋과 연결하는 방법입니다. 다음 강의에서는 DVC가 같은 포인터 아이디어에 로컬 캐시, 데이터 원격과 ML 데이터 버전 관리 기능을 어떻게 더하는지 살펴봅니다.

<LessonSummary>

Git LFS는 Git 이력에 실제 대용량 파일 대신 내용 식별자와 크기가 담긴 포인터를 저장합니다. 실제 파일은 별도의 LFS 저장소에서 내려받습니다. 코드 커밋과 큰 바이너리를 연결하면서 Git 저장소의 부담을 줄일 수 있지만, 포인터와 실제 객체의 업로드·접근 권한을 함께 관리해야 하며 데이터 파이프라인 재현성은 별도로 구성해야 합니다.
