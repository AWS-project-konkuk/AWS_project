## 문제 상황

10GB 이미지 데이터셋을 코드처럼 Git에 계속 커밋하려고 합니다. Git은 파일 내용을 객체로 만들어 이력에 보관하므로 작업 공간의 파일을 지워도 과거 커밋이 참조하는 큰 객체는 남습니다. 데이터 버전이 반복해서 추가되면 저장소 복제·전송·상태 확인 비용도 커질 수 있습니다.

Git은 코드와 작은 텍스트 변경을 관리하는 데 강하지만, 자주 바뀌는 대용량 데이터셋의 실제 내용을 계속 넣는 방식은 비효율적입니다. 압축률과 파일 형식에 따라 증가량은 달라지지만 큰 파일의 여러 버전을 Git 이력에 보관한다는 점이 핵심입니다.

## 개념과 동작 원리

### Git은 파일을 어떻게 기록할까요?

```text
작업 공간의 data.zip
        │ git add
        ▼
Git 객체 저장소의 blob
        │ commit
        ▼
경로와 blob을 가리키는 커밋 이력
```

'git add'는 파일 내용을 해시로 식별한 객체로 저장하고 인덱스에 다음 커밋의 경로와 객체 정보를 준비합니다. 현재 파일을 삭제해 새 커밋을 만들어도 과거 커밋이 blob을 참조하면 객체는 즉시 사라지지 않습니다.

### 대용량 데이터에서 생기는 문제

- 저장소를 복제하거나 가져올 때 큰 이력을 전송해야 합니다.
- 데이터가 조금 바뀌어도 새 blob이 추가되어 저장 공간이 늘 수 있습니다.
- 인덱스와 작업 트리를 확인하는 동작이 대용량 파일의 영향을 받을 수 있습니다.
- Git 원격에도 대용량 이력을 보관하므로 코드 협업 경로가 무거워집니다.

### 무엇을 Git에 남겨야 할까요?

코드, 설정, 데이터의 식별 정보는 Git에 남기고 대용량 실제 데이터는 별도 저장소에 두는 구성이 적합합니다. 다음 강의에서 Git LFS의 포인터 방식을 살펴보고, 이후 DVC가 데이터 버전과 캐시·원격 저장소를 어떻게 연결하는지 확인합니다.

## 비교와 한계

큰 파일을 Git에 절대 넣을 수 없다는 뜻은 아닙니다. 변경이 거의 없고 저장소가 작다면 문제가 드러나지 않을 수 있습니다. 현재 크기뿐 아니라 변경 빈도, 보존할 버전 수, 복제 대상과 네트워크 비용을 함께 판단해야 합니다.

## 전체 과정과 연결

큰 데이터가 Git 이력을 무겁게 만드는 이유를 이해했다면, 다음 단계에서는 Git LFS와 DVC처럼 Git에는 작은 식별 정보만 남기고 실제 파일을 별도 저장소에서 관리하는 방식을 비교합니다.

<LessonSummary>

Git은 파일 내용을 blob으로 이력에 보관하므로 현재 작업 공간에서 큰 파일을 삭제해도 과거 커밋의 객체는 남을 수 있습니다. 자주 바뀌는 대용량 데이터셋은 코드 저장소의 용량과 전송 비용을 키웁니다. 코드와 데이터 식별 정보는 Git으로 추적하고 실제 데이터는 별도 저장소에서 관리하는 구조가 필요한 이유입니다.
