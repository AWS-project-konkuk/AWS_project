## 사진은 한 장 늘었는데 왜 내려받는 데 한참 걸릴까요?

고양이 사진을 한 장 추가하고 10GB짜리 압축 파일을 다시 커밋했습니다. 다음 날 새 팀원이 저장소를 내려받다가 묻습니다. “고양이 한 마리 보는데 왜 점심시간이 다 가요?” 작업 폴더에는 압축 파일 하나만 보이는데, 새 팀원은 왜 이전 내용까지 받게 될까요?

## Git은 과거 내용을 어떻게 기억할까요?

Git은 파일의 내용을 따로 보관하고, 커밋이라는 기록으로 그 시점을 기억합니다. 이 내용은 프로젝트 안의 `.git` 폴더에서 관리합니다.

`git add`를 하면 파일 내용을 **Binary large object**라는 객체로 저장하고, **Index**에 다음 커밋에 넣을 파일의 경로와 객체 정보를 기록합니다. 객체는 `.git/objects`에서 관리됩니다.

```text
내 작업 파일 → git add → 파일 내용 객체 + 다음 커밋 목록
                       → git commit → 시점별 기록
                       → git push → 팀 Git 저장소와 공유
```

작업 폴더의 10GB 파일 외에 Git이 내용을 보관할 공간도 필요해집니다. 다만 압축과 객체 재사용 때문에 항상 정확히 10GB가 한 번 더 생기는 것은 아닙니다. 큰 데이터를 자주 바꿀 때 저장 공간과 읽기·쓰기 부담이 생긴다는 점을 이해하면 됩니다.

| 위치            | 무엇이 있나요?                               |
| --------------- | -------------------------------------------- |
| 작업 폴더       | 지금 열고 수정하는 파일                      |
| Git 이력        | 이전 버전으로 돌아가기 위한 기록과 파일 내용 |
| Git 원격 저장소 | 팀원이 공유하는 Git 기록                     |

파일이 크다고 항상 쓸 수 없는 것은 아닙니다. **큰 파일이 자주 바뀔수록 과거 내용을 보관하고 전달하는 부담이 커진다**는 점이 핵심입니다.

## 큰 파일은 따로 보관할 수 있습니다

- **Git LFS**: 실제 데이터를 보관하는 저장소입니다.
- **DVC**: 데이터의 포인터와 메타데이터를 관리하는 파일입니다.

포인터만 삭제한다고 실제 파일이 없어지는 것은 아닙니다. 다시 사용할 파일은 별도 저장소에 남겨야 합니다.

## 데이터가 바뀌는 상황을 따라가 봅시다

월요일에는 사진 1,000장을 모아 `data.zip`을 만들었습니다. 화요일에는 잘못 분류된 사진을 고쳐서 같은 이름으로 저장했습니다. 수요일에는 새 사진을 추가했습니다. 이름은 모두 같지만, 세 파일의 내용은 서로 다릅니다.

Git은 파일 이름만 기억해서는 월요일 상태로 돌아갈 수 없습니다. 각 커밋이 사용한 내용을 다시 찾을 수 있도록 보관합니다. 그래서 작업 폴더에 수요일 파일만 보이더라도 월요일·화요일 기록이 저장소에 남을 수 있습니다.

| 작업                   | 현재 파일     | 과거 기록                                |
| ---------------------- | ------------- | ---------------------------------------- |
| 첫 데이터 커밋         | 월요일 데이터 | 월요일 버전 참조                         |
| 내용을 고쳐 다시 커밋  | 화요일 데이터 | 월요일·화요일 버전 참조                  |
| 현재 파일 삭제 후 커밋 | 파일 없음     | 이전 커밋이 참조하는 내용은 남을 수 있음 |

Git은 내용이 같은 파일을 무조건 여러 번 복사하지는 않습니다. 압축이나 버전 간 차이를 활용할 수도 있습니다. 다만 이미 압축된 사진·영상·모델 파일은 이런 절약 효과가 작을 수 있으므로, **10GB 파일이 세 버전이면 정확히 30GB가 된다**고 외우기보다 실제 저장량을 확인해야 합니다.

## 용량 문제는 어디에서 느낄까요?

가장 먼저 내 컴퓨터에서 작업 파일과 Git 객체를 보관할 공간이 필요합니다. 커밋을 공유할 때는 원격으로 전송해야 하고, 새 팀원이 프로젝트를 복제할 때는 과거 내용을 포함한 Git 기록을 받을 수 있습니다. 현재 코드 몇 줄만 필요해도 데이터 이력 때문에 준비 시간이 길어질 수 있습니다.

`git status`가 언제나 큰 파일 전체를 다시 읽는다고 생각할 필요는 없습니다. 파일의 변경 상태와 Git의 최적화에 따라 다릅니다. 이번 수업에서 기억할 것은 **큰 파일을 반복해서 이력에 넣으면 저장과 공유 부담이 커질 수 있다**는 점입니다.

## 다음에는 무엇을 나누어 관리할까요?

큰 데이터를 분리할 때는 단순히 “이 폴더는 S3에 있다”만 적어서는 부족합니다. 같은 경로의 파일이 바뀌면 지난 실험이 사용한 내용과 달라지기 때문입니다. 어떤 버전의 내용을 썼는지 식별할 수 있는 정보도 필요합니다.

다음 수업에서는 Git LFS가 작은 포인터로 큰 파일을 식별하는 방법을 봅니다. 이어서 DVC가 데이터 이름표와 실제 보관소를 연결하는 방식을 배웁니다.

<LessonSummary>

Git은 현재 파일뿐 아니라 과거 커밋이 참조하는 내용도 보관합니다. 큰 바이너리가 자주 바뀌면 저장 공간과 프로젝트 복제·전송 부담이 늘어날 수 있습니다. 현재 파일을 삭제하는 것만으로 과거 이력이 모두 없어지지는 않습니다. 실제 데이터는 별도 보관소에 두더라도 어떤 내용을 사용했는지 식별할 작은 기록을 Git에 연결해야 합니다.
