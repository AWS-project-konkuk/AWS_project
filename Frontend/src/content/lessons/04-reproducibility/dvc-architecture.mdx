## 문제 상황

코드와 데이터 버전을 연결하되 10GB 데이터셋 자체는 Git에 넣지 않으려 합니다. DVC는 Git에 '.dvc' 메타데이터를 커밋하고 실제 데이터는 내용 해시로 로컬 캐시와 데이터 원격에서 관리합니다.

## 개념과 동작 원리

### '.dvc' 파일이 기록하는 것

```yaml
outs:
  - md5: a1b2c3d4e5f6...
    size: 10737418240
    path: data.zip
```

- 'md5'는 DVC가 데이터 내용을 식별하고 캐시 객체를 찾는 값입니다.
- 'size'는 파일 크기입니다.
- 'path'는 작업 공간에서 파일이 나타날 경로입니다.

이 예시는 구조를 단순화한 것입니다. DVC 버전과 설정에 따라 추가 필드나 다른 해시가 사용될 수 있습니다.

### 네 공간의 역할

| 공간          | 보관하는 것                      | 대표 작업              |
| ------------- | -------------------------------- | ---------------------- |
| Git           | 코드, '.dvc', 설정               | 커밋과 코드 원격 전송  |
| 작업 공간     | 프로그램이 읽는 파일 경로        | 학습·전처리 실행       |
| DVC 로컬 캐시 | 내용 해시로 관리하는 데이터 객체 | 빠른 체크아웃과 재사용 |
| DVC 원격      | 팀이 공유하는 실제 데이터 객체   | 'dvc push', 'dvc pull' |

Git 원격과 DVC 원격은 역할이 다릅니다. '.dvc' 파일만 GitHub에 올려도 실제 데이터가 자동으로 DVC 원격에 올라가지는 않습니다.

### 저장 흐름과 복원 흐름

```text
저장: 작업 파일 → dvc add → 로컬 캐시 → dvc push → 데이터 원격
                         └→ .dvc → git commit → Git 원격

복원: Git에서 .dvc 선택 → 캐시 확인 → 없으면 데이터 원격 → 작업 공간
```

캐시에 같은 내용이 있으면 다시 다운로드하지 않고 작업 공간을 구성할 수 있습니다. 캐시가 없으면 원격 접근 권한과 해당 객체가 필요합니다.

## 비교와 한계

- '.dvc' 파일은 실제 데이터가 아니라 데이터 위치를 찾기 위한 메타데이터입니다.
- Git 원격과 DVC 원격은 별도이므로 코드와 데이터를 각각 올려야 합니다.
- 원격에 데이터가 없거나 권한이 없으면 다른 환경에서 복원할 수 없습니다.

<LessonSummary>

DVC는 코드와 데이터의 저장 경로를 분리합니다. Git은 코드와 '.dvc' 메타데이터를 추적하고, DVC는 실제 데이터를 내용 해시로 로컬 캐시와 데이터 원격에 보관합니다. 메타데이터의 해시·크기·경로는 어떤 데이터를 작업 공간에 복원할지 연결하지만 실제 데이터 자체가 아니므로 Git 커밋과 데이터 원격 업로드를 모두 확인해야 재현할 수 있습니다.
