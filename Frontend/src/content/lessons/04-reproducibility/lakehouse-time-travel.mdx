## 어제 본 주문 표를 다시 볼 수 있을까요?

어제 주문 CSV로 실험 결과를 보고했습니다. 오늘 같은 파일을 열었더니 금액이 고쳐지고 새 열까지 생겼습니다. 보고서엔 어제 숫자가 그대로인데, 저장소엔 오늘자 CSV 하나뿐입니다. 파일을 매번 덮어쓰면서도 지난 실험 때 읽은 표를 다시 열 수 있을까요?

## 1. Warehouse·Lake·Lakehouse는 어떻게 다를까요?

### Data Warehouse: 분석하기 좋게 정리한 자료실

<strong>데이터 웨어하우스(Data Warehouse, DW)</strong>는 데이터를 정리하고 가공해 분석하기 좋은
형태로 저장하는 곳입니다. 예를 들어 주문 날짜 형식을 통일하고 취소 주문을 구분한 뒤, 일별 매출 표를
만들 수 있습니다.

이처럼 원본에서 필요한 자료를 꺼내고, 정리하고, 저장하는 과정을 **ETL: 추출·변환·적재**라고 부릅니다.

```text
서비스의 원본 주문
        ↓
추출·변환·적재(ETL)
날짜 통일, 오류 확인, 매출 집계
        ↓
Data Warehouse
        ↓
SQL 분석·대시보드
```

일정한 열과 자료형으로 정리된 표를 **정형 데이터**라고 합니다. DW는 이런 데이터를 반복해서 분석하는 데 유용합니다. 로그나 사진을 분석하려면 필요한 정보를 꺼내 표로 바꾸는 추가 작업이 들 수 있습니다. 현대 DW의 지원 범위는 다양하므로 비정형 데이터를 전혀 다룰 수 없다고 외우기보다, 분석에 맞게 준비하는 비용을 생각하세요.

### Data Lake: 여러 모양의 자료를 담는 큰 보관소

<strong>데이터 레이크(Data Lake)</strong>는 표뿐 아니라 로그·사진 같은 다양한 자료를 원본에 가까운
모습으로 모아 두는 저장 기반입니다.

| 자료의 모양 | 예시            | 쉽게 이해하기                                   |
| ----------- | --------------- | ----------------------------------------------- |
| 정형        | 주문 CSV        | 정해진 열을 갖춘 표                             |
| 반정형      | 서버 JSON       | 이름과 값의 구조는 있지만 항목이 달라질 수 있음 |
| 비정형      | 상품 JPG·동영상 | 그대로는 행과 열로 된 표가 아님                 |

```text
주문 CSV · 서버 JSON · 상품 JPG
                ↓
       Data Lake의 보관소
           예: Amazon S3
                ↓
SQL 분석 · 로그 분석 · AI 학습
```

원본을 미리 한 가지 모양으로 바꾸지 않고 모을 수 있다는 장점이 있습니다. 다만 S3에 저장하기만 하면 분석이 자동으로 되는 것은 아닙니다. 자료를 찾을 목록, 접근 권한, 읽고 처리할 프로그램도 필요합니다. 관리가 부족하면 어느 파일이 최신인지, 누가 만든 자료인지 알기 어려워집니다.

### Data Lakehouse: 큰 보관소에 표 관리 기능 더하기

<strong>레이크하우스(Data Lakehouse)</strong>는 레이크의 저장 기반에 표 단위의 버전·스키마·변경 관리
기능을 더한 구조입니다. 스키마는 열 이름과 자료형처럼 표의 모양을 정한 규칙입니다.

| 구분      | 강점                                | 준비하거나 관리할 것         |
| --------- | ----------------------------------- | ---------------------------- |
| DW        | 정리한 표를 SQL로 분석하기 좋음     | 적재와 변환 작업             |
| Data Lake | 다양한 원본 자료를 넓게 보관        | 목록·품질·권한과 파일의 의미 |
| Lakehouse | 보관된 파일을 일관된 표로 함께 사용 | 표 기록·처리 엔진·버전 보존  |

Lakehouse가 두 구조의 모든 단점을 없애 주는 것은 아닙니다. 보관할 자료의 종류와 분석·학습 작업에 맞게 구성합니다. 이미지 파일 자체가 저절로 SQL 테이블이 되는 것도 아닙니다.

## 2. Lakehouse의 세 역할: 저장·기록·계산

도서관으로 비유하면 파일은 책, 메타데이터는 책을 찾는 목록, 계산 엔진은 책을 꺼내 읽는 사람에 가깝습니다. **메타데이터**는 데이터 자체에 관한 설명과 위치 정보를 뜻합니다.

| 계층                 | 하는 일                          | 예시                      |
| -------------------- | -------------------------------- | ------------------------- |
| 저장층(Storage)      | 실제 데이터를 보관               | S3의 Parquet 파일         |
| 표 포맷·메타데이터층 | 유효한 파일·열·버전을 기록       | Iceberg·Delta Lake의 기록 |
| 계산층(Compute)      | 기록을 확인하고 파일을 읽어 계산 | Spark·Trino 같은 엔진     |

**Parquet**는 분석용 표 데이터를 저장할 때 자주 사용하는 파일 형식입니다. 반면 **테이블 포맷**은 여러 파일을 모아 한 표로 관리하는 규칙입니다. 파일 하나의 형식과 여러 파일을 관리하는 규칙을 구분해 보세요.

“어제 주문의 매출 합계”를 요청하면 엔진이 어제 표의 기록을 찾고, 필요한 실제 파일을 읽어 합계를 계산합니다. 메타데이터가 계산을 대신하지는 않습니다.

## 3. 오픈 테이블 포맷은 파일 목록 이상의 역할을 합니다

**Apache Iceberg와 Delta Lake**는 공개된 테이블 관리 규칙을 제공하는 오픈 테이블 포맷입니다. 어떤 파일이 표에 포함되는지, 열 구조와 버전이 어떻게 바뀌는지 관리합니다.

일반 폴더에서 모든 파일을 읽으면 준비 중인 파일이나 과거 파일까지 섞일 수 있습니다. 테이블 포맷을 쓰면 **현재 표의 기록이 가리키는 파일만 선택**할 수 있습니다. 이것이 파일을 표처럼 관리한다는 뜻입니다.

데이터베이스에서 익숙한 트랜잭션 같은 기능을 파일 위에서도 지원하지만, 모든 관계형 데이터베이스 기능을 자동으로 제공한다는 뜻은 아닙니다.

### Iceberg: 목록을 따라 필요한 파일 찾기

큰 도서관에서 안내 목록을 따라 책을 찾듯, Iceberg는 여러 단계의 기록을 따라갑니다.

```text
Catalog: 테이블 기록의 위치
        ↓
Table Metadata: 표의 구조와 버전 정보
        ↓
Snapshot: 선택한 시점의 표
        ↓
Manifest List: 파일 목록들의 목록
        ↓
Manifest Files: 실제 파일의 정보·통계
        ↓
필요한 Parquet 파일 읽기
```

1. <strong>카탈로그(Catalog)</strong>에서 테이블 메타데이터 위치를 찾습니다.
2. **테이블 메타데이터**에서 조회할 스냅샷을 확인합니다.
3. **스냅샷**이 가리키는 매니페스트 목록을 확인합니다.
4. <strong>매니페스트(Manifest)</strong>의 파일 위치·파티션·통계를 보고 읽을 파일을 고릅니다.
5. 선택한 데이터 파일을 저장소에서 읽습니다.

파티션은 날짜처럼 자료를 나누는 기준입니다. 예를 들어 “어제 주문만” 조회할 때 날짜 정보와 통계를 이용하면 관련 없는 파일을 건너뛸 수 있습니다. 모든 쿼리에서 반드시 일부 파일만 읽는다는 뜻은 아니며, 조회 조건에 맞춰 읽을 범위를 줄이는 데 도움이 됩니다.

### Delta Lake: 변경 기록을 모아 표의 상태 찾기

Delta Lake는 <strong>트랜잭션 로그(Transaction Log)</strong>를 중심으로 테이블 상태를 기록합니다. 파일이 추가되거나 표에서 제외되면 그 변경을 기록하고, 해당 버전에 포함되는 파일을 알아냅니다.

처음부터 모든 변경을 매번 따라가면 오래 걸릴 수 있어 중간 상태를 요약한 <strong>체크포인트(Checkpoint)</strong>도 활용합니다. 체크포인트와 이후 로그로 원하는 버전의 상태를 찾는 방식입니다. 이 체크포인트는 모델 학습 중 저장하는 가중치 파일과 역할이 다릅니다.

## 4. 새 파일을 먼저 만들고, 마지막에 공개합니다

테이블의 한 번의 변경을 묶어 처리하는 것을 **트랜잭션**이라고 합니다. 이를 공식적인 새 상태로 확정하는 일이 <strong>커밋(Commit)</strong>입니다.

현재 표 V1이 A와 B 파일로 구성되어 있고, B의 잘못된 주문 금액을 고친다고 가정해 보세요.

### 첫째, 수정한 내용을 새 파일 C로 준비합니다

이 예시에서는 B를 제자리에서 바꾸는 대신 수정한 데이터를 C 파일로 씁니다. 아직 현재 표의 기록은 A와 B를 가리킵니다. 저장소에 C가 생겼다는 이유만으로 읽는 사람에게 C가 보이지는 않습니다.

### 둘째, A와 C를 사용할 새 기록 V2를 만듭니다

새 기록은 준비되었지만 커밋 전에는 현재 표로 공개되지 않습니다. 기존 파일 B도 과거 조회에 필요할 수 있으므로 즉시 지우지 않습니다.

### 셋째, 현재 표의 기록을 한 번에 바꿉니다

```text
커밋 전: 현재 기록 → V1 → [A, B]
                   ↓ 커밋 성공
커밋 후: 현재 기록 → V2 → [A, C]
```

| 시점         | 저장소에 있는 파일 | 현재 표가 읽는 파일 |
| ------------ | ------------------ | ------------------- |
| 수정 전      | A, B               | A, B                |
| 새 파일 준비 | A, B, C            | A, B                |
| 커밋 후      | A, B, C            | A, C                |

사용자에게 V1 또는 V2라는 **완성된 상태**가 보여야 합니다. 이 수정에서 A·B·C를 모두 읽으면 B와 C의 주문이 중복될 수 있습니다. 기록을 한 번에 확정하는 것을 <strong>원자적(Atomic)</strong>이라고 합니다.

Iceberg는 카탈로그 등이 현재 메타데이터를 가리키는 참조를 조건에 맞게 바꾸는 방식으로 커밋합니다. Delta Lake는 새 로그 버전을 확정해 변경을 공개합니다. 구체적인 처리는 카탈로그·엔진·저장소 구성에 따라 달라집니다. 위 예시는 파일 교체 방식을 쉽게 설명한 것으로, 모든 수정이 항상 파일 전체 교체로 처리된다는 뜻은 아닙니다.

## 5. 두 사람이 동시에 고치면 어떻게 할까요?

민수와 지수가 모두 V1을 읽고 같은 주문을 고쳤다고 가정합니다. 민수가 먼저 새 버전을 커밋한 뒤 지수가 자신의 결과를 그대로 덮어쓰면 민수의 변경이 사라질 수 있습니다.

그래서 커밋할 때 **내가 읽은 뒤 다른 작업이 무엇을 바꿨는지** 확인합니다. 충돌하면 최신 상태를 다시 읽어 재시도하거나 실패를 알립니다.

| 순서      | 민수           | 지수                          |
| --------- | -------------- | ----------------------------- |
| 시작      | V1을 읽고 수정 | V1을 읽고 수정                |
| 먼저 커밋 | 변경 확정      | 아직 수정 중                  |
| 다음 커밋 | 완료           | 다른 변경과 충돌하는지 확인   |
| 충돌 발생 | 완료           | 최신 상태로 재시도하거나 실패 |

이 방식을 <strong>낙관적 동시성 제어(Optimistic Concurrency Control)</strong>라고 부릅니다. 먼저 작업을 허용하고 마지막에 충돌을 확인한다는 뜻입니다. 다른 사람이 먼저 커밋했다고 항상 실패하는 것은 아니며, 변경 내용과 충돌 규칙에 따라 판단합니다.

### ACID를 주문 표의 예로 기억하세요

| ACID               | 쉬운 뜻                                   | 연결되는 장치                    |
| ------------------ | ----------------------------------------- | -------------------------------- |
| Atomicity·원자성   | 수정 내용을 전부 공개하거나 공개하지 않음 | 버전 커밋을 한 번에 확정         |
| Consistency·일관성 | 표가 정한 규칙을 지킴                     | 스키마·지원되는 제약과 커밋 검증 |
| Isolation·격리성   | 동시에 하는 작업의 영향을 조정            | 스냅샷을 기준으로 읽기·충돌 검사 |
| Durability·지속성  | 확정한 결과를 남김                        | 실제 파일과 표 기록을 영속 저장  |

이 기능은 테이블 포맷과 이를 사용하는 시스템이 함께 구현합니다. S3에 파일을 모아 두는 것만으로 테이블의 모든 규칙이 자동으로 보장되지는 않습니다.

## 6. 과거 표 조회와 현재 표 되돌리기를 구분하세요

특정 시점의 표를 가리키는 기록을 <strong>스냅샷(Snapshot)</strong>이라고 생각하면 쉽습니다. 기록이나 버전을 골라 과거 데이터를 읽는 기능이 <strong>타임 트래블(Time Travel)</strong>입니다.

오늘 표에 오류가 있으면 어제 데이터를 조회해 무엇이 달라졌는지 조사할 수 있습니다. 현재 상태를 과거 상태로 되돌리는 <strong>롤백(Rollback)</strong>은 별도 작업입니다.

| 작업                 | 읽는 데이터 | 현재 표                 |
| -------------------- | ----------- | ----------------------- |
| 오늘 조회            | 오늘 120건  | 오늘 상태 유지          |
| 어제 시점 조회       | 어제 100건  | 오늘 상태 유지          |
| 과거 상태로 되돌리기 | 복구한 상태 | 별도 복구 작업으로 변경 |

“어제 표 조회”를 눌러 현재 표는 120건으로 유지되는지 보세요. 지난 모델을 다시 학습할 때는 사용한 테이블과 스냅샷 ID 또는 버전도 기록합니다.

스냅샷마다 데이터를 전부 복사하는 것은 아닙니다. 바뀌지 않은 파일은 여러 버전에서 공유할 수 있습니다. 대신 과거 기록이나 그 기록이 참조하는 파일을 삭제하면 해당 시점을 다시 읽지 못할 수 있습니다.

## 7. DVC와 Lakehouse는 어떤 단위를 관리할까요?

| 비교             | DVC                                  | Lakehouse의 테이블 포맷           |
| ---------------- | ------------------------------------ | --------------------------------- |
| 주된 관리 대상   | 프로젝트의 파일·디렉터리와 작업 순서 | 여러 작업이 공유하는 표의 상태    |
| 버전을 찾는 기준 | Git 기록과 데이터 해시               | 테이블 스냅샷 또는 로그 버전      |
| 예시             | 사진 묶음과 전처리·학습 결과 관리    | 계속 추가되는 주문 표의 조회·수정 |
| 공통점           | 작은 기록과 실제 내용이 모두 필요    | 작은 기록과 실제 내용이 모두 필요 |

DVC도 표 파일을 관리할 수 있고, 하나의 실험에서 두 방식을 함께 쓸 수도 있습니다. 예를 들어 Lakehouse의 특정 스냅샷을 읽어 학습용 파일을 만들고, 그 파일과 이후 파이프라인은 DVC로 추적할 수 있습니다.

<Callout title="실험 기록에 남길 질문">

어떤 코드로, 어느 테이블의 어떤 버전과 열을 읽었고, 어떤 설정으로 학습했나요? 그 버전의 기록과 실제 파일이 다음 달에도 보존되는지도 함께 확인하세요.

</Callout>

<LessonSummary>

Data Warehouse는 분석하기 좋게 정리한 자료를, Data Lake는 다양한 원본 자료를 보관하는 기반을 강조합니다. Lakehouse는 그 기반 위에 표 관리 기능을 더합니다. Iceberg·Delta Lake는 실제 파일과 표 기록을 연결하고 완성된 버전을 커밋합니다. 타임 트래블은 과거 조회, 스키마 진화는 열 구조의 변화 관리입니다. 실험을 다시 준비하려면 사용한 버전·구조와 실제 파일이 함께 남아 있어야 합니다.

</LessonSummary>
