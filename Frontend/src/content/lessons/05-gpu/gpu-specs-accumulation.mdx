## 배치 64를 한 번에 보낼 필요가 있을까요?

배치 8로는 잘 돌던 실험을 32로 바꿨더니 첫 단계도 끝나기 전에 GPU 메모리 오류가 났습니다. 배치를 다시 8로 바꾸면 실행은 되지만, 이번엔 샘플 32개를 모아 한 번만 모델을 갱신하고 싶습니다. 계산은 네 번 나눠 하고 갱신은 한 번만 할 수 있을까요?

## 개념과 동작 원리

GPU 사양은 숫자를 외우기보다, 각 수치가 어떤 문제와 이어지는지로 읽습니다.

| 사양               | 정하는 것                                                | 상황과 연결                                                 |
| ------------------ | -------------------------------------------------------- | ----------------------------------------------------------- |
| VRAM 용량          | 모델 상태 · 활성값 · 임시 공간이 들어갈 수 있는지        | Out of Memory 여부                                          |
| 메모리 대역폭      | GPU 안에서 자료를 읽고 쓰는 속도 (TB/s)                  | 메모리 이동이 병목인 연산의 속도, LLM 추론의 토큰 생성 속도 |
| 정밀도별 연산 성능 | FP32, BF16, FP16, FP8 등으로 연산을 끝내는 속도 (TFLOPS) | 혼합 정밀도의 처리량                                        |
| GPU 간 연결        | 기울기 · 파라미터를 주고받는 속도 (NVLink, PCIe)         | 병렬화에서의 통신 비용                                      |

자주 비교하는 데이터센터 GPU를 같은 기준으로 놓으면 다음과 같습니다. 같은 이름이라도 SXM·PCIe·NVL 구성에 따라 수치가 다르므로, 실제 선택 전에는 제조사 사양서를 확인합니다.

| GPU (세대)       | VRAM           | 메모리 대역폭     | 새로 지원하는 정밀도     | 이런 상황에                               |
| ---------------- | -------------- | ----------------- | ------------------------ | ----------------------------------------- |
| T4 (Turing)      | 16GB GDDR6     | 약 0.3TB/s        | FP16 Tensor Core         | 실습, 소규모 추론 (Colab 무료 GPU)        |
| A100 (Ampere)    | 40·80GB HBM2e  | 약 1.6~2.0TB/s    | BF16, TF32               | 7B~13B 모델 파인튜닝, 비용 대비 성능      |
| H100 (Hopper)    | 80GB HBM3      | 약 3.35TB/s (SXM) | FP8 (Transformer Engine) | 대규모 학습·추론                          |
| H200 (Hopper)    | 141GB HBM3e    | 약 4.8TB/s        | FP8                      | 메모리가 병목인 큰 모델, 긴 컨텍스트 추론 |
| B200 (Blackwell) | 약 180GB HBM3e | 약 7.7TB/s        | FP4                      | 초거대 모델 학습·추론                     |

H100과 H200은 같은 Hopper 칩을 쓰고, H200은 메모리 용량과 대역폭만 늘린 제품입니다. 그래서 같은 모델이라도 메모리를 많이 읽는 LLM 추론에서 차이가 크게 납니다. NVIDIA가 발표하는 "A100 대비 최대 몇 배"라는 수치는 특정 모델·정밀도·클러스터 구성에서 측정한 값이므로, 우리 작업에서도 같은 배율이 나온다고 기대하지 않습니다.

## 마이크로배치와 기울기 누적

작은 마이크로배치로 forward · backward propagation을 수행해 기울기를 누적하고, 정해진 횟수만큼 반복한 뒤 optimizer step을 한 번 수행합니다.
활성값은 backward propagation이 끝나면 해제되므로, 동시에 메모리에 있는 활성값은 마이크로배치 한 개의 몫입니다.

<Figure
  src="images/lessons/05-gpu/gpu-specs-accumulation/accumulation.svg"
  alt="마이크로배치 네 개를 차례로 forward와 backward한 뒤 step을 한 번 수행하는 타임라인. 활성값 메모리는 마이크로배치마다 올라갔다 내려가 최고점이 배치 32를 한 번에 처리할 때보다 낮고, 기울기 버퍼는 4분의 1씩 누적됩니다."
  caption="활성값의 최고점은 마이크로배치 하나 몫이고, 기울기 버퍼는 파라미터 크기 그대로 누적됩니다."
/>

GPU 한 장의 유효 배치는 **마이크로배치 × 누적 횟수**입니다. 목표 유효 배치가 32이고 한 번에 8개까지 들어간다면 누적 횟수는 4입니다. 데이터 병렬이면 여기에 **GPU 수**가 곱해집니다.

```python
accum_steps = 4  # 유효 배치 = 8 × 4 = 32

optimizer.zero_grad()
for i, (x, y) in enumerate(loader):          # loader의 batch_size = 8
    loss = loss_fn(model(x), y) / accum_steps  # 평균을 맞추기 위해 나눔
    loss.backward()                            # .grad에 기울기가 더해짐
    if (i + 1) % accum_steps == 0:
        optimizer.step()                       # 4번에 한 번만 갱신
        optimizer.zero_grad()
```

큰 배치와 똑같은 결과를 항상 보장하지는 않습니다. 확인할 것은 세 가지입니다.

- **loss 크기**: 누적 횟수로 loss를 나누어야 큰 배치의 평균과 맞습니다.
- **정규화**: BatchNorm은 마이크로배치 단위로 통계를 구하므로 결과가 달라지고, LayerNorm은 샘플 단위라 영향이 작습니다.
- **처리량**: 마이크로배치가 너무 작으면 GPU가 놀아 step당 시간이 늘어납니다.

## 기울기 누적으로 풀리지 않는 문제

| 상황                                       | 기울기 누적                                        | 다음 선택지                             |
| ------------------------------------------ | -------------------------------------------------- | --------------------------------------- |
| 활성값 때문에 OOM                          | 효과 있음                                          | 활성값 재계산(activation checkpointing) |
| 파라미터·기울기·옵티마이저 상태만으로 넘침 | 효과 없음 (배치와 무관)                            | 상태 분할(ZeRO·FSDP), 모델 병렬         |
| 혼합 정밀도 적용                           | 활성값은 줄지만 FP32 가중치·옵티마이저 상태는 남음 | 전체가 절반이 되는 것은 아님            |
| 데이터 병렬로 GPU 추가                     | 처리량은 늘지만 모델 상태는 GPU마다 복제됨         | 상태를 나누는 전략과 통신 비용 비교     |

배치를 키우는 것 자체에도 비용이 있습니다. 유효 배치가 커지면 step 수가 줄어 한 step의 학습률을 다시 맞춰야 하고, 너무 큰 배치는 일반화 성능이 떨어질 수 있다는 연구도 있습니다. 대규모 배치 학습에서는 배치에 비례해 학습률을 키우고 초반에 서서히 올리는 warmup을 함께 쓰는 것이 일반적입니다.

## 전체 과정과 연결

GPU가 빠르다는 설명만으로는 자원 선택을 할 수 없습니다. 작업 크기, 모델과 활성값의 메모리, 데이터 공급 속도, 장치 간 통신을 함께 고려해야 합니다. 모델이 한 GPU에 들어가는지와 계산을 더 빨리 끝내려는지는 다른 질문이며, 이 차이가 병렬화 전략을 결정합니다.

<Callout title="판단할 때 확인하기">

OOM이 발생하면 먼저 어느 메모리가 넘쳤는지 확인합니다. 활성값이라면 마이크로배치를 줄이고 기울기를 누적하면 됩니다. 파라미터와 옵티마이저 상태라면 배치를 줄여도 해결되지 않습니다.

</Callout>
