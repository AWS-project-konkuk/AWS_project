## 가중치를 올렸는데 첫 학습에서 왜 메모리가 부족할까요?

GPU에 모델을 올리는 데 성공했습니다. 안심하고 첫 학습을 시작했더니 메모리 부족 오류가 뜹니다. 모델을 올릴 때는 조용하던 GPU가 계산을 시작하자 공간을 더 내놓으라고 합니다. 첫 학습 단계에서 가중치 외에 어떤 데이터가 더 들어올까요?

## 개념 이해

**VRAM**은 GPU에 붙어 있는 전용 메모리입니다. 이름은 그래픽(Video)에서 왔지만, 딥러닝에서는 GPU가 계산할 모든 텐서가 이곳에 있어야 합니다. 일반 RAM이 지연 시간을 줄이는 데 집중한다면, VRAM은 넓은 통로로 한 번에 많은 데이터를 옮기는 **대역폭**에 집중합니다. 소비자용 GPU는 GDDR을, 데이터센터용 GPU는 칩 옆에 메모리를 쌓아 올린 HBM을 주로 씁니다.

학습 중 VRAM을 차지하는 것은 크게 다섯 가지입니다.

| 항목             | 크기를 정하는 것                    | 배치를 줄이면 |
| ---------------- | ----------------------------------- | ------------- |
| 가중치(파라미터) | 파라미터 수 × 자료형 크기           | 그대로        |
| 기울기           | 파라미터 수만큼 (보통 FP32)         | 그대로        |
| 옵티마이저 상태  | Adam은 파라미터마다 2개(m, v)       | 그대로        |
| 활성값           | 배치 × 시퀀스 길이 × 레이어 수      | 줄어듦        |
| 임시 공간        | 연산 라이브러리의 작업 공간, 단편화 | 일부 줄어듦   |

파라미터 10억 개 모델을 Adam으로 학습하면 가중치 4GB, 기울기 4GB, 옵티마이저 상태 8GB로 **모델 상태만 16GB**입니다. 여기에 배치에 비례하는 활성값이 더해집니다. 그래서 "가중치 4GB가 16GB GPU에 들어간다"는 계산만으로는 학습이 가능한지 알 수 없습니다. 할당할 공간이 부족하면 OOM이 발생하며, 이는 GPU 사용률(GPU-Util)이 높다는 것과는 다른 문제입니다.

### 혼합 정밀도로 메모리 줄이기

**혼합 정밀도**(Mixed Precision)는 계산량이 많은 연산은 16비트(FP16·BF16)로, 정밀도가 중요한 부분은 32비트(FP32)로 처리하는 방법입니다. 16비트 연산은 Tensor Core에서 훨씬 빠르고, 16비트로 저장한 활성값은 절반의 공간을 씁니다.

<Figure
  src="images/lessons/05-gpu/vram-oom/mixed-precision.svg"
  alt="FP32 가중치를 유지한 채 autocast로 순전파를 FP16으로 계산하고, loss에 배율 S를 곱해 역전파한 뒤, 기울기를 S로 나누고 inf와 NaN을 검사해 optimizer step을 수행하는 여덟 단계 흐름"
  caption="①~③은 autocast, ④~⑧은 GradScaler가 담당합니다."
/>

FP16은 표현할 수 있는 수의 범위가 좁아서 아주 작은 기울기가 0으로 사라질 수 있습니다(underflow). 이를 막는 방법이 **loss scaling**입니다. 역전파 **전에** loss에 큰 수 S를 곱해 기울기를 키우고, optimizer step 직전에 S로 나누어 원래 크기로 되돌립니다. 기울기가 넘쳐 inf·NaN이 생기면 그 step은 건너뛰고 S를 줄입니다. BF16은 FP32와 지수 범위가 같아 보통 loss scaling 없이 씁니다.

```python
import torch

scaler = torch.amp.GradScaler("cuda")      # FP16일 때 필요 (BF16이면 생략 가능)

for x, y in loader:
    optimizer.zero_grad()
    with torch.amp.autocast("cuda", dtype=torch.float16):
        loss = loss_fn(model(x), y)        # matmul·conv는 FP16, softmax·loss는 FP32
    scaler.scale(loss).backward()          # loss × S 로 역전파
    scaler.step(optimizer)                 # ÷ S 후 inf/NaN이면 step 건너뜀
    scaler.update()                        # 다음 S 조정
```

예전 코드의 `torch.cuda.amp.autocast()`와 `torch.cuda.amp.GradScaler()`는 더 이상 권장되지 않으며, 위처럼 `torch.amp`에 장치 이름을 넘기는 방식을 씁니다. `autocast`를 쓰면 모델을 직접 `.half()`로 바꿀 필요가 없습니다. 행렬 곱셈·합성곱은 FP16으로 바꾸고, `softmax`·`layer_norm`·loss처럼 정밀도가 중요한 연산은 FP32로 유지합니다.

## 관찰한 결과 해석하기

마이크로배치, 정밀도, 기울기 누적 횟수를 바꾸며 OOM이 나는 상태와 메모리에 들어가는 상태를 각각 확인하세요.

<Activity />

혼합 정밀도가 전체 메모리를 절반으로 줄이지는 않습니다. PyTorch의 `autocast`는 가중치·기울기·옵티마이저 상태를 FP32로 그대로 두고 연산만 16비트로 바꾸기 때문에, 주로 **활성값**이 줄어듭니다. 대신 연산 속도가 크게 빨라집니다. 실제로 Colab의 Tesla T4에서 같은 행렬 곱셈을 FP32와 FP16으로 비교하면 FP16이 몇 배 빠르게 측정됩니다(스터디 실습에서는 약 4.7배). T4의 Tensor Core가 FP16 연산을 가속하기 때문입니다.

메모리는 PyTorch 함수로 직접 확인할 수 있습니다.

```python
torch.cuda.memory_allocated()               # 텐서가 실제로 쓰고 있는 양
torch.cuda.memory_reserved()                # 캐싱 할당기가 GPU에서 확보해 둔 양
torch.cuda.max_memory_allocated()           # 실행 이후 최고 사용량(peak)
torch.cuda.get_device_properties(0).total_memory  # GPU 전체 VRAM
```

## 적용 조건과 한계

OOM을 만났을 때 시도할 방법을 효과가 큰 순서로 정리하면 다음과 같습니다.

| 방법                                              | 줄이는 것                    | 주의할 점                                    |
| ------------------------------------------------- | ---------------------------- | -------------------------------------------- |
| 배치(마이크로배치) 줄이기                         | 활성값                       | 유효 배치를 지키려면 기울기 누적을 함께 사용 |
| 혼합 정밀도                                       | 활성값, 연산 시간            | FP16은 loss scaling 필요, 모델 상태는 그대로 |
| 기울기 누적                                       | 활성값 (유효 배치 유지)      | step당 시간 증가                             |
| 활성값 재계산(checkpointing)                      | 활성값                       | 역전파 때 순전파를 다시 계산해 느려짐        |
| `with torch.no_grad()` / `torch.inference_mode()` | 추론·평가 시 역전파용 활성값 | 학습 단계에는 쓸 수 없음                     |
| 상태 분할(ZeRO·FSDP), 더 큰 GPU                   | 모델 상태                    | 통신 비용·비용 증가                          |

`del`과 `torch.cuda.empty_cache()`는 만능이 아닙니다. PyTorch는 해제된 메모리를 바로 GPU에 돌려주지 않고 캐시로 보관해 다음 할당에 재사용합니다. `empty_cache()`는 이 **빈 캐시**만 반납할 뿐 아직 참조되는 텐서는 지우지 못하므로, 같은 프로세스의 OOM은 대개 해결되지 않습니다. 오히려 다음 할당 때 다시 GPU에 요청해야 해서 느려질 수 있습니다. 반복문에서 `loss` 대신 `loss.item()`을 기록하는 것처럼 계산 그래프를 붙잡고 있는 참조를 없애는 것이 더 중요합니다.

## 전체 과정과 연결하기

학습 중에는 가중치 외에도 활성값·기울기·옵티마이저 상태와 임시 공간이 필요합니다. 배치를 늘리면 활성값이 커져 VRAM을 넘을 수 있고, 모델이 커지면 배치와 무관한 모델 상태만으로 넘칠 수 있습니다. 어느 쪽인지에 따라 다음 강의의 기울기 누적, 혼합 정밀도, 병렬화 중 무엇을 고를지가 달라집니다.

<Callout title="판단할 때 확인하기">

GPU 사용률과 메모리 부족은 다른 지표로 확인합니다. `nvidia-smi`의 Memory-Usage, `torch.cuda.max_memory_allocated()`로 최고 사용량을 재고, 배치를 바꿔도 줄지 않는 부분이 모델 상태입니다.

</Callout>

<LessonSummary>

VRAM에는 가중치·기울기·옵티마이저 상태처럼 배치와 무관한 모델 상태와, 배치에 비례하는 활성값이 함께 올라갑니다. 혼합 정밀도는 무거운 연산을 16비트로 계산해 활성값과 연산 시간을 줄이고, loss scaling으로 작은 기울기가 사라지는 것을 막습니다. 다만 FP32 모델 상태는 남으므로 메모리가 절반이 되지는 않습니다.
