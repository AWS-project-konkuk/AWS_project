## 문서가 백만 건이면 전부 확인해야 할까요?

문서 천 건일 때는 검색창에 질문을 넣자마자 답이 나왔습니다. 백만 건을 넣은 뒤 같은 질문을 했더니 결과 대신 로딩 표시를 한참 봅니다. 모든 문서를 비교하는 시간을 줄이면서 좋은 후보를 놓쳤는지도 어떻게 확인할 수 있을까요?

## 개념과 동작 원리

벡터 검색에서는 **무엇을 가깝다고 볼지**(거리·유사도 기준)와 **어떻게 찾을지**(탐색 방식)가 별개의 선택입니다.

- **정확 검색 (k-NN, Flat)**: 질문 벡터와 저장된 모든 벡터의 거리를 계산해 가장 가까운 k개를 고릅니다. 결과는 정확하지만, 계산량이 `벡터 수 × 차원 수`에 비례합니다. 384차원 벡터 1,000만 개라면 질문 하나에 약 38억 번의 곱셈이 필요합니다.
- **근사 검색 (ANN, Approximate Nearest Neighbor)**: 정확도를 조금 양보하는 대신 일부 후보만 탐색해 속도를 크게 높입니다. 얼마나 놓치는지는 **recall@k**(정확 검색의 top-k 중 ANN이 찾아낸 비율)로 잽니다.

ANN 중 가장 널리 쓰이는 방식이 **HNSW**(Hierarchical Navigable Small World)입니다. Chroma, Qdrant, Milvus, pgvector 등 대부분의 벡터 DB가 HNSW를 지원합니다.

<Figure
  src="images/lessons/07-rag/ann-hnsw/mechanism.svg"
  alt="HNSW의 세 층. 노드가 적은 Layer 2의 진입점에서 출발해 질문에 가까운 노드로 이동하고, 더 가까운 이웃이 없으면 아래 층으로 내려가 Layer 0의 촘촘한 그래프에서 가장 가까운 이웃을 찾는 탐색 경로"
  caption="주황 화살표가 탐색 경로, 점선이 층을 내려가는 지점, 초록 노드가 최종 결과입니다."
/>

HNSW는 고속도로와 일반 도로를 함께 쓰는 길 찾기와 비슷합니다.

- **구조**: 맨 아래 Layer 0에는 모든 벡터가 가까운 이웃끼리 촘촘하게 연결되어 있습니다. 위층으로 갈수록 노드가 적고 연결이 멀리 뻗어 있습니다. 새 벡터가 몇 층까지 올라갈지는 확률로 정해지며, 위층일수록 확률이 급격히 낮아집니다.
- **탐색**: 맨 위층의 진입점에서 출발해, 지금 노드의 이웃 중 질문에 더 가까운 노드로 계속 이동합니다(greedy). 더 가까운 이웃이 없으면 한 층 내려가 같은 과정을 반복합니다. Layer 0에서는 후보 `ef`개를 유지하며 넓게 탐색한 뒤 가장 가까운 k개를 반환합니다.
- **속도**: 위층에서 크게 이동하고 아래층에서 세밀하게 좁히므로, 실험적으로 데이터 수가 늘어도 탐색 시간이 로그에 가깝게 증가합니다.

## 자료와 요청의 흐름

HNSW의 성능은 세 가지 파라미터로 조절합니다.

| 파라미터          | 의미                            | 키우면                 |
| ----------------- | ------------------------------- | ---------------------- |
| `M`               | 노드 하나가 연결하는 이웃 수    | recall↑, 메모리↑       |
| `ef_construction` | 색인을 만들 때 살펴보는 후보 수 | 색인 품질↑, 구축 시간↑ |
| `ef_search`       | 검색할 때 유지하는 후보 수      | recall↑, 지연↑         |

ANN의 다른 대표 방식으로 **IVF**(Inverted File)가 있습니다.

<Figure
  src="images/lessons/07-rag/ann-hnsw/ivf.svg"
  alt="벡터 공간을 다섯 개 군집으로 나누고 질문에 가까운 군집 두 개만 탐색하는 IVF 그림과, Flat, IVF, HNSW의 특징을 비교한 카드"
  caption="IVF는 nprobe개 군집만 비교합니다. 질문이 군집 경계에 있으면 정답을 놓칠 수 있습니다."
/>

IVF는 k-means로 공간을 여러 군집으로 미리 나누고, 검색할 때 질문에 가까운 군집 `nprobe`개 안의 벡터만 비교합니다. 메모리를 적게 쓰지만 군집 중심을 먼저 학습해야 하고, 데이터 분포가 바뀌면 다시 학습해야 할 수 있습니다.

설정을 고를 때는 같은 질문 집합에서 정확 검색 결과를 정답으로 두고, ANN의 recall@k·지연·메모리를 함께 측정합니다. PostgreSQL도 pgvector 확장으로 HNSW·IVFFlat 인덱스를 쓸 수 있으므로 관계형 DB와 벡터 검색은 배타적인 선택이 아닙니다.

```sql
-- pgvector: 코사인 거리 기준 HNSW 인덱스
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;  -- 검색 시 후보 수
```

## 비교와 한계

| 방식             | 장점                        | 단점                                                         |
| ---------------- | --------------------------- | ------------------------------------------------------------ |
| Flat (정확 검색) | 항상 정확, 색인 구축 불필요 | 데이터에 비례해 느려짐                                       |
| IVF              | 메모리 적음, 대규모에 적합  | 군집 학습 필요, 경계에서 누락                                |
| HNSW             | 빠르고 recall이 높음        | 그래프를 메모리에 두어 메모리 사용이 큼, 삽입·삭제 비용이 큼 |

- **메모리**: HNSW는 벡터 외에 노드마다 `M`개 안팎의 연결 정보를 메모리에 둡니다.
- **삽입·삭제**: 새 벡터를 넣을 때마다 각 층에서 이웃을 찾아 연결을 갱신하므로 색인 구축이 느립니다. 삭제는 보통 표시만 해 두었다가 나중에 정리합니다.
- **필터와 함께 쓸 때**: "카테고리 = 과일"처럼 조건을 걸면, 그래프 탐색 중 조건에 맞는 노드가 적어져 recall이 떨어질 수 있습니다. 벡터 DB마다 필터 처리 방식이 다르므로 실제 조건으로 측정합니다.
- 데이터가 수만 건 이하라면 정확 검색만으로도 충분히 빠른 경우가 많습니다. 색인은 필요해질 때 도입합니다.

## 전체 과정과 연결

상품 상담 서비스가 사내 문서의 최신 정책에 근거해 답하려면 문서를 준비하는 과정과 질문에 답하는 과정이 모두 필요합니다. 문서 분할·임베딩·색인 갱신은 사전 준비이고, 질문 임베딩·검색·근거 전달·생성은 요청 처리입니다. ANN 색인은 이 중 "검색"을 빠르게 만들며, 이 흐름은 리뷰 분류 모델의 학습 과정과 구별되는 선택적 확장입니다.

<Callout title="판단할 때 확인하기">

빠른 응답과 정답 이웃의 재현율을 함께 측정합니다. `ef_search`를 올리면 recall이 오르지만 지연도 늘어납니다.

</Callout>

<LessonSummary>

정확 검색은 모든 벡터와 거리를 계산해 정확하지만 데이터에 비례해 느려지고, ANN은 일부 후보만 탐색해 속도를 높이는 대신 일부를 놓칠 수 있습니다. HNSW는 여러 층의 이웃 그래프를 위층부터 내려가며 탐색해 빠르고 recall이 높지만 메모리를 많이 쓰고, IVF는 군집을 나눠 가까운 군집만 비교합니다.
