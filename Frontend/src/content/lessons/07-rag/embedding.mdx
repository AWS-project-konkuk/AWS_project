## ‘반품’과 ‘물건 돌려보내기’는 얼마나 가까울까요?

고객은 ‘물건을 돌려보내고 싶어요’라고 쓰고, 도움말에는 ‘반품 절차’라고 적혀 있습니다. 글자가 다른 두 표현을 컴퓨터는 어떻게 같은 이야기로 묶을까요? 문장을 벡터로 바꾸는 임베딩을 쓰면 이 관계를 숫자 사이의 거리로 비교할 수 있습니다.

## 개념 이해

**벡터 임베딩**(Vector Embedding)은 텍스트·이미지·오디오 같은 비정형 데이터를 고정 길이의 숫자 배열(벡터)로 바꾼 표현입니다. 임베딩 모델은 의미가 비슷한 입력이 서로 가까운 위치에 놓이도록 학습되어 있습니다.

```text
"고양이"  → [ 0.12, -0.54,  0.90, ... ]   (384개 숫자)
"강아지"  → [ 0.10, -0.49,  0.85, ... ]   ← 고양이와 가까움
"지하철"  → [-0.71,  0.33, -0.02, ... ]   ← 멂
```

키워드 일치나 TF-IDF는 같은 단어가 나와야 관련 있다고 판단합니다. 그래서 "달콤한 과일"로 검색하면 "사과는 붉은색을 띠는 아주 맛있는 과일입니다"는 찾아도, "바나나는 길고 노랗다"처럼 단어가 겹치지 않는 문장은 놓칩니다. 임베딩은 단어가 달라도 의미가 비슷하면 가까운 벡터를 만들기 때문에 이런 문장도 찾을 수 있습니다.

두 벡터가 얼마나 가까운지는 보통 다음 셋 중 하나로 계산합니다.

| 기준               | 계산              | 특징                                                              |
| ------------------ | ----------------- | ----------------------------------------------------------------- |
| 코사인 유사도      | `A·B / (‖A‖ ‖B‖)` | 방향만 비교 (길이 무시). 1이면 같은 방향, 0이면 무관, -1이면 반대 |
| 내적 (dot product) | `A·B`             | 길이까지 반영. 벡터를 정규화하면 코사인과 같음                    |
| 유클리드 거리 (L2) | `‖A − B‖`         | 좌표 사이의 직선 거리. 작을수록 가까움                            |

텍스트 임베딩에는 코사인 유사도를 가장 많이 씁니다. 벡터를 길이 1로 정규화해 두면 세 기준이 같은 순위를 냅니다.

차원 수는 모델마다 다릅니다. ChromaDB의 기본 임베딩 모델인 `all-MiniLM-L6-v2`는 384차원, OpenAI의 `text-embedding-3-small`은 1536차원입니다. 차원이 높다고 항상 더 좋은 것은 아니며, 저장 공간과 검색 비용이 차원에 비례해 늘어납니다.

## 관찰한 결과 해석하기

질문 예시를 바꾸며 가까운 문서의 위치를 살펴보세요.

<Activity />

저장할 때와 질문할 때 **같은 임베딩 모델**을 사용해야 합니다. 좌표의 한 축이 특정 단어의 의미를 뜻하는 것도 아닙니다. 의미는 숫자 하나가 아니라 수백 개 숫자의 조합으로 표현됩니다.

<Figure
  src="images/lessons/07-rag/embedding/same-model.svg"
  alt="문서를 모델 A로 임베딩해 벡터 DB에 저장한 뒤, 질문도 모델 A로 임베딩하면 관련 문서가 상위에 오지만, 질문을 같은 384차원의 다른 모델 B로 임베딩하면 거리 비교가 의미 없어지는 비교 그림"
  caption="차원이 같으면 계산은 되지만, 의미 공간이 같다는 보장은 없습니다."
/>

ChromaDB로 직접 확인해 볼 수 있습니다. 컬렉션에 문서를 넣으면 기본 임베딩 함수가 자동으로 벡터를 만들고, `include`에 `"embeddings"`를 지정해야 벡터 값을 돌려줍니다. 성능과 용량을 위해 기본값으로는 문서와 ID만 반환하기 때문입니다.

```python
import chromadb

client = chromadb.Client()
collection = client.create_collection(
    name="study",
    configuration={"hnsw": {"space": "cosine"}},  # 기본값은 l2
)
collection.add(
    ids=["doc1", "doc2", "doc3", "doc4"],
    documents=[
        "쿠버네티스는 컨테이너 오케스트레이션 도구입니다.",
        "사과는 붉은색을 띠는 아주 맛있는 과일입니다.",
        "피처 스토어는 머신러닝 데이터의 재사용성을 높여줍니다.",
        "바나나는 길고 노란 과일이며 원숭이가 좋아합니다.",
    ],
)
got = collection.get(ids=["doc2"], include=["embeddings"])
print(len(got["embeddings"][0]))  # 384
```

## 적용 조건과 한계

- **같은 모델·같은 전처리**: 차원이 같아도 다른 모델의 좌표는 호환되지 않습니다. 모델을 바꾸면 저장된 문서 전체를 다시 임베딩해야 합니다.
- **거리 기준 확인**: 벡터 DB마다 기본 거리 기준이 다릅니다. Chroma는 기본값이 L2이며, 컬렉션을 만든 뒤에는 바꿀 수 없으므로 처음부터 지정합니다.
- **언어와 도메인**: 영어 위주로 학습한 모델은 한국어 문장의 의미를 잘 구분하지 못할 수 있습니다. 사내 용어나 전문 분야라면 다국어·도메인 모델을 비교해 고릅니다.
- **입력 길이 제한**: 임베딩 모델은 한 번에 받을 수 있는 토큰 수가 정해져 있어, 긴 문서는 잘라서(청킹) 임베딩합니다. 이 내용은 RAG 강의에서 이어집니다.

## 전체 과정과 연결하기

임베딩은 RAG의 출발점입니다. 문서를 벡터로 바꿔 저장하고, 질문도 같은 모델로 벡터로 바꾼 뒤, 두 벡터의 가까움으로 관련 문서를 찾습니다. 임베딩의 품질이 낮으면 이후의 검색과 생성이 아무리 좋아도 엉뚱한 근거가 전달됩니다.

<Callout title="판단할 때 확인하기">

문서와 질문은 같은 모델·전처리·거리 기준을 사용해야 합니다. 차원이 같다는 사실만으로 유사도 비교가 의미 있어지지 않습니다.

</Callout>
