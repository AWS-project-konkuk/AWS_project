## 이번 미션

상품 상담 챗봇이 "구매한 상품을 반품할 수 있나요?"라는 질문에 엉뚱한 답을 합니다. 살펴보니 두 가지 문제가 겹쳐 있습니다.

1. 문서는 한 임베딩 모델로 저장했는데, 질문은 **다른 모델**로 임베딩하고 있습니다. 차원 수는 같아서 오류 없이 검색은 되지만 결과가 엉망입니다.
2. 그 결과 반품 정책 대신 **무관한 날씨 문서**가 근거로 전달되고, 모델은 그 근거에 맞춰 답을 만들어 냅니다. 이 실습의 검색 노드는 두 공간이 다르다는 것을 감지해 검색을 차단합니다. 실제 시스템은 차원이 같으면 차단하지 않고 조용히 틀린 결과를 돌려줄 수 있습니다.

## 설계하고 비교할 것

실습은 EC2, 저장소, Gateway 세 서비스로 구성됩니다. 시작은 원본 문서와 반품 질문을 보내고, 도착은 근거 문서 ID가 붙은 답변을 확인합니다. 처음에는 **문서 임베딩 → 색인**과 **API 요청 처리 → 도착**만 연결되어 있고, 질문 경로는 직접 만들어야 합니다.

1. EC2에 **임베딩**을 하나 더 만들어 질문 임베딩으로 씁니다. 저장소에는 **검색**을 만듭니다.
2. 시작의 질문을 질문 임베딩과 API 요청 처리에 연결합니다. 프롬프트에는 근거뿐 아니라 질문 원문도 필요합니다.
3. 질문 임베딩 → 검색, 색인 → 검색, 검색 → API 요청 처리를 연결하고 실행합니다.
4. 저장소는 처음에 객체 저장소(S3)라서 색인과 검색을 쓸 수 없습니다. **저장소 유형**을 `Vector DB`로 바꿉니다.
5. 다시 실행하면 질문 임베딩은 공간 B, 문서 임베딩은 공간 A라서 검색이 차단됩니다.
6. 질문 임베딩의 **임베딩 공간**을 문서 임베딩과 같은 공간으로 맞추고 다시 실행합니다.

| 확인할 것        | 실패 상태             | 개선 상태                   | 확인 방법                            |
| ---------------- | --------------------- | --------------------------- | ------------------------------------ |
| 질문 임베딩 공간 | 다른 모델의 벡터 공간 | 저장 문서와 같은 벡터 공간  | 저장·질문에 쓴 모델 이름과 버전 비교 |
| 검색 결과        | 검색 차단             | 반품 정책 문서 `doc-return` | 도착의 근거 문서 ID                  |

청킹 단위는 임베딩 노드의 설정입니다. 문장 단위로 바꾸면 벡터 수가 늘어나지만 같은 문서가 근거로 검색됩니다. 처음 있던 노드는 삭제할 수 없고, 직접 만든 노드는 삭제할 수 있습니다. 결과 패널의 **관찰할 조건**(공간 불일치 차단, 근거 ID가 붙은 답변)을 확인한 뒤 이해 확인에 답하면 실습이 완료됩니다.

ChromaDB로 같은 상황을 재현해 볼 수 있습니다. 컬렉션은 만들 때 지정한 임베딩 함수를 기억하므로, 질문도 `query_texts`로 넘기면 같은 모델로 임베딩됩니다. 직접 다른 모델로 만든 벡터를 `query_embeddings`로 넘기면 차원이 같아도 이번 미션과 같은 문제가 생깁니다.

```python
# 같은 컬렉션의 임베딩 함수 사용 → 저장 문서와 같은 벡터 공간
results = collection.query(query_texts=["구매한 상품을 반품할 수 있나요?"], n_results=2)
print(results["documents"])   # 검색된 근거를 먼저 눈으로 확인
print(results["distances"])   # 거리가 모두 비슷하게 크다면 의심
```

## 실습에서 가져갈 이해

Feature Store는 피처의 일관된 제공, 벡터 검색은 관련 문서 조회, RAG는 근거를 생성 문맥에 전달하는 역할입니다. 서로 같은 기능이 아닙니다.

| 구성 요소     | 다루는 것                         | 핵심 질문                               |
| ------------- | --------------------------------- | --------------------------------------- |
| Feature Store | 정형 피처 (클릭 수, 결제 금액 등) | 학습과 서빙이 같은 피처 값을 쓰는가     |
| Vector DB     | 임베딩 벡터와 원문                | 질문과 의미가 가까운 문서를 빨리 찾는가 |
| RAG           | 검색한 근거 + LLM                 | 답이 전달한 근거를 따르는가             |

흥미롭게도 Feature Store의 "학습-서빙 불일치(Training-Serving Skew)"와 이번 미션의 "저장-질문 임베딩 불일치"는 같은 종류의 문제입니다. 준비할 때와 사용할 때 처리 방식이 달라지면, 오류 없이 조용히 틀린 결과가 나옵니다.

## 적용 조건과 한계

- 이 활동은 고정된 문서와 응답을 사용하는 교육용 모형입니다. 실제 시스템에서는 같은 질문에도 LLM의 답이 조금씩 달라질 수 있습니다.
- 임베딩 모델을 업그레이드할 때는 기존 문서를 모두 새 모델로 다시 임베딩한 새 컬렉션을 만들고, 검색 품질을 비교한 뒤 전환합니다.
- 관련 근거를 전달해도 모델이 근거를 무시하거나 일부만 쓸 수 있습니다. 실제 시스템에서는 근거가 없을 때 답을 보류하도록 프롬프트를 설계하고, 근거 충실도를 따로 평가합니다. 이 실습에는 답변 보류 설정이 없습니다.

## 전체 과정과 연결하기

이번 단원에서는 HNSW로 빠르게 찾고, 임베딩으로 의미를 좌표로 바꾸고, 조건 검색과 유사도 검색을 구분한 뒤, RAG의 두 경로를 살펴보았습니다. 이 미션은 그 연결이 "동작한다"와 "제대로 동작한다"가 다르다는 것을 보여 줍니다. 문서와 질문을 같은 벡터 공간으로 맞추고, 검색된 근거를 확인하고, 답이 근거를 따르는지까지 확인해야 합니다.
