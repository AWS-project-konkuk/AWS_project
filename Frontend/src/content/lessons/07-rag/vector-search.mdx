## 검색창에 ‘집 앞에 두고 가 주세요’를 쳐 봤습니다

쇼핑몰에서 ‘집 앞에 두고 가 주세요’를 검색했더니 결과가 없습니다. 알고 보니 도움말 제목은 ‘비대면 배송’입니다. 답이 있는데 제목을 먼저 알아야 찾을 수 있다면 검색창이 퀴즈를 내는 셈입니다. 표현이 달라도 관련 문서를 어떻게 찾을까요?

## 개념 이해

관계형 질의는 가격·분류·정확한 키 같은 조건으로 데이터를 좁히는 데 적합합니다. 벡터 검색은 임베딩의 거리·유사도로 가까운 후보를 찾습니다. 키워드 일치와 의미가 비슷한 것은 같은 기준이 아닙니다.

| 검색 기준   | 예시                         | 주요 판단          |
| ----------- | ---------------------------- | ------------------ |
| 조건 일치   | 가격 &lt; 10000, 분류 = 과일 | 정확한 속성 조건   |
| 키워드 포함 | 본문에 "과일"이 들어간 문서  | 같은 단어가 있는가 |
| 벡터 유사도 | "달콤한 과일"과 가까운 문서  | 임베딩 공간의 거리 |

두 방식은 데이터를 훑는 방법부터 다릅니다.

<Figure
  src="images/lessons/07-rag/vector-search/rdbms-vs-vector.svg"
  alt="왼쪽은 B+Tree 인덱스에서 age = 42를 찾기 위해 루트의 30과 60 사이로 내려가 가운데 노드에 도달하는 과정, 오른쪽은 벡터 공간에서 질문 별표와 가장 가까운 점 세 개를 원으로 묶은 top-k 검색"
  caption="B+Tree는 값의 순서로, 벡터 인덱스는 거리로 후보를 찾습니다."
/>

- **RDBMS**는 전체 행을 차례로 검사하는 **Full Table Scan**이나, 값을 정렬해 둔 **B+Tree 인덱스**로 원하는 행을 찾습니다. B+Tree는 "42는 30보다 크고 60보다 작다"처럼 값의 대소 비교로 내려가므로, 정확히 일치하는 값(`WHERE name = 'Kim'`)이나 범위(`BETWEEN 20 AND 29`)를 찾는 데 효율적입니다.
- **벡터 DB**는 "질문과 가장 가까운 k개"를 찾습니다. 모든 벡터와 거리를 계산하는 **Flat Scan**은 정확하지만 데이터에 비례해 느려지므로, 보통 HNSW·IVF 같은 **ANN 인덱스**를 씁니다.

그렇다면 왜 B+Tree로 가까운 벡터를 찾을 수 없을까요? B+Tree는 값을 한 줄로 정렬할 수 있을 때 동작합니다. 384차원 벡터에는 "이 벡터가 저 벡터보다 크다"는 순서가 없습니다. 한 차원으로 정렬하면 다른 383개 차원의 거리 정보가 사라지고, 여러 차원을 나누는 k-d tree 같은 구조도 차원이 수백 개가 되면 결국 거의 모든 노드를 방문하게 됩니다. 그래서 고차원 벡터에는 그래프·군집 기반의 전용 인덱스가 필요합니다.

## 관찰한 결과 해석하기

같은 질문으로 정확한 문구 검색과 유사도 검색의 결과를 비교하세요.

<Activity />

정확한 문구 검색은 질문의 단어가 그대로 들어간 문서만 찾고, 유사도 검색은 단어가 달라도 의미가 가까운 문서를 찾습니다. 하지만 유사도 검색은 항상 "가장 가까운 k개"를 돌려주므로, 관련 있는 문서가 없어도 무언가를 결과로 내놓는다는 점에 주의합니다.

RDBMS도 확장 기능으로 벡터 검색을 할 수 있고, 반대로 벡터 DB도 메타데이터 필터를 지원합니다. 실제 서비스에서는 둘을 함께 쓰는 경우가 많습니다.

```sql
-- PostgreSQL + pgvector: 조건으로 좁힌 뒤 유사도로 정렬
SELECT id, content
FROM products
WHERE category = '과일' AND price < 10000            -- 조건 일치
ORDER BY embedding <=> '[0.12, -0.54, ...]'::vector   -- 코사인 거리
LIMIT 3;
```

```python
# Chroma: 메타데이터 필터 + 유사도 검색
collection.query(
    query_texts=["달콤한 과일"],
    n_results=3,
    where={"category": "과일"},
)
```

## 적용 조건과 한계

- **정확한 조건이 필요한 질문**: "주문번호 1234의 배송 상태"처럼 답이 하나로 정해진 질문은 벡터 검색보다 조건 검색이 정확합니다.
- **고유명사·코드**: 제품 코드, 에러 메시지처럼 철자가 중요한 검색은 키워드 검색이 더 잘 맞을 수 있습니다. 그래서 키워드 검색과 벡터 검색의 점수를 합치는 **하이브리드 검색**도 많이 씁니다.
- **도구 선택**: 벡터 DB는 Pinecone(관리형 클라우드), Milvus·Qdrant(오픈소스), Chroma(가볍게 시작하기 쉬움), PostgreSQL의 pgvector(기존 DB에 확장) 등이 있습니다. Vector DB가 RDBMS의 트랜잭션·조인 같은 기능을 대체하지는 않으므로, 제품 이름보다 데이터 규모·필터 요구·운영 부담으로 고릅니다.

## 전체 과정과 연결하기

속성 조건과 키워드로 후보를 좁힐 수도 있고 임베딩의 거리·유사도로 관련 후보를 찾을 수도 있습니다. RAG에서는 질문과 의미가 가까운 문서를 찾는 단계에 벡터 검색을 쓰고, 날짜·권한·카테고리 같은 조건은 메타데이터 필터로 함께 적용합니다.

<LessonSummary>

RDBMS는 B+Tree로 값의 순서를 따라 정확한 값이나 범위를 찾고, 벡터 DB는 ANN 인덱스로 질문과 거리가 가까운 top-k를 찾습니다. 고차원 벡터에는 정렬할 수 있는 순서가 없어 B+Tree가 동작하지 않기 때문에 전용 인덱스가 필요합니다. 벡터 검색은 선택한 표현 공간과 유사도 기준에 따라 순위가 달라집니다.
