## 문제 상황

Kubernetes에서 모델을 학습하는 Pod가 임시 저장 공간인 **`emptyDir` 볼륨을 컨테이너의 `/checkpoints` 경로에 마운트**하고, 여기에 체크포인트를 저장하고 있습니다. `/checkpoints`는 파일을 읽고 쓰는 경로이며, 실제 파일은 그 경로에 연결된 `emptyDir`에 저장됩니다.

학습 도중 문제가 생겨 기존 Pod를 삭제하고 새 Pod를 만들었습니다. 이때 기존 Pod의 `emptyDir`도 함께 삭제되어 체크포인트가 사라졌습니다. 같은 이름의 Pod를 다시 만들어도 새로운 빈 `emptyDir`이 생성되므로 이전 파일은 돌아오지 않습니다.

`emptyDir`은 **같은 Pod 안에서 컨테이너만 재시작할 때는 유지되지만, Pod가 삭제되면 함께 사라집니다.** 이 상황은 컨테이너 재시작이 아니라 Pod 자체가 교체된 경우입니다.

Pod가 교체되어도 데이터를 계속 사용하려면 Pod와 독립적으로 관리되는 저장 공간을 연결해야 합니다.

  src="/images/lessons/02-storage/pv-pvc/emptydir_pvc_official_style.svg"
  alt="Pod 임시 볼륨과 PVC 연결 볼륨의 데이터 보존 범위를 비교한 그림"
  caption="비교"
/>

그렇다면 Pod는 실제 저장소의 위치와 종류를 모두 알고 있어야 할까요?

Kubernetes에서는 Pod가 **PersistentVolumeClaim(PVC)**을 요청하고, 클러스터가 조건에 맞는 **PersistentVolume(PV)**을 연결합니다.

**이번 학습에서는 Pod, PVC, PV의 역할과 연결 관계를 알아보고, Pod 교체 뒤에도 데이터를 다시 사용하는 방법을 학습합니다.**

## 개념과 동작 원리

### 1. PersistentVolume(PV)

PV는 Kubernetes 클러스터가 사용할 수 있는 **저장 자원**입니다. 저장 용량, 접근 모드, StorageClass, 실제 스토리지 정보와 반환 정책 등이 포함될 수 있습니다. PV의 수명은 이를 사용하는 개별 Pod의 수명과 분리되어 있습니다.

PV는 네임스페이스에 속하지 않는 클러스터 범위의 리소스입니다. 저장소 자체를 Kubernetes 객체로 바꾸는 것이 아니라, 실제 저장소에 연결할 정보를 표현합니다. 클러스터 범위라고 해서 모든 Pod가 같은 파일에 자동으로 접근하는 것은 아닙니다.

### 2. PersistentVolumeClaim(PVC)

PVC는 애플리케이션이 필요한 저장 조건을 작성한 **요청서**이며, 네임스페이스에 속합니다. Pod는 같은 네임스페이스의 PVC를 참조합니다.

- 필요한 저장 용량
- 읽기·쓰기 접근 모드
- 사용할 StorageClass
- 파일 시스템 또는 블록 장치와 같은 볼륨 모드

PVC는 조건이 맞는 기존 PV와 연결되거나, StorageClass와 provisioner를 통해 새로운 볼륨을 동적으로 만들 수 있습니다.

### 3. Pod

Pod는 실제 PV를 직접 고르는 대신 PVC의 이름을 참조합니다. 그리고 `volumeMounts`를 이용해 컨테이너 안의 경로에 볼륨을 연결합니다.

<NodeExample practice />

아래 PVC는 10GiB의 저장 공간을 요청합니다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: training-checkpoints
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

PVC를 만든 것만으로 컨테이너에 자동 마운트되지는 않습니다. Pod 명세에서도 요청과 경로를 연결해야 합니다.

```yaml
spec:
  volumes:
    - name: checkpoints
      persistentVolumeClaim:
        claimName: training-checkpoints
  containers:
    - name: trainer
      volumeMounts:
        - name: checkpoints
          mountPath: /checkpoints
```

### 4. StorageClass와 CSI

**StorageClass**는 어떤 provisioner와 설정으로 볼륨을 만들지 정의합니다. **CSI(Container Storage Interface)**는 Kubernetes와 저장소 드라이버가 소통하는 표준 인터페이스입니다. CSI 드라이버는 Kubernetes 핵심 코드 밖에서 독립적으로 배포·관리하는 Out-of-Tree 방식으로 사용할 수 있습니다.

```text
Pod → PVC → 조건에 맞는 PV → 실제 저장소
       │
       └─ 동적 생성: StorageClass → provisioner·CSI 드라이버 → 저장소와 PV 준비
```

CSI 드라이버의 컨트롤러 구성 요소는 볼륨 생성·삭제·연결 등을 담당하고, 노드 구성 요소는 해당 노드에서 볼륨을 준비하고 마운트합니다. 지원 작업은 드라이버에 따라 다릅니다. StorageClass가 데이터를 직접 나누어 저장하는 것은 아닙니다.

앞의 PVC 예시는 `storageClassName`을 생략했으므로 클러스터의 기본 StorageClass 설정을 확인해야 합니다. 수동으로 PV를 만드는 정적 프로비저닝에서는 PV와 PVC의 클래스·용량·접근 모드 등을 맞춥니다. [StorageClass 문서](https://kubernetes.io/docs/concepts/storage/storage-classes/)에서 동적 생성 설정을 확인할 수 있습니다.

## 접근 모드 이해하기

| 접근 모드              | 의미                               |
| ---------------------- | ---------------------------------- |
| RWO(ReadWriteOnce)     | 하나의 노드에서 읽기·쓰기로 마운트 |
| ROX(ReadOnlyMany)      | 여러 노드에서 읽기 전용으로 마운트 |
| RWX(ReadWriteMany)     | 여러 노드에서 읽기·쓰기로 마운트   |
| RWOP(ReadWriteOncePod) | 하나의 Pod에서 읽기·쓰기로 마운트  |

RWO는 항상 하나의 Pod만 사용할 수 있다는 뜻이 아닙니다. 같은 노드의 여러 Pod가 사용할 수도 있습니다. 하나의 Pod로 제한해야 한다면 CSI 드라이버가 RWOP를 지원하는지 확인해야 합니다.

모든 스토리지가 모든 접근 모드를 제공하는 것도 아닙니다. PVC에 모드를 적는 것만으로 기반 저장소에 없는 기능이 생기지는 않습니다.

분산 학습에서 여러 노드가 동일한 데이터셋을 읽기만 한다면 ROX 요구를 검토할 수 있습니다. 다만 저장소와 드라이버가 지원해야 하며, RWX 공유 저장소를 읽기 전용으로 마운트하는 구성도 가능합니다. 입력 데이터셋과 결과 저장 경로를 분리하고, 결과는 실행 ID나 rank별 경로에 기록해 충돌을 줄입니다.

접근 모드는 볼륨의 연결 능력을 나타내며 파일 잠금이나 모든 쓰기 차단을 대신하지 않습니다. 읽기 전용 사용에는 Pod의 마운트 설정과 저장소 권한도 확인합니다. [PV 접근 모드 문서](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes)를 참고하세요.

## 문제가 생겼을 때 확인하기

PVC가 `Pending` 상태라면 다음 항목을 확인합니다.

1. 요청한 용량을 제공할 수 있는가?
2. 요청한 접근 모드를 드라이버가 지원하는가?
3. StorageClass 이름과 provisioner가 올바른가?
4. Pod가 올바른 `claimName`을 참조하는가?
5. `volumes`와 `volumeMounts`의 이름이 일치하는가?

## 비교와 한계

- PVC는 저장 공간을 요청하고 연결하는 객체이며 백업 기능이 아닙니다.
- 일반적인 PVC 볼륨은 Pod만 삭제해도 PVC와 PV가 남습니다. PVC까지 삭제할 때는 PV의 회수 정책을 확인해야 합니다.
- 여러 Pod가 볼륨을 마운트할 수 있어도 같은 파일을 안전하게 수정하는 것은 별도 문제입니다.
- S3 버킷은 일반적인 PV와 같은 방식으로 자동 연결되지 않습니다. 필요한 드라이버나 애플리케이션 접근 방식을 확인해야 합니다.

## 전체 과정과 연결

PV와 PVC는 Pod가 사용할 저장 공간을 Kubernetes에서 연결하는 방법입니다. 원본 데이터의 장기 보관, 체크포인트의 보존, 반복 읽기 캐시는 목적이 다르므로 각각의 수명과 공유 조건을 판단해야 합니다.

> **판단할 때 확인하기**
>
> “Pod가 요청한 용량·접근 모드·StorageClass를 실제 저장소가 제공할 수 있을까?”

<LessonSummary>

**PV는 클러스터의 저장 자원**, **PVC는 애플리케이션의 저장 요청**입니다. Pod는 PVC를 참조하고 컨테이너 경로에 볼륨을 마운트해야 실제 파일을 사용할 수 있습니다. PVC와 PV가 연결되어도 백업과 동시 쓰기 안전성이 자동으로 보장되지는 않습니다.

</LessonSummary>
