## 문제 상황

Kubernetes 환경에서 AI 모델을 학습하기 위해 저장소를 선택하려고 합니다.

모델 학습 과정에서는 다음과 같은 데이터가 사용됩니다.

- **운영체제와 애플리케이션 파일**: 하나의 서버에서 빠르게 읽고 써야 합니다.
- **공통 학습 데이터셋**: 여러 학습 Pod가 같은 파일과 디렉터리를 읽어야 합니다.
- **모델 아티팩트**: 학습 서버가 사라진 뒤에도 보관하고 다른 작업에서 다시 사용해야 합니다.

이 데이터들을 모두 같은 저장 방식으로 관리해도 될까요?

Block, File, Object Storage는 데이터를 저장한다는 공통점이 있지만, 프로그램이 데이터를 찾고 읽고 수정하는 방법이 서로 다릅니다. 따라서 단순히 가장 빠르거나 가장 큰 저장소를 고르는 것이 아니라, 애플리케이션이 요구하는 접근 방식을 먼저 확인해야 합니다.

이번 학습에서는 세 저장 방식의 차이를 알아보고, AI 모델 학습 과정의 데이터에 어떤 방식이 알맞은지 판단합니다.

## 먼저 이렇게 떠올려 보세요

세 저장 방식의 차이는 **데이터를 어떤 모습으로 건네받는가**에서 시작합니다.

| 저장 방식 | 익숙한 모습으로 비유하면                   | 프로그램이 받는 것    |
| --------- | ------------------------------------------ | --------------------- |
| Block     | 내 컴퓨터에 새 SSD를 꽂는 것               | 비어 있는 디스크 장치 |
| File      | 여러 사람이 같은 공용 폴더를 여는 것       | 파일과 폴더 경로      |
| Object    | 이름표가 붙은 물건을 보관 창고에 맡기는 것 | 버킷 안의 객체 키     |

예를 들어 **model.pt**라는 모델 파일을 사용한다고 생각해 보겠습니다.

### Block은 “내 서버에 디스크를 하나 더 연결하는 것”

서버는 먼저 디스크를 연결하고, 파일 시스템을 만든 뒤 **/models/model.pt**라는 파일을 저장합니다. **한 서버가 자신의 작업 디스크처럼 사용하는 모습**을 떠올리면 쉽습니다.

다만 이 디스크를 한 서버에 연결했다고 해서 다른 노드의 Pod에서도 같은 파일이 자동으로 보이지는 않습니다.

### File은 “여러 컴퓨터가 같은 공용 폴더를 여는 것”

여러 Pod가 같은 공유 저장소를 **/shared**에 마운트하면 모두 **/shared/model.pt**라는 경로로 파일을 볼 수 있습니다. **학교나 회사의 공용 드라이브**와 비슷합니다.

여러 사용자가 같은 문서를 동시에 수정하면 충돌할 수 있듯이, 여러 Pod가 같은 파일을 동시에 쓸 때도 조정이 필요합니다.

### Object는 “이름표로 물건을 맡기고 찾아오는 보관 창고”

프로그램은 **models/run-42/model.pt**라는 객체 키로 모델을 저장하고, 필요할 때 GET 요청으로 가져옵니다. **파일이 있는 디스크를 직접 연결하는 대신, 보관소에 키를 말하고 객체를 받는 방식**입니다.

학습 서버를 종료해도 객체는 보관소에 남으므로 다른 평가·배포 작업에서 다시 찾기 좋습니다. 대신 기존 프로그램이 로컬 파일 경로를 요구한다면 객체를 먼저 내려받는 과정이 필요할 수 있습니다.

## 개념과 동작 원리

### 1. Block Storage

Block Storage는 데이터를 고정된 크기의 블록으로 나누어 저장할 수 있는 **블록 단위 장치**를 제공합니다. 서버에서는 새로운 디스크가 연결된 것처럼 보이며, 보통 그 위에 파일 시스템을 만든 뒤 사용합니다.

장치에는 파일 경로 대신 **논리 블록 주소(LBA, Logical Block Addressing)**로 읽기·쓰기를 요청합니다. LBA는 HDD나 SSD 등에서 블록의 위치를 논리적으로 지정하는 방식입니다. 파일 시스템을 사용하는 경우에는 파일 시스템이 파일 경로와 파일 내부 위치를 블록 주소로 연결합니다. 따라서 LBA를 사용한다는 이유만으로 모든 작업에서 가장 빠르다고 단정할 수는 없습니다.

> **한 문장으로:** 서버 한 대가 자기 디스크처럼 사용할 저장 공간이 필요할 때 떠올립니다.

- 운영체제나 데이터베이스처럼 낮은 수준의 디스크 접근이 필요한 작업에 적합합니다.
- 일반적으로 특정 서버나 노드에 연결해 사용합니다.
- 디스크를 연결하는 것만으로 노드 간 파일 공유나 동시 쓰기 조정이 자동으로 이루어지지는 않습니다. 여러 노드가 같은 디스크를 사용하려면 다중 연결 지원과 이를 처리할 파일 시스템 등이 필요합니다.

AWS의 대표적인 Block Storage는 Amazon EBS입니다.

### 2. File Storage

File Storage는 데이터를 폴더와 파일로 이루어진 **논리적 계층 구조**로 관리하며, 파일 경로를 통해 읽고 수정합니다. 네트워크 파일 스토리지를 여러 클라이언트가 마운트하면 공통 파일을 읽거나 쓸 수 있습니다.

> **한 문장으로:** 여러 Pod가 같은 폴더와 파일 이름을 봐야 할 때 떠올립니다.

- 기존 프로그램의 파일 읽기·쓰기 방식을 그대로 사용하기 쉽습니다.
- 파일과 디렉터리가 매우 많아지면 목록 조회, 파일 탐색, 메타데이터 처리에 드는 시간이 커질 수 있습니다.
- 여러 Pod나 노드가 같은 디렉터리를 공유해야 할 때 사용할 수 있습니다.
- 여러 작업이 같은 파일을 동시에 수정한다면 충돌을 조정해야 합니다.

AWS의 대표적인 File Storage는 Amazon EFS와 Amazon FSx입니다.

### 3. Object Storage

Object Storage는 데이터와 메타데이터를 **객체** 단위로 저장하며, 버킷과 객체 키를 이용해 찾습니다. 기본적으로 평면적인 키 공간을 사용합니다. 키에 `/`를 넣어 폴더처럼 표현할 수 있지만, 이것만으로 파일 시스템의 디렉터리 구조가 만들어지는 것은 아닙니다.

> **한 문장으로:** 서버와 떨어진 공통 보관소에서 데이터셋이나 모델을 키로 다시 찾을 때 떠올립니다.

- 큰 데이터셋, 모델 파일, 로그와 백업을 장기간 보관하기 좋습니다.
- 서버나 Pod와 저장 공간의 수명을 분리할 수 있습니다.
- 일반적으로 REST API(HTTP/HTTPS)의 GET·PUT 등의 요청으로 객체를 읽고 씁니다.
- 접근 권한을 부여해 여러 노드에서 객체를 공유할 수 있습니다. 다만 일반 파일 시스템 인터페이스를 기본으로 제공하지 않으므로, 파일 경로를 기대하는 프로그램에는 다운로드나 별도 연동이 필요합니다.

AWS의 대표적인 Object Storage는 Amazon S3입니다.

| 저장 방식 | 프로그램이 보는 모습 | 적합한 예시               | 먼저 확인할 조건             |
| --------- | -------------------- | ------------------------- | ---------------------------- |
| Block     | 연결된 디스크        | 운영체제, 데이터베이스    | 연결할 노드, IOPS, 처리량    |
| File      | 파일과 디렉터리      | 여러 Pod의 공유 작업 경로 | 동시 접근, 읽기·쓰기 방식    |
| Object    | 버킷과 객체 키       | 데이터셋, 모델 아티팩트   | API 사용, 객체 크기, 요청 수 |

### MLOps 데이터에 적용하기

OS 부팅 디스크에는 디스크 장치와 파일 시스템이 필요한 만큼 Block을 사용합니다. 여러 학습 노드가 같은 코드·스크립트·데이터 경로를 읽어야 한다면 File을 검토합니다. 원본 데이터셋과 모델 가중치를 실행 서버와 분리해 보관하려면 Object가 적합합니다.

이미지 데이터셋도 하나의 방식만 고집할 필요는 없습니다. 원본은 Object에 보관하고, 학습 때 필요한 데이터를 로컬 디스크에 캐싱하거나 공유 파일 시스템으로 제공할 수 있습니다. 원본 보관과 학습 중 읽기 성능을 각각 설계합니다.

## 지연 시간과 처리량

저장 방식뿐 아니라 실제 요청 형태도 성능에 영향을 줍니다.

Block은 낮은 지연의 임의 읽기·쓰기에 적합하고, 네트워크 File은 파일 경로와 메타데이터 처리 및 네트워크 통신의 영향을 받습니다. Object는 HTTP 요청마다 지연이 발생할 수 있지만, 큰 객체를 병렬로 읽는 작업에서는 높은 처리량을 얻을 수 있습니다. **Block → File → Object 순서로 항상 빠르다고 외우기보다는 지연 시간과 처리량을 나누어 비교해야 합니다.**

- **지연 시간(Latency)**은 요청 하나가 완료될 때까지 걸리는 시간입니다.
- **처리량(Throughput)**은 일정 시간 동안 전송할 수 있는 전체 데이터 양입니다.

작은 파일을 매우 많이 읽으면 요청마다 발생하는 지연과 메타데이터 처리 비용이 커질 수 있습니다. 반대로 큰 파일을 연속으로 읽는 작업에서는 초당 얼마나 많은 데이터를 전달할 수 있는지가 중요합니다.

## 비용을 비교하는 기준

비용은 저장 방식 자체보다 서비스의 과금 단위, 성능 설정, 사용 패턴에 따라 달라집니다.

- **Block:** 할당한 볼륨 용량을 기준으로 과금하는 서비스에서는 내부 공간을 모두 쓰지 않아도 비용이 발생합니다. 이는 개별 블록에 빈 공간이 있어서가 아니라, 용량을 미리 확보하는 과금 방식 때문입니다. 성능 설정에 따른 비용도 확인해야 합니다.
- **File:** 실제 저장량을 기준으로 과금하는 서비스도 있고, 용량이나 처리량을 미리 확보하는 서비스도 있습니다. 항상 “쓴 만큼만 내고 가격은 중간”이라고 단정할 수 없습니다.
- **Object:** 대용량 보관 비용을 낮추기 좋은 경우가 많지만, 저장량 외에 API 요청, 데이터 조회와 전송 비용도 함께 고려해야 합니다.

## 비교와 한계

앞의 활동에서는 **서버 디스크에는 Block**, **공유 폴더에는 File**, **모델 보관에는 Object**를 연결했습니다. 실제로 적용할 때는 각 방식이 제공하는 기능과 추가로 필요한 조건을 함께 확인해야 합니다.

- **Block — 디스크 연결과 파일 공유는 다릅니다.** 한 서버에 연결한 디스크가 다른 노드의 Pod에도 자동으로 보이지는 않습니다. 여러 노드에서 사용하려면 저장소의 연결 지원과 파일 공유 방법을 확인해야 합니다.
- **File — 함께 접근하는 것과 안전하게 수정하는 것은 다릅니다.** 여러 Pod가 같은 데이터셋을 읽을 수 있어도, 같은 결과 파일을 동시에 수정하면 충돌할 수 있습니다. 작업별로 출력 파일을 나누거나 쓰기 순서를 조정해야 합니다.
- **Object — 객체 키는 일반 파일 경로와 사용 방식이 다릅니다.** 모델을 키로 보관하고 가져오는 데 적합하지만, 기존 프로그램이 파일 경로를 요구한다면 객체를 내려받거나 별도의 연결 방법을 마련해야 합니다.

접근 방식이 맞는 저장소를 골랐다면, 앞에서 살펴본 **지연 시간과 처리량**을 확인합니다. 작은 파일을 많이 읽는지, 큰 파일을 연속으로 읽는지에 따라 실제 작업 속도가 달라질 수 있으므로 학습 데이터의 요청 형태로 측정해야 합니다.

## 전체 과정과 연결

storage-lifecycle에서 정한 파일 수명과 공유 조건을 바탕으로 저장 방식을 선택합니다.

1. 애플리케이션이 디스크, 파일 경로, 객체 API 중 어떤 방식을 요구하는지 확인합니다.
2. 하나의 노드만 사용하는지, 여러 Pod와 노드가 함께 접근하는지 확인합니다.
3. 읽기만 필요한지, 여러 작업이 동시에 쓰기도 하는지 확인합니다.
4. 실제 요청 크기와 병렬성으로 지연 시간과 처리량을 측정합니다.
