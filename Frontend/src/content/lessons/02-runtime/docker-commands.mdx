## 그래서 컨테이너는 누가 만들어 주나요?

VM과 컨테이너의 차이는 알겠습니다. 그런데 코드와 라이브러리를 묶고, 다른 컴퓨터로 보내고, 실제로 실행하는 일까지 전부 직접 해야 할까요? 패키지 하나 설치하는 것도 가끔 하루짜리 이벤트인데요. **Docker는 애플리케이션을 이미지로 만들고, 배포하고, 컨테이너로 실행하는 작업을 돕는 플랫폼입니다.**

## Docker에서 만나는 네 가지

| 이름                 | 하는 일                                    | 리뷰 분류 서비스에서는                              |
| -------------------- | ------------------------------------------ | --------------------------------------------------- |
| Dockerfile           | 이미지를 만드는 방법을 적은 텍스트 파일    | 어떤 Python 환경을 쓰고 어떤 파일을 넣을지 작성     |
| 이미지(Image)        | 실행에 필요한 파일과 기본 설정을 담은 묶음 | 코드·라이브러리·시작 명령을 배포 가능한 형태로 준비 |
| 컨테이너(Container)  | 이미지에서 만들어 사용하는 개별 실행본     | 리뷰 요청에 응답하는 서버 프로세스 실행             |
| 레지스트리(Registry) | 이미지를 보관하고 배포하는 서비스          | 다른 서버가 같은 이미지를 내려받을 장소             |

레지스트리에는 Docker Hub나 AWS의 ECR 같은 서비스가 있습니다. **ECR은 이미지를 보관하고, EC2는 프로그램을 실행할 컴퓨터를 제공합니다.** S3도 파일을 보관하지만 컨테이너 이미지 배포에는 레지스트리라는 별도 역할이 있습니다.

## 명령을 치면 누가 일하나요?

터미널에서 사용하는 `docker`는 클라이언트입니다. 클라이언트의 요청을 받은 Docker 데몬이 이미지와 컨테이너를 관리하고, 빌드 작업은 빌더가 처리합니다. 실행할 때는 컨테이너 런타임을 통해 프로세스를 시작합니다. 우리는 명령을 적고, 뒤에서는 여러 구성 요소가 일을 나눠 합니다.

```text
개발자 → docker 명령 → Docker Engine과 빌더·런타임
                              ↕ 이미지 내려받기·올리기
                            레지스트리
```

## Dockerfile을 한 줄씩 읽어 봅시다

아래는 실행 순서를 이해하기 위한 예제입니다. `app.py`는 준비되어 있다고 가정하며, 복사해서 실행할 수 있는 전체 파일은 마지막 실습에서 제공합니다.

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY app.py .
EXPOSE 8000
CMD ["python", "-u", "app.py"]
```

| 명령      | 의미                                                                    |
| --------- | ----------------------------------------------------------------------- |
| `FROM`    | Python이 준비된 베이스 이미지를 사용합니다.                             |
| `WORKDIR` | 이후 작업의 기준 디렉터리를 `/app`으로 정합니다.                        |
| `COPY`    | 빌드할 때 앱 파일을 이미지에 복사합니다.                                |
| `EXPOSE`  | 앱이 사용할 포트를 이미지 정보로 남깁니다. 외부 포트를 열지는 않습니다. |
| `CMD`     | 컨테이너를 시작할 때 기본으로 실행할 명령을 정합니다.                   |

라이브러리를 설치할 때 사용하는 `RUN`은 **이미지를 만드는 중** 실행됩니다. `CMD`는 **컨테이너를 시작할 때** 사용할 기본 명령입니다. `RUN`에 서버 실행 명령을 적고 “왜 빌드가 안 끝나지?” 하고 기다리면, 서버는 성실하게 계속 일하고 있는 겁니다. 실행 시점을 나눠 적어야 합니다.

## 명령도 대상에 따라 나뉩니다

```bash
docker build -t reviews-demo:v1 .
docker run -d --name reviews-a -p 127.0.0.1:8080:8000 reviews-demo:v1
docker logs reviews-a
docker stop reviews-a
docker start reviews-a
```

| 조작    | 바뀌는 대상               | 확인할 결과                                                   |
| ------- | ------------------------- | ------------------------------------------------------------- |
| `build` | 이미지                    | 실행 환경의 묶음이 만들어집니다. 서버가 켜지는 것은 아닙니다. |
| `run`   | 새 컨테이너               | 이미지를 사용해 실행본을 만들고 시작합니다.                   |
| `logs`  | 해당 컨테이너의 출력 조회 | 프로그램이 남긴 로그를 읽습니다.                              |
| `stop`  | 실행 중인 컨테이너        | 프로세스를 중지합니다. 이미지와 컨테이너 객체는 남습니다.     |
| `start` | 기존의 중지된 컨테이너    | 새 실행본을 만들지 않고 기존 컨테이너를 다시 시작합니다.      |

포트 지정의 `8080:8000`은 **내 컴퓨터의 8080 → 컨테이너의 8000**이라는 뜻입니다. `127.0.0.1`은 이 예제의 접속을 로컬 컴퓨터로 제한합니다. `EXPOSE 8000`만 적었다고 이 연결이 생기지는 않습니다.

실제 명령 실행은 마지막 실습에서 진행합니다. 지금은 `build`와 `run`, `stop`과 `start`가 각각 무엇을 바꾸는지 구분하면 됩니다.

## Docker가 다 해결해 주지는 않습니다

이미지에 담지 않은 환경 변수, 비밀 값, 외부 데이터, 마운트와 GPU 드라이버는 별도로 맞춰야 합니다. 비밀번호까지 이미지에 구워 넣는 것은 포장이 잘 된 게 아니라 비밀번호 택배를 보내는 일입니다.

**Docker로 실행 환경을 명시하고, 외부 설정도 함께 관리해야 합니다.** 다음 레슨에서는 Linux가 커널을 공유하면서도 컨테이너를 구분하는 원리를 살펴봅니다.

<LessonSummary>

Docker는 **Dockerfile로 이미지 제작 방법을 정하고, 이미지를 배포하고, 컨테이너를 실행하는 작업**을 돕습니다. 이미지 생성과 프로그램 실행은 서로 다른 단계입니다.

- `build`는 이미지를 만들고, `run`은 새 컨테이너를 만들어 시작합니다.
- `stop`은 중지, `start`는 기존 컨테이너의 재시작입니다.
- 이미지 보관은 레지스트리가 담당하며, 외부 설정과 데이터는 따로 관리합니다.

</LessonSummary>
