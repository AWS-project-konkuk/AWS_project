## VM vs. container

리뷰 분류 프로그램에는 Python과 여러 라이브러리가 필요합니다. 다른 프로그램과 버전이 충돌하지 않게, 실행 환경을 따로 준비하고 싶습니다. 내 방을 정리하기 싫다고 옆집을 한 채 더 사는 건 비싸지만, 컴퓨터에서는 비슷한 선택이 가능합니다. **VM은 별도 운영체제를 실행하고, 컨테이너는 커널을 공유하며 프로세스의 환경을 격리합니다.**

### VM: 가상 컴퓨터를 만들기

**VM은 Virtual Machine, 즉 가상 머신입니다.** 하이퍼바이저가 물리 컴퓨터의 CPU·메모리 같은 자원을 가상 머신에 제공하고, 각 VM 안에서는 게스트 운영체제가 자신의 커널을 실행합니다. 커널은 프로세스 실행, 메모리, 장치 접근 등을 관리하는 운영체제의 핵심 부분입니다.

예를 들어 한 물리 서버에서 Linux VM과 Windows VM을 각각 실행할 수 있습니다. 프로그램을 위한 별도 운영체제까지 갖추는 방식입니다. VM마다 운영체제를 부팅하고 관리해야 하는 비용도 있습니다.

0단원에서 배운 EC2 인스턴스도 가상 서버의 예입니다. 클라우드에서 컴퓨터를 빌린다는 말과 여기서 배운 구조가 연결됩니다.

### 컨테이너: 프로세스의 실행 환경을 나누기

**컨테이너는 애플리케이션과 필요한 사용자 공간 파일을 준비하고, 프로세스의 실행 환경을 격리하는 방식입니다.** 일반적인 Linux 컨테이너는 각자 커널을 부팅하지 않고, 자신이 실행되는 Linux 호스트의 커널을 사용합니다.

컨테이너 A는 Python 3.12, B는 다른 Python 버전을 사용할 수 있습니다. Python과 라이브러리는 각 실행 환경에 둘 수 있지만, 시스템 호출을 처리하는 커널은 공유합니다. **같은 커널을 쓴다는 말이 같은 Python 패키지를 강제로 쓴다는 뜻은 아닙니다.**

| 비교 기준        | VM                                 | 일반적인 Linux 컨테이너                          |
| ---------------- | ---------------------------------- | ------------------------------------------------ |
| 나누는 경계      | 가상 하드웨어와 게스트 운영체제    | 프로세스가 보는 환경과 자원 사용                 |
| 커널             | VM마다 게스트 커널 실행            | 실행 호스트의 커널 공유                          |
| 앱과 라이브러리  | 게스트 OS 안에 설치                | 이미지에 담아 컨테이너에서 사용                  |
| 시작할 때        | 게스트 운영체제 부팅 필요          | 준비된 커널에서 프로세스 실행                    |
| 비용을 비교할 때 | 운영체제별 메모리와 관리 부담 고려 | 커널 부팅 부담은 줄지만 앱·모델 로딩 비용은 남음 |
| 선택 이유의 예   | 서로 다른 OS·커널이 필요한 환경    | 같은 앱 환경을 여러 곳에 배포하는 환경           |

컨테이너가 무조건 몇 초, VM이 무조건 몇 분이라고 외울 필요는 없습니다. 큰 모델을 읽는 컨테이너는 시작 준비가 오래 걸릴 수 있습니다. 차이는 **각자 운영체제를 부팅하는가, 이미 있는 커널을 이용하는가**입니다.

## 둘 중 하나만 골라야 하나요?

아닙니다. **EC2 같은 VM 안에서 컨테이너를 실행할 수 있습니다.** VM으로 서버를 나누고, 그 안에서 컨테이너로 여러 프로그램을 실행하는 구조는 자연스럽습니다. VM과 컨테이너가 서로 왕위를 다투는 관계는 아닙니다.

Windows나 macOS에서 Linux 컨테이너를 실행할 때는 Docker Desktop이 사용하는 Linux 환경도 고려해야 합니다. Linux 컨테이너가 Windows 커널을 그대로 가져다 쓰는 것은 아닙니다.

## 하나가 늘면 무엇이 늘어날까요?

아래에서는 **앱마다 실행 환경을 하나씩 분리**합니다. VM 한 개 또는 컨테이너 한 개에 앱 하나를 넣는 예제입니다. 한 VM에서 앱 여러 개를 실행할 수도 있지만, 지금은 독립된 환경을 추가할 때의 차이를 비교합니다.

1. 처음에는 양쪽에 앱이 하나씩 있습니다. **파란 커널 영역**을 찾으세요.
2. **앱 하나 추가**를 두 번 눌러 앱을 3개로 늘립니다.
3. VM 쪽은 **각 VM 안의 커널이 3개**, 컨테이너 쪽은 **모든 앱 아래의 공유 커널이 1개**인지 직접 세어 보세요.

재생 버튼을 누를 필요는 없습니다. 앱을 추가하거나 제거하면 구조도와 개수가 즉시 바뀝니다.

<Activity open />

**차이는 앱의 개수가 아니라 커널의 위치입니다.** VM은 별도 게스트 운영체제 안에서 앱을 실행하고, 컨테이너는 앱 환경을 나누면서 같은 호스트 커널을 사용합니다.

<Callout title="공유와 보안은 함께 봅니다">

커널을 공유하면 실행 환경을 가볍게 구성할 수 있지만, 공유 커널의 취약점이나 잘못된 권한 설정도 고려해야 합니다. VM도 컨테이너도 설정과 운영을 빼고 무조건 안전하다고 말할 수는 없습니다.

</Callout>

<LessonSummary>

**VM은 게스트 운영체제와 커널을 갖고, 일반적인 Linux 컨테이너는 실행 호스트의 커널을 공유합니다.** 컨테이너마다 앱과 라이브러리를 준비할 수 있으므로, 커널 공유와 패키지 환경 분리는 함께 가능합니다.

- VM 안에서도 컨테이너를 실행할 수 있습니다.
- 실행 속도는 OS 부팅뿐 아니라 이미지 준비와 모델 로딩에도 영향을 받습니다.
- 다음에는 컨테이너 환경을 만들고 실행하는 도구인 Docker를 배웁니다.

</LessonSummary>
