## 커널을 같이 쓰면 옆집 프로세스도 보이나요?

Linux 컨테이너는 같은 커널을 사용한다고 했습니다. 그렇다면 컨테이너 A에서 실행한 프로그램을 B에서도 마음대로 보고, 파일도 꺼내 쓸 수 있을까요? 같은 건물에 산다고 옆집 냉장고를 열 수 있는 것은 아니잖아요. **공유하는 자원과 각 프로세스에 허용된 범위는 다릅니다.**

## Namespaces & Cgroups

리뷰 분류 프로그램이 파일을 읽고 메모리를 할당하고 네트워크 요청을 보낼 때, 운영체제의 커널이 그 작업을 처리합니다. 컨테이너 내부 프로그램도 이 경로를 사용합니다. 컨테이너라고 물리 CPU에 바로 명령을 던지는 특별 대우를 받지는 않습니다.

```text
컨테이너 안의 앱 → 시스템 호출 → 공유 Linux 커널 → CPU·메모리·장치
```

그러면 공유 커널은 프로그램마다 무엇을 볼 수 있고 얼마를 사용할 수 있는지 구분해야 합니다. 여기서 **Namespaces**와 **Cgroups**가 등장합니다.

## Namespaces: 무엇이 보이는가

**Namespaces는 프로세스가 보는 시스템 자원의 범위를 나누는 Linux 기능입니다.** 별도의 컴퓨터를 부팅하지 않아도, 프로세스 ID나 네트워크 등의 범위를 다르게 제공할 수 있습니다.

| 종류              | 나누는 범위                     | 알아둘 예                                                      |
| ----------------- | ------------------------------- | -------------------------------------------------------------- |
| PID namespace     | 보이는 프로세스 ID 범위         | 컨테이너 안에서는 자기 프로그램이 PID 1로 보일 수 있음         |
| Network namespace | 네트워크 장치·IP·포트 등의 범위 | 서로 다른 네트워크 namespace의 앱이 각각 8000번 포트 사용 가능 |
| Mount namespace   | 보이는 마운트 구성              | 컨테이너마다 다른 파일 시스템 뷰 제공                          |

서로 다른 네트워크 범위의 두 앱이 각각 8000번을 쓰는 것과, **호스트의 같은 IP·8000번 포트에 둘 다 연결하려는 것**은 다른 상황입니다. 후자는 충돌할 수 있습니다. 방 번호가 같아도 건물이 다르면 괜찮지만, 같은 건물의 같은 호수를 두 집이 동시에 쓸 수는 없습니다.

namespace가 다르다고 모든 접근이 자동으로 금지되는 것은 아닙니다. 네트워크로 통신하게 하거나 같은 볼륨을 마운트하면 의도적으로 공유할 수 있습니다.

## Cgroups: 얼마를 사용할 수 있는가

**Cgroups는 프로세스 집합의 CPU·메모리 같은 자원 사용량을 계측하고 제한하는 기능입니다.** Namespaces가 “무엇이 보이지?”라면, Cgroups는 “얼마나 써도 되지?”에 가깝습니다.

같은 서버에서 리뷰 API와 학습 작업이 함께 실행된다고 합시다. 학습 작업이 메모리를 끝없이 차지하지 않게 제한을 둘 수 있습니다. 제한을 초과하면 설정과 상황에 따라 메모리 할당 실패나 OOM으로 프로세스가 종료될 수 있습니다. CPU 제한과 메모리 제한의 결과가 항상 같은 것은 아닙니다.

| 나타난 현상                               | 먼저 연결할 개념                 |
| ----------------------------------------- | -------------------------------- |
| 컨테이너 A에서 B의 프로세스가 보이지 않음 | PID namespace                    |
| 두 앱이 각자의 환경에서 같은 포트를 사용  | Network namespace                |
| 메모리 제한에 걸려 프로세스가 종료        | Cgroups의 메모리 제어와 OOM 조사 |

## 공유하는데도 안전한가요?

격리는 한 기능으로 완성되지 않습니다. Linux 권한, capabilities, seccomp 같은 접근 제어와 컨테이너 설정도 함께 작용합니다. 권한을 과하게 주거나 호스트 경로를 마운트하면 기대한 격리를 약하게 만들 수 있습니다.

또한 **같은 Pod 안의 컨테이너는 네트워크 namespace를 공유합니다.** 뒤에서 Pod를 배울 때 “컨테이너마다 무조건 IP가 다르다”라고 외우면 충돌합니다. 어떤 범위를 공유하도록 구성했는지 봐야 합니다.

다음 레슨에서는 이 원리 위에서 같은 이미지로 실행한 두 컨테이너가 왜 서로 다른 상태를 갖는지 확인합니다.

<LessonSummary>

일반적인 Linux 컨테이너는 **공유 커널 위에서 실행되는 프로세스**입니다. Namespaces는 보이는 자원의 범위를, Cgroups는 자원 사용량의 계측과 제한을 담당합니다.

- 커널 공유가 프로세스·파일·설정의 무제한 공유를 뜻하지는 않습니다.
- 공유 namespace나 볼륨처럼 의도적으로 함께 사용하는 범위도 있습니다.
- 격리 문제를 조사할 때는 범위 설정과 자원 제한, 접근 권한을 나누어 확인합니다.

</LessonSummary>
