## Pod는 켜졌는데, 요청은 왜 길을 잃을까요?

리뷰 서버 Pod를 노드에 배치했습니다. 상태도 Running입니다. 그런데 Service로 접속하면 응답이 없습니다. “켜졌는데 왜 안 되지?”라는 상황입니다. 컴퓨터가 켜진 것과 프로그램이 실행되는 것이 달랐듯이, **Pod가 실행되는 것과 사용자 요청이 그 Pod에 도착하는 것도 다릅니다.**

## 첫 번째 경로: 선언에서 실제 실행까지

사용자가 Deployment YAML을 `kubectl apply`로 제출하면, Kubernetes는 선언을 받아 실행 상태를 조정합니다. 아래는 역할을 설명하기 위한 순서이며, 한 요청을 각 구성 요소가 단순히 직렬 전달하는 구조는 아닙니다. 여러 구성 요소가 API 객체를 관찰하며 각자 반복해서 일합니다.

| 구성 요소       | 하는 일                                 | 맡지 않는 일                          |
| --------------- | --------------------------------------- | ------------------------------------- |
| API Server      | 객체의 생성·변경 요청을 받고 검증·제공  | 리뷰 분류 요청을 대신 계산            |
| etcd            | API 객체의 상태를 저장                  | Pod를 직접 실행하거나 HTTP 요청 분배  |
| 컨트롤러        | 원하는 상태와 실제 상태의 차이 조정     | 사용자 요청마다 목적지를 선택         |
| Scheduler       | 아직 배치되지 않은 Pod의 실행 노드 결정 | 컨테이너 프로세스 직접 실행           |
| kubelet         | 해당 노드의 Pod 실행과 상태 관리        | 클러스터 전체의 배치 결정             |
| 컨테이너 런타임 | 컨테이너 생성과 프로세스 실행           | 서비스가 제공할 모델 버전 스스로 판단 |

Deployment는 ReplicaSet을 관리하고, ReplicaSet은 필요한 Pod를 생성·관리합니다. Scheduler가 노드를 정하면 그 노드의 kubelet이 런타임과 함께 컨테이너 실행을 진행합니다. etcd는 기억 담당이지 실행 담당이 아닙니다. 회의록이 일을 대신하지 않는 것과 비슷합니다.

## 두 번째 경로: 사용자 요청에서 응답까지

리뷰 예측 요청은 접근 경로가 준비된 **Service → 대상 Pod의 앱 → 응답** 흐름을 따릅니다. 배포할 때 API Server를 썼다고 해서, 사용자 리뷰를 etcd에 보내 읽어 오는 것은 아닙니다.

Service의 안정적인 주소 뒤에 어떤 Pod가 연결되는지는 Pod 라벨, selector, EndpointSlice와 준비 상태 등의 정보로 관리합니다. 실제 패킷 전달은 클러스터의 네트워크 구현이 담당하며 kube-proxy나 다른 구현을 사용할 수 있습니다.

| 확인할 설정            | 보는 대상                         | 예                                       |
| ---------------------- | --------------------------------- | ---------------------------------------- |
| Pod의 `nodeSelector`   | 노드의 라벨                       | `workload: inference`인 노드에 배치      |
| Service의 `selector`   | Pod의 라벨                        | `app: reviews-api`인 Pod를 대상으로 선택 |
| Service의 `port`       | 클라이언트가 접속하는 서비스 포트 | 80                                       |
| Service의 `targetPort` | 대상 Pod 앱이 실제 듣는 포트      | 8000                                     |
| readiness              | 앱이 요청을 받을 준비가 되었는지  | 모델 로딩이나 상태 확인이 통과했는지     |

노드에 `workload: inference`가 있다고 Pod에 `app: reviews-api`가 자동으로 붙지는 않습니다. **배치 조건과 요청 대상 조건을 따로 적어야 합니다.**

## 노드에서 두 화살표를 구분해 보세요

아래 Deployment → Pod 화살표는 **원하는 실행 상태를 관리하는 관계**를 단순화한 것입니다. Service → Pod 화살표는 **사용자 요청의 전달**입니다. 둘 다 Pod로 향하지만 의미가 다릅니다.

<NodeExample />

직접 연결한 뒤 “Deployment는 Pod를 관리한다. Service는 대상 Pod로 요청을 전달한다”라고 설명해 보세요. Deployment → Service → Pod라는 한 줄로 모두 합치면 관리 정보와 사용자 요청이 섞입니다.

## 고장 난 위치부터 나눠 봅시다

| 증상                     | 먼저 확인할 것                            | 왜 확인할까?                            |
| ------------------------ | ----------------------------------------- | --------------------------------------- |
| Pod가 Pending에서 멈춤   | 이벤트, 자원 요청, 배치 조건              | 실행할 노드를 정하지 못했을 수 있음     |
| 이미지를 받지 못함       | 이미지 이름·버전·레지스트리 접근          | 앱 실행 준비 자체가 안 됨               |
| Running인데 Ready가 아님 | 앱 로그, readiness, 모델 로딩             | 프로세스 존재와 응답 준비는 다름        |
| Service 대상이 비어 있음 | Pod 라벨, selector, EndpointSlice         | 요청을 전달할 대상이 맞지 않음          |
| 대상은 있는데 접속 실패  | 앱 리슨 주소, `targetPort`, 네트워크 정책 | 대상 선택 뒤의 전달·수신 조건 문제 가능 |

Running 하나만 보고 “서버는 멀쩡한데 인터넷이 이상하네”라고 결론 내리면 네트워크가 억울합니다. **배치 → 실행 → 준비 → 대상 선택 → 포트** 순서로 확인 범위를 좁혀 보세요.

<Reveal title="심화: GPU 노드에 배치하려면">

`nodeSelector`와 node affinity는 실행 위치 조건을 표현하고, taints와 tolerations는 배치 허용 조건에 관여합니다. toleration이 있다고 그 노드로 반드시 배치되는 것은 아닙니다. GPU를 실제로 할당하려면 장치 플러그인과 GPU 자원 요청 같은 조건도 맞아야 합니다. 자세한 GPU 자원 선택은 뒤의 GPU 단원에서 다룹니다.

</Reveal>

<LessonSummary>

**제어 경로는 무엇을 어디에 실행할지 관리하고, 요청 경로는 실행된 앱으로 사용자 요청을 전달합니다.** API 객체 관리와 앱의 요청 처리를 구분해야 고장 난 위치를 찾을 수 있습니다.

- `nodeSelector`는 노드 라벨, Service `selector`는 Pod 라벨을 확인합니다.
- Running과 Ready, 대상 선택과 실제 포트 수신은 각각 구분합니다.
- 마지막 실습에서는 이미지·관리 선언·사용자 요청을 별도 연결로 구성해 봅니다.

</LessonSummary>
