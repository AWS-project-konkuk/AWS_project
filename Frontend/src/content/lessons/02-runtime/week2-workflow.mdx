## 모델 파일은 있는데, 서비스는 아직 없습니다

리뷰를 긍정·부정으로 분류하는 모델을 학습하고 평가까지 마쳤습니다. 이제 팀원이 말합니다.

> 그럼 이 모델로 사용자가 리뷰를 분류하게 해 주세요.

모델 파일을 메신저로 보내 주면 끝일까요? 파일은 도착했지만 사용자는 어디에 리뷰를 입력해야 할지도 모릅니다. **학습 결과를 만드는 일과, 그 결과를 계속 사용할 수 있게 제공하는 일은 다릅니다.** 이번 실습에서는 그 사이를 연결합니다.

## 이번 실습에서 만들 것

목표는 **학습된 모델을 읽는 서빙 프로그램을 컨테이너로 실행하고, Kubernetes의 Pod로 관리하며, 사용자 요청에 예측을 돌려주는 흐름**입니다. 여기서 모델 학습을 다시 하지는 않습니다.

| 구성 요소            | 이 실습에서 맡는 역할                                   | MLOps에서 필요한 이유                                                    |
| -------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------ |
| 검증된 모델 파일     | 학습·평가가 끝난 `model-v1` 제공                        | 어떤 모델로 예측했는지 추적하고 같은 모델을 사용하기 위해                |
| 서빙 컨테이너 이미지 | 추론 코드·Python·라이브러리를 실행 가능한 환경으로 준비 | 노트북과 배포 서버의 패키지 차이로 모델 실행이 실패하는 일을 줄이기 위해 |
| 컨테이너             | 이미지로 준비한 환경에서 서빙 앱 실행                   | 모델 파일을 읽어 실제 예측을 계산할 프로세스가 필요하기 때문에           |
| Pod                  | 서빙 컨테이너가 실행되는 Kubernetes의 단위              | 실행할 앱을 클러스터에서 배치하고 관리할 대상으로 만들기 위해            |
| Deployment           | 사용할 이미지와 두 실행본을 유지할 목표 선언            | 같은 실행 구성을 다시 만들고 필요한 실행본을 유지하기 위해               |
| Service              | 준비된 Pod의 앱으로 접근할 접점 제공                    | Pod 이름이나 주소가 바뀌어도 호출 경로를 관리하기 위해                   |

**모델이 예측하고 Kubernetes가 정답을 만드는 구조가 아닙니다.** 정확히는 모델을 읽은 앱이 컨테이너 안에서 계산하고, Kubernetes는 그 앱을 배치·유지하는 쪽을 돕습니다. Kubernetes를 설치했다고 모델의 정확도가 올라가면 좋겠지만, 그런 서비스는 아직 없습니다.

작은 실험이나 단일 서버에서는 Docker만으로도 충분할 수 있습니다. 이번에는 여러 서빙 실행본을 운영해야 하는 상황을 가정합니다. 모든 MLOps 시스템에 Kubernetes가 필수라는 뜻은 아닙니다.

## 세 가지 흐름을 나누어 연결합니다

아래는 순서도가 아니라 **같은 Pod로 모이는 서로 다른 입력과 관계**입니다. Pod 안에는 서빙 앱을 실행하는 컨테이너 하나가 있다고 가정합니다.

```text
서빙 이미지 ── 실행 환경 ───────────┐
검증된 모델 ── 앱이 로딩할 파일 ───┤
Deployment ── 원하는 실행 상태 ────┤→ Pod 안의 서빙 컨테이너
사용자 리뷰 → Service ── 요청 ─────┘       ↓ 모델로 추론
                                       예측 응답 → 사용자
```

여기서는 모델을 이미지에 넣지 않고 **별도의 모델 파일을 앱이 읽는 방식**으로 단순화합니다. 실제 서비스에서는 이미지에 모델을 포함하거나 S3·모델 저장소 등에서 가져올 수 있습니다. 모델 입력 화살표는 파일을 읽는 관계이지, 학습을 다시 실행하는 명령이 아닙니다.

컨테이너를 Pod에 넣는다는 것은 별도의 컴퓨터를 한 겹 더 부팅한다는 뜻이 아닙니다. Kubernetes가 컨테이너들을 Pod라는 단위로 배치·관리한다는 뜻입니다. Pod를 두 개 만들면 각 컨테이너가 자기 프로세스와 메모리에서 모델을 읽습니다.

## 1. 완성된 서비스의 흐름 추적하기

**실습 시작하기 → 1. 예시 흐름 추적**을 누릅니다. 처음에는 같은 서빙 이미지 v1을 사용하고 복구 설정도 켠 상태로 시작합니다. 버전부터 고치는 문제가 아니라, 각 입력이 어디에 쓰이는지 먼저 봅니다.

1. **서빙 이미지**를 선택합니다. 추론 코드와 라이브러리가 들어 있습니다. 이것만으로 아직 요청을 계산하는 프로세스가 생긴 것은 아닙니다.
2. **검증된 모델**에서 두 Pod로 가는 연결을 확인합니다. 같은 앱 환경이어도 모델 파일이 없으면 실제 추론을 준비할 수 없습니다.
3. **Pod 1·2 안의 서빙 컨테이너**를 봅니다. 앱이 같은 모델을 로딩하고, 각자 사용자 리뷰를 처리하는 실행본입니다.
4. **Deployment → Pod**는 실행을 관리하는 관계입니다. 리뷰 문장이 이 화살표를 타고 전달되는 것은 아닙니다.
5. **요청 → Service → Pod → 사용자 응답**을 따라갑니다. 단계별 결과에서 누가 모델을 읽고 누가 요청을 처리했는지 확인합니다.

이 모형은 리뷰 10건을 두 경로에 5건씩 나눠 전달합니다. 실제 Service가 항상 정확히 반반씩 분배한다는 뜻은 아닙니다. 화면의 예측은 교육용 고정 결과이며 실제 모델 추론이나 품질 측정은 수행하지 않습니다.

## 2. 모델이 빠지면 어디서 막히는지 확인하기

모델에서 **Pod 2의 모델 입력**으로 가는 연결을 하나 제거하고 실행해 보세요. 지우기 전에 결과를 예상합니다.

| 예상할 질문                                            | 실행 뒤 확인할 근거                                           |
| ------------------------------------------------------ | ------------------------------------------------------------- |
| 컨테이너 이미지가 있으니 모델 없이도 예측할 수 있을까? | Pod 2에서 모델 입력 누락을 알리고 예측 결과를 만들지 못하는지 |
| Pod 1이 성공하면 전체 서비스도 준비된 것일까?          | 두 실행 경로가 필요한 이 과제에서 최종 응답이 막히는지        |
| 해결하려면 모델을 다시 학습해야 할까?                  | 이미 검증한 모델 파일의 연결을 되살리면 준비가 완료되는지     |

연결을 복구한 뒤 다시 실행합니다. **실행 환경 준비, 모델 준비, 요청 연결은 각각 확인해야 한다**는 것이 이번 실습의 핵심입니다. 실제 서비스가 건강한 Pod만으로 일부 요청을 계속 처리할 수 있는 것과 달리, 이 과제는 두 경로가 모두 연결되어야 전체 성공으로 판단합니다.

## 3. 내 손으로 서비스 구성하기

**3. 새로운 상황 구성**을 누르면 연결 없이 시작합니다. 이미지와 배포 태그는 v1, 실행본 복구는 사용 상태로 두고 아래 관계를 완성하세요.

| 출발        | 도착                     | 전달하는 의미                |
| ----------- | ------------------------ | ---------------------------- |
| 서빙 이미지 | Pod 1·2의 이미지 입력    | 같은 앱 실행 환경            |
| 검증된 모델 | Pod 1·2의 모델 입력      | 각 앱이 로딩할 모델 파일     |
| Deployment  | Pod 1·2의 관리 선언 입력 | 어떤 구성과 수를 유지할지    |
| 사용자 요청 | Service                  | 새 리뷰의 예측 요청          |
| Service     | Pod 1·2의 요청 입력      | 대상 앱으로 리뷰 전달        |
| Pod 1·2     | 사용자 응답              | 모델을 이용해 만든 예측 결과 |

실행을 마지막 단계까지 확인하고, 이해 확인 문제에서 **실제로 추론하는 곳과 Kubernetes의 역할**을 구분해 답합니다. 기본 완료 조건은 올바른 연결, 현재 구성의 성공 실행, 역할 설명입니다. 일부러 버전을 틀리거나 장애를 만들어야 완료되는 조건은 없습니다.

## 확장: 그래서 버전과 복구도 중요합니다

기본 구조를 이해한 다음 **2. 잘못된 구성 수정**에서 버전 불일치와 장애를 확인할 수 있습니다. 이는 이번 실습의 출발점이 아니라, 만든 서비스를 계속 운영할 때 생기는 문제입니다.

| 추가로 바꿔 볼 것                            | 앞의 개념과 연결할 이유                                        |
| -------------------------------------------- | -------------------------------------------------------------- |
| 제공한 이미지 v2와 Deployment 지정 v1이 다름 | 사용할 실행 환경을 명시하고 실제로 그 환경을 제공해야 함       |
| 장애 뒤 복구를 사용하지 않는 모형과 비교     | 이미지가 있어도 실행본이 없으면 사용자 요청을 처리할 수 없음   |
| 두 Pod가 같은 이미지와 모델을 사용           | 실행본이 달라도 의도한 코드·라이브러리·모델 조합을 유지해야 함 |

모형은 선택한 이미지 하나만 제공하므로 Deployment 지정과 다르면 실패합니다. 실제 Kubernetes에서 v1·v2가 모두 존재하면 서로 다른 버전도 실행될 수 있습니다. 또 실제 Deployment에 이 모형과 같은 복구 끄기 스위치가 있는 것은 아닙니다.

## 로컬에서 직접 실행하기

여기부터는 **선택 추가 실습**입니다. 아래 파일과 명령을 자신의 로컬 환경에서 사용합니다. 브라우저 실습만으로 이 명령이 실행되지는 않습니다.

준비물은 **Docker와 Minikube, kubectl**입니다. Docker가 실행 중이어야 하고, 이후 명령은 직접 만든 실습 폴더와 로컬 Minikube 클러스터에서 사용합니다. 설치 방법은 참고 자료의 공식 안내를 확인하세요.

이 예제 앱은 **버전과 실행본 이름을 응답하는 데모 API**입니다. 실제 모델을 학습하거나 리뷰의 긍정·부정을 예측하지 않습니다. 모델 계산 대신 실행 환경과 요청 전달을 확인하는 데 집중합니다.

### 1. 앱과 이미지 준비

빈 실습 폴더에 다음 두 파일을 만듭니다. `app.py`는 요청을 받으면 버전과 자기 실행본 이름을 반환합니다.

```python
# app.py
import json
import os
import socket
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = json.dumps({
            "version": os.environ.get("APP_VERSION", "v1"),
            "instance": socket.gethostname(),
        }).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
```

```dockerfile
# Dockerfile
FROM python:3.12-slim
WORKDIR /app
ARG APP_VERSION=v1
ENV APP_VERSION=${APP_VERSION}
COPY app.py .
EXPOSE 8000
CMD ["python", "-u", "app.py"]
```

`0.0.0.0`은 컨테이너의 네트워크 인터페이스에서 요청을 받을 수 있게 합니다. 이 앱을 컨테이너 안의 `127.0.0.1`에만 바인딩하면 외부 연결이 실패할 수 있습니다.

```bash
docker build --build-arg APP_VERSION=v1 -t reviews-demo:v1 .
docker build --build-arg APP_VERSION=v2 -t reviews-demo:v2 .
docker run -d --name reviews-a -p 127.0.0.1:8080:8000 reviews-demo:v1
docker run -d --name reviews-b -p 127.0.0.1:8081:8000 reviews-demo:v1
```

브라우저에서 `http://127.0.0.1:8080`과 `http://127.0.0.1:8081`을 엽니다. **두 응답의 버전은 v1이고 실행본 이름은 다르다**는 것을 확인하세요. v2 이미지도 빌드했지만, 여기서 실행한 것은 v1입니다.

```bash
docker stop reviews-a
docker ps -a
docker start reviews-a
docker logs reviews-a
```

A를 중지하면 8080 접속이 실패하지만 B의 8081은 계속 응답해야 합니다. A를 다시 시작하면 재접속할 수 있습니다. `ps -a`에서 중지된 컨테이너가 남아 있는지도 확인합니다. 이미지와 컨테이너 레슨의 파일 쓰기 실험을 여기서 추가해도 됩니다.

### 2. 같은 이미지를 Kubernetes에서 실행

```bash
minikube start --driver=docker
kubectl config current-context
minikube image load reviews-demo:v1
minikube image load reviews-demo:v2
```

현재 context가 `minikube`인지 확인한 뒤 진행합니다. Docker에 이미지를 만들었다고 모든 클러스터가 그 이미지를 갖는 것은 아닙니다. 여기서는 `minikube image load`로 클러스터에 가져옵니다. 운영 환경에서는 ECR 같은 레지스트리를 통한 배포를 고려합니다.

아래 전체 내용을 `reviews.yaml`로 저장합니다. 이 실습의 리소스는 `reviews-lab` namespace 안에 만듭니다.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: reviews-lab
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reviews-api
  namespace: reviews-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: reviews-api
  template:
    metadata:
      labels:
        app: reviews-api
    spec:
      containers:
        - name: api
          image: reviews-demo:v1
          imagePullPolicy: Never
          ports:
            - containerPort: 8000
          readinessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 1
            periodSeconds: 2
---
apiVersion: v1
kind: Service
metadata:
  name: reviews-api
  namespace: reviews-lab
spec:
  selector:
    app: reviews-api
  ports:
    - port: 80
      targetPort: 8000
```

`imagePullPolicy: Never`는 이 로컬 실습에서 미리 가져온 이미지를 사용하기 위한 설정입니다. 이미지가 노드에 없으면 실행되지 않습니다. 앱은 `/health` 요청에도 200으로 응답합니다. 실제 모델 서버라면 모델 로딩까지 끝났을 때 준비됐다고 응답하도록 구성해야 합니다.

```bash
kubectl apply -f reviews.yaml
kubectl rollout status deployment/reviews-api -n reviews-lab
kubectl get pods -n reviews-lab -l app=reviews-api -o wide
kubectl get endpointslices -n reviews-lab -l kubernetes.io/service-name=reviews-api
kubectl port-forward -n reviews-lab service/reviews-api 8082:80
```

브라우저에서 `http://127.0.0.1:8082`를 엽니다. v1 응답과 Pod 이름이 보이면 앱까지 연결된 것입니다. Pod 목록에서 `READY`가 `1/1`인 두 Pod와 Service의 대상 주소도 함께 확인하세요.

<Callout title="port-forward가 증명하는 범위">

`kubectl port-forward service/...`는 해당 Service가 선택하는 Pod 중 하나로 디버깅 연결을 만듭니다. 이것만으로 실제 Service 데이터 경로의 부하 분산을 검증했다고 할 수는 없습니다. Service 대상 확인은 위의 EndpointSlice 조회와 함께 하고, Pod가 교체되면 연결을 다시 시작해야 할 수 있습니다.

</Callout>

### 3. Pod 교체와 버전 변경을 따로 확인

먼저 실행 중인 `port-forward`를 Ctrl+C로 종료합니다. Pod 목록에서 한 개의 실제 이름을 확인한 뒤, 아래 명령의 `실제_Pod_이름` 부분을 그 이름으로 바꿉니다.

```bash
kubectl get pods -n reviews-lab -l app=reviews-api
kubectl delete pod 실제_Pod_이름 -n reviews-lab
kubectl get pods -n reviews-lab -l app=reviews-api -w
```

새 이름의 Pod가 만들어져 Ready가 되고 원하는 수 2개로 돌아오는지 확인합니다. 관찰을 끝낼 때 Ctrl+C를 누릅니다. **Pod 하나를 지운 것이 Deployment의 “2개 유지” 선언을 지운 것은 아닙니다.** 새 Pod의 나이와 이름도 비교하세요.

다음에는 실행할 이미지 버전을 변경합니다.

```bash
kubectl set image deployment/reviews-api api=reviews-demo:v2 -n reviews-lab
kubectl rollout status deployment/reviews-api -n reviews-lab
kubectl get pods -n reviews-lab -l app=reviews-api -o wide
kubectl port-forward -n reviews-lab service/reviews-api 8082:80
```

다시 브라우저에 접속해 **응답의 version이 v2인지** 확인합니다. 새 이미지를 만드는 작업과 Deployment가 사용할 이미지를 바꾸는 작업을 따로 수행했다는 점이 핵심입니다.

| 관찰할 것                   | 성공했다고 판단할 근거                              |
| --------------------------- | --------------------------------------------------- |
| 같은 이미지의 독립된 실행본 | Docker의 두 응답에서 버전은 같고 실행본 이름은 다름 |
| 한 실행본 중지              | A만 접속이 끊기고 B는 계속 응답                     |
| Pod 삭제 후 대체            | 새 이름의 Pod가 생기고 Ready인 두 실행본으로 돌아옴 |
| 이미지 버전 변경            | 배포 완료 후 응답의 version이 v2로 바뀜             |

### 4. 실습 리소스 정리

`port-forward`를 Ctrl+C로 끝낸 뒤, 이번 실습에서 만든 컨테이너와 namespace만 정리합니다. 같은 이름의 리소스를 다른 작업에 재사용하고 있다면 그 작업을 먼저 확인하세요.

```bash
docker stop reviews-a reviews-b
docker rm reviews-a reviews-b
kubectl delete namespace reviews-lab
```

Minikube 자체를 더 사용하지 않을 때는 `minikube stop`으로 중지할 수 있습니다. 전체 클러스터나 다른 프로젝트의 이미지를 무작정 삭제할 필요는 없습니다.

<Reveal title="더 해보기: 원문 워크북의 OOM과 HPA">

MLOps 원문의 확장 실험은 메모리 제한으로 인한 OOM과 HPA의 부하 기반 확장을 다룹니다. OOM에서는 Pod 이름이 유지되고 컨테이너 재시작 횟수만 늘 수도 있으므로 `RESTARTS`, 종료 이유, 이전 로그를 구분해 확인합니다. Pod 삭제 후 새 이름의 Pod를 만드는 실험과 같은 사건으로 기록하지 마세요.

HPA를 확인하려면 자원 지표 수집과 CPU requests 등 기준 설정이 필요합니다. “Pod 두 개 유지”만으로 부하 기반 자동 확장이 켜지지는 않습니다. 기본 실습의 교체·버전·요청 경로를 먼저 이해한 뒤 원문의 추가 미션으로 진행하세요.

</Reveal>

<LessonSummary>

**MLOps에서 모델 파일을 서비스로 쓰려면 실행 환경, 모델을 읽는 앱, 요청을 전달할 경로가 함께 필요합니다.** 이미지는 앱의 환경을 준비하고, 컨테이너는 앱을 실행하며, Pod는 Kubernetes가 관리하는 실행 단위입니다.

- 실제 추론은 모델을 로딩한 앱이 수행합니다. Deployment와 Service가 예측을 계산하는 것은 아닙니다.
- Kubernetes는 실행본을 배치·유지하고 접근 구성을 관리하는 데 연결됩니다. 모델 품질 검증이나 학습을 대신하지 않습니다.
- 이미지 버전과 복구는 이 서비스 구조를 유지하기 위한 확장 주제입니다. 다음 단원에서는 실행본과 별도로 데이터를 보존하고 공급하는 저장소를 배웁니다.

</LessonSummary>
