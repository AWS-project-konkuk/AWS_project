## 컨테이너가 **100개**면 누가 켜 주나요?

Docker로 리뷰 서버 하나를 실행했습니다. 사용자가 늘어나 서버를 여러 개 띄웠는데, 그중 하나가 꺼졌습니다. 새 버전도 배포해야 하고 어느 서버가 비었는지도 확인해야 합니다. 이제 `docker run`을 빨리 치는 능력만으로는 버티기 어렵습니다. 손가락도 유한한 자원입니다.

**Kubernetes는 여러 컴퓨터에 컨테이너화한 애플리케이션을 배치하고, 선언한 실행 상태에 맞추도록 관리하는 플랫폼입니다.** 이런 일을 컨테이너 오케스트레이션이라고 합니다. 줄여서 K8s라고도 씁니다.

## “두 개 실행해 줘”라는 목표를 남기기

명령 한 번으로 컨테이너 두 개를 실행하는 것과, **항상 두 개가 필요하다는 목표를 관리하는 것**은 다릅니다. Kubernetes의 컨트롤러는 원하는 상태와 실제 상태의 차이를 반복해서 확인하고 조정합니다.

리뷰 서버가 두 개 필요하다고 선언했는데 하나가 삭제되면, 조건이 허용될 때 새 실행 단위를 만들어 부족한 수를 맞춥니다. 원래 프로세스의 기억을 되살리는 마법은 아닙니다. 새 실행본이 같은 프로그램과 모델을 읽어 준비되는 과정입니다.

## 먼저 네 가지를 구분합시다

| 이름              | 의미                                           | 리뷰 서비스에서의 역할                  |
| ----------------- | ---------------------------------------------- | --------------------------------------- |
| 클러스터(Cluster) | 관리 구성 요소와 실행 노드가 모인 시스템       | 여러 컴퓨터를 하나의 운영 대상으로 관리 |
| 노드(Node)        | 작업을 실행하는 물리 서버 또는 VM              | CPU·메모리와 컨테이너 실행 환경 제공    |
| Pod               | Kubernetes가 배치·관리하는 가장 작은 실행 단위 | 리뷰 서버 컨테이너를 담아 실행          |
| Deployment        | Pod 템플릿과 원하는 복제본 수 등의 선언        | 어떤 이미지로 몇 개를 유지할지 관리     |

Pod에는 하나 이상의 컨테이너가 들어갑니다. 같은 Pod의 컨테이너들은 네트워크를 공유하고, 설정한 볼륨도 함께 사용할 수 있습니다. 그렇다고 모든 컨테이너가 같은 파일을 자동으로 보거나 프로세스 ID 범위까지 항상 공유하는 것은 아닙니다.

이번 예제는 **한 Pod에 리뷰 서버 컨테이너 하나**를 넣습니다. 모든 Pod가 반드시 모델 하나만 실행해야 한다는 규칙은 아닙니다.

## Deployment와 Service의 역할

**Deployment는 실행본의 구성과 수를 관리하고, Service는 실행본들에 접근하는 안정적인 접점을 제공합니다.** Pod가 교체되면 이름이나 IP가 달라질 수 있으므로, 사용자가 매번 Pod 주소를 찾아가게 하지 않습니다.

Deployment는 ReplicaSet을 통해 Pod 집합을 관리합니다. 이번에는 “리뷰 서버 v1을 두 개 유지”라고 이해하고, 다음 레슨에서 내부 경로를 따라갑니다.

```yaml
# Deployment 설정의 일부입니다. 이 조각만으로 배포하지는 않습니다.
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: api
          image: reviews-demo:v1
```

| 궁금한 일                              | 담당과 확인 기준                       |
| -------------------------------------- | -------------------------------------- |
| 같은 버전의 서버 두 개를 유지하고 싶다 | Deployment의 Pod 템플릿과 `replicas`   |
| Pod가 어느 서버에 실행될까?            | Scheduler의 배치 결정과 노드 자원·조건 |
| 사용자가 어디로 요청해야 할까?         | Service와 외부 접근 구성               |
| 부하가 늘면 자동으로 개수도 늘어날까?  | HPA 같은 별도 자동 확장 구성 필요      |

Deployment의 복제본 유지와 부하 기반 자동 확장은 다릅니다. “둘 유지”를 선언했다고 바쁜 눈치를 보고 알아서 열 개로 바꾸지는 않습니다. 자동 확장은 지표와 정책을 따로 구성합니다.

## 복구된다고 데이터까지 돌아오나요?

컨테이너 안의 프로세스가 실패하면 kubelet의 재시작 정책이 작용할 수 있고, 관리 중인 Pod가 삭제되면 컨트롤러가 대체 Pod를 만들 수 있습니다. **컨테이너 재시작과 새 Pod 생성도 다른 사건**입니다.

실행본을 다시 만들 수 있다는 것과 이전 메모리·학습 진행 상태를 복원한다는 것은 다릅니다. 중요한 결과와 체크포인트를 어디에 저장하고 어떻게 읽을지 따로 설계해야 합니다. 이 부분은 다음 스토리지 단원과 연결됩니다.

Kubernetes도 자원이 부족하거나 이미지에 접근하지 못하면 실행을 완료할 수 없습니다. 자동 관리가 모든 실패를 자동 해결한다는 뜻은 아닙니다.

## AWS에서는 어디에 해당하나요?

DevOps 워크북의 ECR·ECS·EKS를 이 위치에 놓아 보면 이해하기 쉽습니다.

| AWS 서비스 | 이 흐름에서의 위치                    |
| ---------- | ------------------------------------- |
| ECR        | 컨테이너 이미지를 저장하는 레지스트리 |
| ECS        | AWS의 컨테이너 실행·관리 서비스       |
| EKS        | AWS의 관리형 Kubernetes 서비스        |

<LessonSummary>

Kubernetes에서는 **원하는 실행 상태를 선언하고 실제 상태를 그에 맞추는 흐름**을 배웁니다. Pod는 실행 단위, Deployment는 템플릿과 복제본 관리, Service는 접근 접점이라는 역할을 갖습니다.

- 새 실행본을 만드는 복구와 이전 계산·파일의 복원은 다릅니다.
- 복제본 유지와 HPA의 부하 기반 자동 확장도 구분합니다.
- 다음에는 선언이 실제 실행으로 이어지는 경로와, 사용자 요청이 도착하는 경로를 나눠 봅니다.
