## 이미지를 두 번 실행하면 두 서버가 생기나요?

리뷰 분류 프로그램을 이미지로 만들었습니다. 같은 이미지에서 컨테이너 A와 B를 실행하면, 둘은 같은 서버일까요? **실행에 쓰는 이미지가 같을 뿐, 컨테이너는 각각 별개의 실행본입니다.** 같은 게임을 설치했다고 두 사람의 세이브 파일까지 자동으로 같아지는 것은 아니잖아요.

## 이미지: 실행하기 전의 묶음

이미지에는 프로그램 코드, Python 같은 실행 환경, 필요한 라이브러리와 기본 시작 설정 등이 들어갑니다. 이미지를 저장해 두었다는 것만으로 서버가 실행되지는 않습니다. 0단원의 “파일이 있는 것”과 “프로그램이 실행 중인 것”의 차이를 다시 떠올려 보세요.

이미지는 읽기 전용 레이어와 설정으로 구성됩니다. 파일을 추가하거나 라이브러리를 설치한 결과를 레이어로 쌓아 재사용할 수 있습니다. 이미지 내용을 바꾸려면 새 이미지를 만듭니다. 이름표인 태그는 다른 이미지로 옮겨 붙일 수 있으므로, `v1`이라는 글자가 같다는 사실만으로 내용까지 영원히 같다고 보장하지는 않습니다. 정확한 내용을 식별할 때는 digest를 사용합니다.

## 컨테이너: 이미지에서 만든 개별 실행본

이미지에서 컨테이너를 만들면, 해당 실행본을 위한 설정과 쓰기 가능한 레이어가 준비됩니다. 실행 중에는 별도의 프로세스가 동작합니다. **컨테이너를 중지해도 컨테이너 객체는 남을 수 있습니다.** 그래서 컨테이너가 항상 “현재 실행 중인 프로세스”만 뜻하는 것은 아닙니다.

| 항목      | 이미지                           | 컨테이너                                |
| --------- | -------------------------------- | --------------------------------------- |
| 역할      | 실행에 사용할 파일·설정의 템플릿 | 그 템플릿에서 만든 개별 실행본          |
| 실행 상태 | 실행 중·중지 상태가 없음         | 실행 중·중지 같은 상태가 있음           |
| 파일 변경 | 기존 이미지 내용은 불변          | 컨테이너별 쓰기 레이어에 기록 가능      |
| 재사용    | 하나로 여러 컨테이너 생성        | 각 컨테이너의 프로세스·변경 상태는 별개 |

## 노드로 두 실행본 만들기

아래에서 이미지와 컨테이너 A·B의 관계를 확인합니다. **직접 연결해 보기**를 누르고 같은 이미지에서 A와 B로 각각 연결해 보세요. A에서 B로 연결하는 것이 아닙니다. A의 기분이나 메모리를 B에게 인수인계하는 흐름이 아니니까요.

두 화살표는 **같은 이미지 사용**을 나타냅니다. 사용자 요청의 이동이나 실행 중인 메모리 복사를 뜻하지 않습니다. 연결 후 두 컨테이너의 시작 환경은 같지만 실행 중 생기는 상태는 달라질 수 있다고 설명해 보세요.

## 파일 하나로 차이를 확인한다면

마지막 실습에서 두 컨테이너를 만든 뒤 아래 실험을 추가할 수 있습니다. 두 컨테이너는 같은 볼륨을 공유하지 않는다고 가정합니다.

```bash
docker exec reviews-a python -c "from pathlib import Path; Path('/tmp/note.txt').write_text('A only')"
docker exec reviews-a python -c "from pathlib import Path; print(Path('/tmp/note.txt').exists())"
docker exec reviews-b python -c "from pathlib import Path; print(Path('/tmp/note.txt').exists())"
```

**예상 결과:** A에서는 `True`, B에서는 `False`입니다. A의 쓰기 레이어에 만든 파일이 B나 원본 이미지에 자동 반영되지 않기 때문입니다. 같은 볼륨을 두 컨테이너에 연결했다면 결과는 달라질 수 있습니다.

| 이어서 해볼 조작                                      | 확인할 것                                         |
| ----------------------------------------------------- | ------------------------------------------------- |
| A를 `stop`하고 `start`                                | 기존 컨테이너의 쓰기 레이어 파일은 남음           |
| A를 중지한 뒤 `rm`하고 같은 이미지로 새 컨테이너 생성 | 이전 A의 쓰기 레이어 파일은 새 컨테이너에 없음    |
| 같은 이미지를 쓰되 환경 변수를 다르게 지정            | 시작할 이미지가 같아도 실제 설정은 달라질 수 있음 |

실행 상태를 잃어도 보존해야 하는 데이터는 컨테이너 내부 쓰기 레이어에만 맡기지 않습니다. 다음 단원에서 저장소와 수명을 더 자세히 다룹니다.

## 같은 환경을 어디까지 보장할까요?

동일한 이미지로 코드와 라이브러리를 맞출 수 있어도, 호스트의 커널·CPU 아키텍처·GPU 드라이버나 외부 데이터까지 자동으로 같아지지는 않습니다. 이미지 버전, 환경 변수, 마운트, 사용할 모델 버전을 함께 확인합니다.

다음 질문은 규모입니다. 컨테이너 하나를 직접 실행하는 것은 알겠는데, 서버가 여러 대이고 실행본이 수십 개면 누가 관리할까요? 다음 레슨에서 Kubernetes를 연결합니다.

<LessonSummary>

**이미지는 실행 환경의 템플릿이고, 컨테이너는 그 이미지로 만든 개별 실행본입니다.** 같은 이미지에서 A와 B를 만들 수 있지만 프로세스와 쓰기 레이어는 각각 따로 관리됩니다.

- 중지와 삭제는 다릅니다. 기존 컨테이너의 파일 유지와 새 컨테이너의 파일 상태도 구분합니다.
- 동일 이미지에 더해 외부 설정·모델·데이터도 확인해야 실행 환경을 맞출 수 있습니다.
- 여러 실행본을 계속 유지하는 일은 다음의 Kubernetes로 연결됩니다.
