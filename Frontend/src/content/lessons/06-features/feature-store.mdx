## 같은 고객이 두 팀에서 다르게 보이는 이유는?

추천 팀과 이탈 예측 팀이 같은 고객의 최근 클릭 수를 계산했습니다. 한쪽 보고서에는 3번, 다른 쪽에는 8번으로 나옵니다. 고객은 한 명인데 전처리 코드가 두 벌이라 집계 기준부터 다시 맞춰야 합니다. 두 팀이 같은 정의를 한 번만 만들고 함께 쓰려면 어떻게 해야 할까요?

Feature Store는 피처를 계산하고 저장해 필요한 팀과 모델에 제공하는 과정을 관리하는 시스템입니다.

## Feature Store의 다섯 가지 역할

| 역할                   | 쉽게 말하면                          | 예시                                    |
| ---------------------- | ------------------------------------ | --------------------------------------- |
| Transform              | 원천 데이터에서 피처를 계산          | 클릭 로그 → 최근 1시간 클릭 수          |
| Storage                | 과거 값과 최신 값을 목적에 맞게 보관 | Offline Store와 Online Store            |
| Serving                | 학습이나 서비스에 피처를 전달        | 사용자 ID로 최신 피처 조회              |
| Operational Monitoring | 피처 시스템의 상태와 품질을 관찰     | 지연, 누락, 오류율, 오래된 값 확인      |
| Registry               | 피처의 설명과 버전을 기록하는 목록   | 이름, 계산식, 담당자, 자료형, 사용 모델 |

Registry는 팀이 사용할 피처를 찾는 카탈로그이자 기준표입니다. 같은 이름의 피처가 무엇을 뜻하는지, 누가 관리하는지, 어느 모델이 사용하는지 확인할 수 있습니다.

## 한 번 만든 피처를 재사용합니다

한 팀이 검증한 `customer_click_count_1h`를 등록하면 다른 팀은 원천 로그부터 다시 집계하지 않고 같은 피처를 사용할 수 있습니다.

- 중복된 전처리 코드가 줄어듭니다.
- 팀마다 계산 결과가 달라지는 문제를 줄입니다.
- 이미 검증한 피처로 새 모델 실험을 빠르게 시작할 수 있습니다.
- 피처의 버전과 사용 모델을 추적하기 쉬워집니다.

재사용은 값을 무조건 복사한다는 뜻이 아닙니다. **같은 정의와 관리 기준을 공유한다**는 뜻이며, 필요에 따라 과거 값이나 최신 값을 알맞은 저장소에서 조회합니다.

## Feature Store 내부 흐름을 한눈에 봅니다

> **경로를 바꿔 관찰하기** — 구성 요소를 눌러 역할을 확인하고, 실시간 추론과 모델 학습을 선택해 데이터가 전달되는 경로를 살펴보세요. Storage에서는 최신 값과 과거 이력이 나뉘는 구조를 확인할 수 있습니다.

<Activity open />

아키텍처에서 확인할 핵심은 다음과 같습니다.

1. Registry가 피처의 이름, 계산식, 버전과 소유자를 관리합니다.
2. Transform이 원천 데이터를 같은 정의의 피처 값으로 계산합니다.
3. 저장된 피처는 학습용 대량 조회와 서비스용 빠른 조회 경로로 전달됩니다.
4. Serving이 모델에 값을 제공하고 Monitoring이 지연, 누락과 오래된 값을 관찰합니다.

두 경로는 목적과 조회 방법이 달라도 같은 피처 정의를 따라야 합니다. 계산식이나 집계 범위가 달라지면 조회 속도가 빨라도 Training-Serving Skew가 남습니다.

## Feature Store가 자동으로 해결하지 못하는 것

- 잘못 작성한 피처 정의
- 온라인 갱신 실패로 남은 오래된 값
- 과거 학습 자료에 섞인 미래 정보
- 실제 고객 행동이 변하는 Data Drift

따라서 피처 값뿐 아니라 지연·누락·분포 변화와 학습·서비스 간 차이도 계속 관찰해야 합니다.

<Callout title="Feature Store를 한 문장으로 설명한다면">

피처를 한 번 정의해 여러 팀과 모델이 학습과 서비스에서 일관되게 찾고 사용할 수 있도록 계산·저장·제공·등록·관찰을 관리하는 시스템입니다.

</Callout>

<LessonSummary>

Feature Store는 단순한 데이터베이스가 아니라 피처의 전체 흐름을 관리합니다. Transform은 원천 데이터를 피처로 만들고, Storage와 Serving은 학습용 과거 값과 서비스용 최신 값을 목적에 맞게 제공합니다. Registry는 정의와 버전을 기록하고 Monitoring은 지연과 품질 문제를 관찰합니다. 이렇게 등록한 피처를 여러 팀이 재사용하면 중복 작업과 학습-서빙 불일치를 줄일 수 있습니다.

</LessonSummary>
