## 왜 저장소가 두 개일까요?

모델 학습은 수개월치 피처를 한꺼번에 읽지만, 실시간 서비스는 사용자 한 명의 최신 피처를 매우 빠르게 읽어야 합니다. 하나의 저장 방식으로 두 요구를 모두 만족시키기 어렵기 때문에 Feature Store는 보통 Offline Store와 Online Store를 나눕니다.

두 저장소는 속도와 보관 범위가 다르지만, `최근 1시간 클릭 수`처럼 **피처가 뜻하는 내용은 같아야 합니다.**

## Offline Store는 과거 피처를 모아 학습에 제공합니다

Offline Store는 **피처의 과거 이력을 보관하는 저장소**입니다. 모델을 학습할 때는 한 사용자의 현재 값만 필요한 것이 아니라, 많은 사용자가 과거에 어떤 상태였는지 알아야 합니다. 이 때문에 대량 데이터를 읽고 학습 기준 시각에 맞춰 결합하는 작업에 적합하게 구성합니다.

Offline은 인터넷에 연결되어 있지 않다는 뜻이 아닙니다. 여기서는 실시간 요청 한 건의 응답보다 **과거 이력 보존과 대량 학습 자료 생성**에 초점을 둔다는 뜻입니다. 모델 학습·검증과 배치 추론에 사용할 수 있습니다.

## Online Store는 최신 피처를 빠르게 제공합니다

Online Store는 **실시간 추론에 필요한 최신 피처 값을 보관하는 저장소**입니다. 추천 요청이 들어오면 사용자 ID나 상품 ID 같은 키로 필요한 값을 읽어 모델 입력에 전달합니다. 일반적으로 키로 값을 빠르게 찾는 Key-Value 저장 방식을 사용합니다.

같은 고객 A가 오전 10시에 추천 화면을 열면 Online Store에서 최신 `최근 1시간 클릭 수`인 12회를 가져옵니다. 수개월치 이력을 훑어보지 않고 필요한 엔터티의 값만 조회하므로 낮은 지연과 높은 요청 처리량이 중요합니다.

다만 **빠른 조회가 최신 값을 보장하지는 않습니다.** 갱신 작업이 멈추면 오래된 값도 빠르게 반환될 수 있습니다. 마지막 갱신 시각과 지연, 누락을 관찰하고, 오래된 값의 만료·대체 기준을 정해야 합니다.

## 두 저장소를 비교해 봅시다

| 구분      | Offline Store           | Online Store                          |
| --------- | ----------------------- | ------------------------------------- |
| 주요 목적 | 모델 학습과 대량 분석   | 실시간 추론                           |
| 보관 범위 | 수개월·수년의 과거 이력 | 사용자별 최신 값 중심                 |
| 조회 방식 | 많은 행을 한꺼번에 읽기 | 사용자 ID 같은 키로 빠르게 한 건 조회 |
| 중요 조건 | 큰 용량, 과거 시점 조회 | 낮은 지연, 최신성                     |
| 대표 예시 | S3, BigQuery, Snowflake | Redis, DynamoDB                       |

Offline Store가 느리다는 말은 실시간 요청에 적합하지 않다는 뜻입니다. 대량 학습 자료를 효율적으로 읽는 능력은 뛰어날 수 있습니다. Online Store는 모든 과거 이력을 보관하기보다 서비스에 필요한 최신 값을 빠르게 제공하는 데 집중합니다.

두 저장소의 값이 언제나 숫자까지 같아야 하는 것은 아닙니다. 오전 9시와 오전 10시의 클릭 수는 달라도 됩니다. 일치시켜야 하는 것은 `최근 1시간`이라는 집계 범위와 계산식·버전, 그리고 각 값을 해석하는 시점입니다.

## 피처는 어떻게 두 저장소에 들어갈까요?

```text
원천 이벤트
   ↓
Transform: 공통 정의로 피처 계산
   ├─ Offline Store: 과거 이력 저장 → 모델 학습
   └─ Online Store: 최신 값 저장 → 실시간 추론
```

학습용 피처를 계산해 Offline Store에 저장한 뒤 그 값을 학습에 사용하므로, 항상 같은 계산을 두 번 해야 하는 것은 아닙니다. 다만 Online Store에 최신 값을 전달하고 유지하는 작업에는 별도의 저장·갱신 비용이 듭니다.

## 두 저장소를 갱신하는 방법

| 방식          | 언제 사용하나요?                          | 주의할 점                         |
| ------------- | ----------------------------------------- | --------------------------------- |
| 배치 갱신     | 하루 한 번처럼 약간 오래된 값도 괜찮을 때 | 실행 사이에는 값이 오래될 수 있음 |
| 스트리밍 갱신 | 클릭·결제처럼 즉시 반영해야 할 때         | 지연, 중복 이벤트, 실패 처리 필요 |
| 요청 시 계산  | 요청 순간에만 알 수 있는 정보가 필요할 때 | 응답 시간이 길어지지 않게 관리    |

배치와 실시간 중 하나만 고집할 필요는 없습니다. 국가나 상품 분류처럼 천천히 변하는 피처는 배치로, 최근 10분 결제 횟수처럼 신선도가 중요한 피처는 스트리밍으로 갱신할 수 있습니다.

## Online Store에 값이 없다면?

피처가 없을 때의 행동은 미리 정해야 합니다.

- 안전하게 즉시 계산할 수 있다면 요청 시 계산합니다.
- 모델을 만들 때 정한 기본값이나 검증된 평균값을 사용합니다.
- 중요한 피처라면 예측을 중단하고 규칙 기반 처리로 전환합니다.

아무 평균값이나 넣으면 학습 때와 다른 입력이 되어 새로운 불일치가 생길 수 있습니다. 어떤 대체값을 쓸지 학습 단계부터 정하고, 누락 횟수도 Monitoring으로 관찰해야 합니다.

## 실습은 다음 순서로 진행하세요

실습은 **공통 피처 정의 → 두 저장소 → 정의 비교·결과 확인**의 4개 노드로 구성됩니다. 원천 이벤트 수집과 피처 계산은 준비된 것으로 두고, 공통 정의에서 두 저장소로 가는 연결 2개도 기본으로 제공합니다.

1. **Offline Store · 학습**의 출력을 비교 노드의 **학습 피처 정의** 입력에 연결합니다.
2. **Online Store · 추론**의 출력을 비교 노드의 **현재 사용자 피처** 입력에 연결합니다.
3. 온라인 집계 시간을 `최근 24시간`으로 실행해 불일치를 확인합니다.
4. `최근 1시간 · 학습과 일치`로 바꾸고 다시 실행해 일치 결과를 확인합니다.

실습에서 학습 정의는 최근 1시간으로 고정되어 있습니다. 온라인 경로가 최근 24시간이면 저장소 연결이 모두 있어도 피처의 의미가 다르므로 올바른 결과가 아닙니다.

직접 연결은 2개, 바꾸는 설정은 온라인 집계 시간 하나입니다. 원천 계산과 별도 결과 노드를 줄여 두 저장소의 역할과 정의 일치에 집중합니다. `새 구성 만들기`를 선택하면 기본 연결도 비워지므로, 처음에는 기본 화면이나 `잘못된 구성 수정`에서 시작하세요.

<Callout title="두 저장소를 확인하는 기준">

저장 위치가 같은지를 보는 것이 아니라 피처 이름·계산식·집계 시간·시점·버전이 같은지 확인하세요. 또한 Online Store의 값이 얼마나 최신인지와 갱신 실패 여부도 함께 관찰해야 합니다.

</Callout>

<LessonSummary>

Offline Store는 모델 학습에 필요한 많은 과거 피처를 보관하고, Online Store는 실시간 추론에 필요한 최신 피처를 낮은 지연으로 제공합니다. 피처는 배치나 스트리밍으로 갱신할 수 있으며 요청 시 계산이 필요한 경우도 있습니다. 두 저장소의 기술과 조회 방식은 달라도 같은 공통 정의를 사용해야 하며, 값이 누락될 때 사용할 대체 방법과 갱신 지연도 미리 정하고 관찰해야 합니다.

</LessonSummary>
