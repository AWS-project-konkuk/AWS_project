## 같은 click_count인데 모델은 왜 헷갈릴까요?

무척 활발한 고객이라고 모델이 판단했습니다. 확인해 보니 서비스가 보여 준 숫자는 24시간 동안의 클릭 수였고, 모델은 1시간 동안의 클릭 수로 학습했습니다. 열 이름은 똑같은데 기준이 하루치로 늘어난 셈입니다. 학습과 서비스에서 숫자의 뜻을 어떻게 맞출까요?

학습에서 사용한 피처와 운영에 전달된 피처가 어긋나는 현상을 **학습-서빙 불일치(Training-Serving Skew)**라고 합니다.

## 먼저 피처가 무엇인지 알아봅시다

피처(Feature)는 모델이 예측할 때 사용하는 입력값입니다. 원천 데이터를 그대로 쓰기도 하지만, 보통은 계산과 전처리를 거쳐 만듭니다.

```text
클릭 로그 → 최근 1시간 클릭 수 계산 → click_count_1h = 12 → 모델 입력
```

모델은 `12`라는 숫자만 봅니다. 이 값이 1시간 동안의 클릭인지 24시간 동안의 클릭인지 스스로 알 수 없으므로, 만드는 기준을 사람이 일관되게 관리해야 합니다.

## 왜 불일치가 생길까요?

| 원인             | 쉬운 예시                                                   |
| ---------------- | ----------------------------------------------------------- |
| 전처리 코드 차이 | 학습은 Spark로 1시간 집계, 서비스는 다른 코드로 24시간 집계 |
| 기본값 차이      | 학습은 누락값을 0, 서비스는 평균값으로 처리                 |
| 데이터 변화      | 학습 후 고객 행동이나 상품 구성이 달라짐                    |
| 갱신 지연        | 온라인 저장소에 오래된 피처가 남아 있음                     |

전처리 코드가 다른 문제와 실제 데이터가 시간에 따라 변한 문제는 구분해야 합니다. **Training-Serving Skew**는 주로 두 경로가 같은 입력을 다르게 처리하는 불일치이고, **Data Drift**는 시간이 지나며 실제 데이터 분포가 변하는 현상입니다.

## 해결의 출발점은 같은 정의입니다

가장 좋은 출발점은 학습과 서비스가 같은 피처 정의를 재사용하는 것입니다.

```text
같은 원천 데이터
      ↓
공통 피처 정의: 최근 1시간 클릭 수
      ├─ 학습용 과거 피처
      └─ 서비스용 최신 피처
```

언어나 실행 환경이 달라 같은 코드를 그대로 실행하기 어렵다면, 두 경로에 같은 입력을 넣고 만들어진 **피처 벡터가 같은지 비교하는 테스트**가 필요합니다. 정의의 이름뿐 아니라 집계 시간, 누락값 처리, 자료형과 버전도 함께 확인합니다.

## 과거 학습에는 당시 알 수 있었던 값만 사용합니다

1월 1일의 구매 여부를 예측하는 학습 행에 1월 2일에 확정된 결제 결과를 붙이면 미래의 답을 미리 본 셈입니다. 학습 점수는 높게 나오지만 실제 서비스에서는 그 값을 사용할 수 없습니다.

따라서 학습 자료를 만들 때는 **예측 시점에 실제로 이용 가능했던 피처만 연결**해야 합니다. 이를 Point-in-Time Correctness라고 합니다. 이벤트가 발생한 시간뿐 아니라 시스템에 도착하고 사용할 수 있게 된 시간도 확인해야 합니다.

<LessonSummary>

Training-Serving Skew는 학습할 때 사용한 피처와 실제 서비스가 모델에 전달하는 피처가 서로 다른 문제입니다. 전처리 코드, 집계 범위, 기본값이나 갱신 시점이 다르면 같은 피처 이름도 다른 의미가 됩니다. 공통 정의를 사용하고 두 경로의 결과를 비교해야 하며, 과거 학습 자료에는 그 예측 시점에 실제로 알 수 있었던 값만 넣어야 합니다.

</LessonSummary>
