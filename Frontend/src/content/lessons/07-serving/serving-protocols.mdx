## 문제 상황

모델 추론은 빠른데 서비스 간 직렬화와 통신 비용이 큽니다. 프로토콜을 바꾸기 전에 비용이 어디서 발생하는지 측정합니다.

## 개념과 동작 원리

HTTP API와 gRPC는 통신 인터페이스 선택입니다. gRPC는 Protocol Buffers 기반 메시지와 서비스 계약, HTTP/2 기반 통신·스트리밍 등을 활용합니다. JSON 기반 HTTP API는 브라우저·도구에서 접근하기 쉬운 장점이 있습니다. 서버·클라이언트·중간 프록시 지원을 함께 고려합니다.

## 자료와 요청의 흐름

요청 직렬화 → 네트워크 전송 → 입력 검증·전처리 → 추론 → 응답 직렬화의 시간을 나눠 측정합니다. Batch와 Real-time은 처리 시점의 선택이고 HTTP·gRPC는 통신 방식의 선택이므로 서로 대체하는 분류가 아닙니다.

## 비교와 한계

전송 프로토콜 선택은 모델 품질을 바꾸지 않습니다. Shadow는 새 모델의 응답을 사용자에게 보내지 않고, Canary는 일부 사용자에게 실제로 보냅니다. 전환과 승격은 별도 판단입니다.

## 전체 과정과 연결

평가를 통과한 모델도 사용자가 접근할 실행 환경과 요청 경로가 필요합니다. 응답을 미리 계산할지 요청마다 계산할지에 따라 서빙 구조가 달라집니다. 모델 교체 시에는 누가 새 응답을 받는지, 실패 시 어떻게 이전 버전으로 돌아갈지, 어떤 지표를 보고 전환할지를 함께 정해야 합니다.
