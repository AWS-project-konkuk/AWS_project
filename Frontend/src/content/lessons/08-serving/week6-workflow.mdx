## 두 설정 모두 10%인데 고객이 받는 답도 같을까요?

배포 화면에 10%가 표시됩니다. 한 동료는 고객 열 명 중 한 명이 새 답을 받는다고 하고, 다른 동료는 새 모델이 결과만 기록한다고 합니다. 두 방식에서 고객이 받는 답은 어떻게 달라질까요?

## 이번 미션

모델을 바꾸는 동안에도 사용자 요청에 응답해야 합니다. **응답을 처리하는 동안 단 한 번도 멈추면 안 됩니다.**

## 설계하고 비교할 것

1. **Gateway**를 선택해 **모델 처리**를 추가합니다. **요청 분배의 신규 모델 요청**과 **시작의 신규 모델**을 새 노드에 연결하세요.
2. 새 노드의 **모델 결과**를 **결과 관측**에 연결하세요. 기존 모델의 결과 경로는 준비되어 있습니다.
3. **요청 분배**에서 **중단 배포**를 실행합니다. 기존 모델을 내린 뒤 응답이 끊긴 요청 수를 확인하세요.
4. **Blue-Green 전환**으로 실행합니다. 두 환경을 준비했지만, 이 실습의 라우터는 요청 대상을 한꺼번에 바꾸는 순간 일부 요청을 놓칩니다. 배포가 반려된 이유를 결과에서 확인하세요.
5. **Canary 전환** 또는 **Shadow 비교**로 바꿔 사용자 요청 100건에 누락이나 중복 없이 응답하세요. Canary의 비율은 신규 모델이 응답하는 사용자 수, Shadow의 비율은 비교를 위해 복제하는 요청 수를 정합니다.

## 실습에서 가져갈 이해

Canary의 신규 응답은 사용자에게 전달됩니다. Shadow는 복제 요청을 비교하지만 사용자에게는 기존 모델의 응답을 전달합니다.

## 적용 조건과 한계

이 실습은 요청 100건을 고정 비율로 나누는 모형입니다. Blue-Green의 응답 누락은 이 라우터의 일괄 전환 조건에서 발생합니다. 실제 운영에서는 두 환경을 유지하면서 전환 중에도 응답하도록 구성할 수 있습니다. Shadow에서 신규 모델의 사용자 응답을 검증하려면 실제 트래픽을 넘기는 단계가 이어져야 합니다.

## 전체 과정과 연결하기

배포 전략에 맞게 요청 경로를 구성하고, 전환 중에 응답이 끊기지 않는지 확인합니다. Canary의 전환 비율은 실제 응답 대상을, Shadow의 복제 비율은 관측용 추가 실행을 바꿉니다.
