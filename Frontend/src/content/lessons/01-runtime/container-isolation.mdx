## 문제 상황

두 컨테이너가 같은 커널을 쓰는데 서로 다른 프로세스 목록을 보고 메모리 제한도 다릅니다.

그림의 **컨테이너 A**, **컨테이너 B**, **공유 커널**에 주목해 보세요. 같은 Linux 커널을 쓰는 프로세스라도 Namespaces로 보이는 프로세스·네트워크·마운트 범위를 나눌 수 있습니다.

## 개념과 동작 원리

Linux Namespaces는 프로세스 ID·네트워크·마운트 등의 관측 범위를 나누고 Cgroups는 프로세스 집합의 자원 사용량을 제한·계측합니다. 컨테이너의 애플리케이션은 호스트 커널의 시스템 호출을 사용하며 VM처럼 각자의 게스트 커널을 부팅하는 구조와 다릅니다.

## 자료와 요청의 흐름

애플리케이션 → 격리된 프로세스 환경 → 공유 호스트 커널 → 하드웨어 순서로 봅니다. 이미지의 사용자 공간 라이브러리와 호스트 드라이버의 역할을 나눠 확인합니다. Docker Desktop에서는 Linux VM 위에 컨테이너가 실행될 수도 있습니다.

## 그림으로 비교하는 VM과 컨테이너

왼쪽은 가상 머신마다 게스트 커널을 갖는 구조이고 오른쪽은 컨테이너 프로세스가 호스트 커널을 공유하는 구조입니다. 커널 공유와 프로세스 격리를 서로 다른 층으로 읽어 보세요.

## 비교와 한계

컨테이너는 호스트 커널을 공유합니다. 이미지가 같아도 GPU 드라이버나 외부 설정이 다를 수 있습니다. Deployment의 복제본 유지와 HPA의 부하 기반 확장은 별도 기능입니다.

## 전체 과정과 연결

같은 코드가 다른 서버에서 실패한다면 패키지·라이브러리·실행 설정을 비교해야 합니다. 이미지는 실행 환경의 배포 단위이고 컨테이너는 그 이미지로 실행한 프로세스입니다. Kubernetes는 원하는 Pod 수와 배치 조건을 받아 실행 상태를 조정합니다. 실행 위치를 정하는 과정과 사용자 요청을 전달하는 과정은 서로 다른 책임입니다.
