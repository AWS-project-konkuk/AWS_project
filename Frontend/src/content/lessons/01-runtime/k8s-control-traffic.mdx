## 문제 상황

GPU 서버에 Pod를 배치했는데 Service로 보낸 요청이 도착하지 않습니다. 올바른 노드에 배치됐다는 사실만으로 요청 대상이 되는 것은 아닙니다.

## 개념과 동작 원리

API Server는 객체 변경을 받고 etcd는 API 객체 상태를 저장합니다. 컨트롤러는 원하는 상태와 실제 상태의 차이를 조정하고 Scheduler는 아직 배치되지 않은 Pod의 노드를 선택합니다. kubelet과 컨테이너 런타임은 노드에서 컨테이너 실행을 담당합니다.

## 자료와 요청의 흐름

Deployment → ReplicaSet → Pod 생성·배치 → kubelet 실행이라는 제어 흐름과 클라이언트 → Service → 선택된 준비 상태의 Pod라는 요청 흐름을 구분합니다. nodeSelector는 노드 라벨을, Service selector는 Pod 라벨을 봅니다. 노드 라벨이 Pod에 자동 복사되는 것은 아닙니다.

> **연결 전에 예측하기** — Deployment가 원하는 상태를 관리하는 관계와 Service가 요청을 전달하는 관계를 서로 다른 포트로 읽어보세요.

<NodeExample />

연결을 따라가며 확인한 자료는 **원하는 실행 상태 · 추론 요청**입니다. Pod가 배치되지 않는 문제와 실행 중인데 요청이 도착하지 않는 문제를 나눠 보세요. 각각 배치 조건과 요청 대상·포트·준비 상태에서 단서를 찾습니다.

## 비교와 한계

컨테이너는 호스트 커널을 공유합니다. 이미지가 같아도 GPU 드라이버나 외부 설정이 다를 수 있습니다. Deployment의 복제본 유지와 HPA의 부하 기반 확장은 별도 기능입니다.

## 전체 과정과 연결

같은 코드가 다른 서버에서 실패한다면 패키지·라이브러리·실행 설정을 비교해야 합니다. 이미지는 실행 환경의 배포 단위이고 컨테이너는 그 이미지로 실행한 프로세스입니다. Kubernetes는 원하는 Pod 수와 배치 조건을 받아 실행 상태를 조정합니다. 실행 위치를 정하는 과정과 사용자 요청을 전달하는 과정은 서로 다른 책임입니다.
