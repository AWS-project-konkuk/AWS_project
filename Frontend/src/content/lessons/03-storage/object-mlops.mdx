## 문제 상황

여러 개의 GPU 학습 서버를 필요할 때마다 생성하고 종료하는 MLOps 환경을 구축하려고 합니다.

학습 서버의 로컬 디스크에 데이터셋을 저장했더니 다음과 같은 문제가 발생했습니다.

- 서버를 종료하면 다음 학습 작업에서 데이터셋을 다시 찾기 어렵습니다.
- 새로운 서버마다 같은 대용량 데이터를 다시 복사해야 합니다.
- 학습이 끝난 모델 파일이 특정 서버에만 남아 배포 작업에서 사용할 수 없습니다.
- 어떤 데이터 버전으로 어떤 모델을 만들었는지 추적하기 어렵습니다.

그렇다면 데이터셋과 모델을 학습 서버의 수명과 분리해 공통으로 보관할 수는 없을까요?

Object Storage를 사용하면 학습 서버가 교체되어도 버킷과 객체 키를 이용해 같은 데이터를 다시 찾을 수 있습니다.

**이번 학습에서는 Object Storage가 MLOps에서 어떤 역할을 담당하며, 데이터 보관과 빠른 학습 공급이 왜 다른 문제인지 알아봅니다.**

## 개념과 동작 원리

### 1. 객체는 어떻게 저장될까요?

Object Storage는 데이터를 **객체(Object)** 단위로 저장합니다. 각 객체는 데이터 본문, 메타데이터, 객체를 찾기 위한 키로 구성됩니다.

Amazon S3에서는 다음 요소로 객체를 찾습니다.

- **버킷(Bucket)**: 객체를 보관하는 공간입니다.
- **객체 키(Object Key)**: 버킷 안에서 객체를 식별하는 이름입니다.
- **버전 ID(Version ID)**: Versioning을 사용할 때 같은 키의 여러 버전을 구분합니다.

```text
datasets/cat-images/v3/train.tar
checkpoints/run-42/epoch-10.pt
models/cat-classifier/run-42/model.pt
```

키의 `/`는 관리하기 쉬운 이름 구조를 표현하지만, 일반 파일 시스템의 실제 디렉터리와 완전히 같은 개념은 아닙니다.

### 2. MLOps에서는 어떻게 사용할까요?

| 단계            | 객체 작업 | 예시                          |
| --------------- | --------- | ----------------------------- |
| 데이터 준비     | PUT       | 전처리한 데이터셋을 저장      |
| 모델 학습       | GET       | 지정한 버전의 데이터셋을 읽음 |
| 체크포인트 저장 | PUT       | 중간 학습 상태를 저장         |
| 모델 배포       | GET       | 검증이 끝난 모델을 가져옴     |

학습 작업의 흐름은 다음과 같습니다.

1. 데이터 준비 작업이 버전이 표시된 데이터셋 객체를 저장합니다.
2. 데이터 로더가 필요한 객체를 읽어 배치를 만듭니다.
3. GPU가 전달받은 배치로 모델을 학습합니다.
4. 학습 작업이 체크포인트와 최종 모델을 다시 저장합니다.
5. 평가나 배포 작업이 같은 객체 키를 이용해 모델을 가져옵니다.

### 3. 버전을 왜 기록해야 할까요?

S3 Versioning을 사용하면 같은 키의 과거 객체를 보존하고 버전 ID로 구분할 수 있습니다.

하지만 Versioning만으로 어떤 데이터로 모델을 학습했는지 자동으로 알 수 있는 것은 아닙니다. 데이터 객체의 버전, 학습 코드 버전, 실행 설정과 결과 모델의 관계를 함께 기록해야 합니다.

## 비교와 한계

- 객체는 API로 읽고 쓰므로 일반 로컬 파일 시스템과 사용 방식이 다릅니다.
- 작은 객체를 매우 많이 개별 요청하면 요청 지연이 누적될 수 있습니다.
- Object Storage에 원본이 있어도 로더나 네트워크가 느리면 GPU는 기다립니다.
- 버전이 남아 있어도 학습 실행과 연결한 기록이 없으면 사용한 객체를 찾기 어렵습니다.
- 여러 작업이 같은 키에 결과를 저장하면 의도하지 않은 덮어쓰기가 발생할 수 있습니다.

## 전체 과정과 연결

Object Storage는 **데이터를 오래 보관하는 경로**를 담당합니다. 다음 강의에서는 저장소의 데이터를 GPU까지 빠르게 공급하지 못할 때 발생하는 I/O 병목을 살펴봅니다.

> **판단할 때 확인하기**
>
> “이 데이터와 모델을 어떤 버킷·객체 키·버전 ID로 다시 찾을 수 있을까?”

## 핵심 정리

Object Storage는 학습 서버와 데이터의 수명을 분리하여 **데이터셋, 체크포인트, 모델 아티팩트의 공통 보관소**를 제공합니다. 같은 실험을 다시 찾으려면 객체 키와 버전뿐 아니라 코드·설정·실행 ID의 관계도 함께 기록해야 합니다.
