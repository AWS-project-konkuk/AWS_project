## Pod도 돌아오고 GPU도 켜졌는데 왜 느릴까요?

학습 Pod를 교체하고 다시 실행했더니 첫 배치가 늦게 들어옵니다. 바로 전 실행에서 만들어 둔 `cache.bin`은 새 Pod에서 보이지 않고, 원본부터 읽자니 GPU가 다음 배치를 한참 기다립니다. 파일을 살려야 하는 문제와 공급을 빠르게 해야 하는 문제를 어디서부터 풀까요?

## 저장소 원본에서 GPU 학습까지 연결하기

**시작**은 원본 객체 목록과 GPU 학습 요청을 보냅니다. 초기 구성에서 객체 목록은 저장소의 **원본 읽기**에, 학습 요청은 EC2의 **배치 준비**에 연결되어 있습니다. 남은 포트를 연결하세요.

| 출력      | 입력      | 전달하는 자료                    |
| --------- | --------- | -------------------------------- |
| 원본 읽기 | 배치 준비 | 원본 이미지 데이터               |
| 배치 준비 | 학습 실행 | 준비된 배치가 담긴 학습 작업     |
| 학습 실행 | 모델 저장 | 학습 결과 체크포인트             |
| 모델 저장 | 도착      | 저장소에 저장한 모델과 실행 지표 |

## Pod 교체 후 캐시와 공급 비교하기

연결을 마쳤으면 **실습 실행**을 누르고 결과에서 GPU 공급량과 Pod 교체 후 캐시를 확인하세요. 매 실행에서 Pod 교체를 가정합니다. PV와 PVC가 볼륨을 연결하는 과정은 앞의 PV·PVC 강의에서 확인할 수 있습니다.

| 실행                  | 반복 읽기 캐시 | 작은 파일 읽기 | 캐시 보관 경로 | 예상 결과                        |
| --------------------- | -------------- | -------------- | -------------- | -------------------------------- |
| 기본                  | 사용 안 함     | 개별 읽기      | Pod 임시 저장  | 30배치/초, GPU 데이터 대기율 70% |
| 임시 캐시             | 사용           | 개별 읽기      | Pod 임시 저장  | 교체 후 캐시 손실, 30배치/초     |
| 유지 캐시             | 사용           | 개별 읽기      | 유지 볼륨      | 교체 후 캐시 보존, 60배치/초     |
| 유지 캐시와 파일 묶음 | 사용           | 파일 묶음 읽기 | 유지 볼륨      | 120배치/초, 공급 목표 충족       |

이 실습의 GPU 소비 능력은 100배치/초이고 공급 목표는 80배치/초입니다. 공급량은 파일 묶음 읽기와 보존된 캐시가 각각 두 배씩 늘린다는 가정을 사용합니다.

## 모델 저장까지 확인하기

마지막 실행의 결과 지표에서 공급 목표, 캐시 보존, 저장소 모델 객체 키를 확인하세요. 모델은 원본 이미지 객체 목록을 읽어 학습한 결과입니다. 결과 패널의 관찰 기록과 이해 확인을 마치세요.

<LessonSummary>

원본과 학습 모델은 객체 저장소에 보관합니다. 반복 읽기 캐시와 파일 묶음은 GPU에 보내는 데이터의 공급을 개선합니다. 캐시를 교체 뒤에도 재사용하려면 유지 볼륨에 보관해야 합니다.

</LessonSummary>
