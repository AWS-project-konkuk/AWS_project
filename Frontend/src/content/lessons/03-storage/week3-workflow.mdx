## 종합 문제

원본 데이터는 남아 있지만 GPU는 다음 배치를 기다리고, Pod가 교체되면 내려받아 둔 캐시가 사라집니다. **원본 보존**, **빠른 공급**, **Pod 교체 뒤 캐시 유지**를 서로 다른 문제로 나누어 해결해 봅니다.

그림의 **영속 원본**, **캐시·로더**, **GPU 소비**에 주목해 보세요. 원본은 실행 작업보다 오래 보존할 저장소에 두고, 로더와 캐시가 GPU에 배치를 공급하게 구성합니다.

## 이번 미션

GPU는 초당 100배치를 소비하지만 작은 객체 읽기는 초당 30배치만 공급합니다. Pod 교체 후 캐시 파일까지 사라집니다.

## 설계하고 비교할 것

다음 역할을 구분해 연결하세요.

- **Object Storage**: 버전이 있는 원본 데이터와 완성된 모델을 보관합니다.
- **데이터 로더**: 객체를 읽고 전처리해 배치를 만듭니다.
- **캐시·shard**: 반복 읽기와 작은 객체 요청 횟수를 줄입니다.
- **PV·PVC**: Pod가 사용할 캐시 볼륨을 요청하고 연결합니다.
- **GPU**: 준비된 배치를 소비해 학습합니다.

## 실습 순서

1. 기본 설정에서 공급 30배치/초와 소비 100배치/초의 차이를 확인합니다.
2. shard와 반복 읽기 캐시를 적용해 공급 속도가 어떻게 변하는지 비교합니다.
3. 캐시 경로를 Pod 임시 공간과 PVC 볼륨으로 바꾸어 Pod 교체 결과를 비교합니다.
4. 학습 결과 모델이 다시 Object Storage로 가는 경로를 완성합니다.

## 결과를 해석할 때

활동에서 캐시와 shard가 공급을 두 배로 만드는 값은 원리를 보여 주는 교육용 가정입니다. 실제 개선 폭은 객체 크기, 네트워크, 로더 worker, CPU 전처리와 캐시 적중률을 측정해야 알 수 있습니다. PVC로 캐시를 남겨도 원본의 버전 관리와 백업을 대신하지는 않습니다.

## 전체 과정과 연결하기

원본은 실행 작업보다 오래 보존할 저장소에 두고, 로더와 캐시가 GPU에 배치를 공급하게 구성합니다. Pod 교체 때 사라지는 캐시와 다시 가져올 수 있는 원본을 구분합니다.
