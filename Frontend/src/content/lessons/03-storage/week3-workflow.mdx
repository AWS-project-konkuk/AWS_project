## 앞에서 배운 내용을 하나의 흐름으로 연결하기

앞에서 파일의 수명과 공유 조건으로 저장소를 고르고, Object Storage에 원본과 모델을 보관하는 이유를 배웠습니다. 이어서 GPU가 데이터를 기다리는 원인과 PV·PVC로 Pod 밖의 저장 공간을 연결하는 방법을 확인했습니다. 이번에는 **같은 학습 작업의 노드를 직접 연결하고 설정을 바꾸며** 이 개념들을 함께 적용합니다.

원본 이미지 1,000개는 `train-v1`으로 보관되어 있습니다. 로더는 초당 30배치를 준비하지만 GPU는 초당 100배치를 소비할 수 있습니다. 여기에 학습 Pod가 교체되면 임시 공간의 `cache.bin`도 사라집니다. **무엇을 오래 남길지, 어디서 읽을지, 얼마나 빨리 공급할지**를 나누어 해결해 보세요.

## 앞 단원과 실습 노드 연결하기

| 앞에서 배운 내용       | 이번에 조작하거나 관찰할 곳            | 확인할 질문                                        |
| ---------------------- | -------------------------------------- | -------------------------------------------------- |
| 파일 수명과 공유 조건  | 로더의 캐시 보관 경로                  | Pod가 교체되어도 다시 사용할 파일인가?             |
| Block·File·Object 비교 | Object Storage와 PV 볼륨의 역할        | 객체 보관과 마운트해서 쓰는 공간은 어떻게 다른가?  |
| Object Storage와 MLOps | Object Storage → 로더, GPU → 모델 보관 | 학습 입력과 완성된 모델을 실행 작업 밖에 남기는가? |
| I/O 병목               | 로더 → GPU, 캐시·샤딩 설정             | 공급 속도가 GPU 소비 속도를 따라가는가?            |
| PV와 PVC               | PV → PVC → 로더                        | 볼륨 연결과 실제 캐시 경로 설정을 모두 했는가?     |

이 실습에서는 원본과 완성 모델은 객체로 보관하고, 재사용할 캐시는 PVC로 연결한 볼륨에 둡니다. PV의 기반 저장소가 Block인지 File인지 선택하거나 접근 모드를 검증하는 기능은 이 보드에 없습니다. 앞 단원에서 배운 기준으로 선택 이유를 설명해 보세요.

## 1. 노드의 역할을 보고 빠진 연결 완성하기

화면 위의 **설명과 실습**을 선택하고, 노드 보드에서 **2. 잘못된 구성 수정**을 누릅니다. 현재 구성을 기본 연결과 설정으로 바꾸는 버튼입니다. 처음에는 원본 → 로더 → GPU 경로만 연결되어 있습니다.

1. 각 노드를 선택해 역할과 입력·출력을 읽습니다.
2. **연결 검사**를 눌러 어떤 입력이 빠졌는지 확인합니다.
3. 출력 점에서 입력 점으로 선을 연결합니다. 드래그가 어렵다면 **설정·결과 열기 → 연결 편집**에서 출력과 입력을 선택한 뒤 **포트 연결**을 누릅니다.
4. 아래 다섯 연결이 갖춰졌는지 다시 검사합니다.

| 보내는 노드 · 출력         | 받는 노드 · 입력          | 전달하는 것             |
| -------------------------- | ------------------------- | ----------------------- |
| Object Storage · 원본 객체 | 데이터 로더 · 원본 데이터 | 학습할 원본 이미지      |
| PV 볼륨 · 볼륨             | PVC 요청 · 볼륨 자원      | Pod 밖의 저장 자원      |
| PVC 요청 · 볼륨 연결       | 데이터 로더 · 캐시 경로   | 로더가 사용할 볼륨 연결 |
| 데이터 로더 · 준비된 배치  | GPU 학습 · 학습 배치      | 읽기·전처리를 마친 배치 |
| GPU 학습 · 학습 모델       | 모델 보관 · 모델 파일     | 학습 결과 모델          |

**원본 데이터가 흐르는 선**과 **저장 공간을 연결하는 선**을 구분하세요. PV → PVC → 로더는 볼륨을 제공하는 관계를 표현합니다. Kubernetes에서 Pod가 PVC를 참조한다는 앞 단원의 설명과 함께 읽으면 됩니다. 여기서는 로더가 실행되는 Pod를 별도 노드로 표시하지 않습니다.

<Callout title="연결 성공과 실행 성공은 다릅니다">

연결 검사는 포트의 종류와 빠진 입력을 확인합니다. 선을 모두 연결해도 캐시 경로가 임시 공간이거나 공급 속도가 부족하면 실행 조건을 만족하지 못합니다. 다음 단계부터 연결은 유지하고 로더 설정을 하나씩 바꿉니다.

</Callout>

## 2. 파일 수명 실습: Pod가 교체되면 무엇이 사라질까요?

**데이터 로더**를 선택하고 **설정·결과 열기 → 노드 설정**에서 기본값을 확인합니다.

- 반복 읽기 캐시: **사용 안 함**
- 작은 파일 묶음 읽기: **개별 객체 읽기**
- 캐시 보관 경로: **Pod 임시 공간**

**전체 실행**을 누르고 마지막 단계까지 관찰합니다. 로더에서 Pod 교체로 임시 `cache.bin`이 손실되었다는 실패가 나고, 뒤의 GPU와 모델 보관은 입력을 받지 못해 대기합니다. 이 실행은 Pod 교체 상황을 포함한 시뮬레이션입니다.

이제 **캐시 보관 경로만 PVC로 연결한 볼륨으로 변경**하고 다시 전체 실행합니다. 이번에는 로더가 배치를 만들지만 GPU 단계에서 공급 부족이 나타납니다.

앞의 파일 수명·PV와 PVC 단원으로 돌아가 설명해 보세요. **PV·PVC 선을 연결하는 것**과 **로더가 그 볼륨을 사용하도록 설정하는 것**은 모두 필요합니다. 캐시 보존 문제를 해결해도 읽기 성능까지 자동으로 개선되지는 않습니다.

## 3. I/O 병목 실습: 공급량을 한 조건씩 바꿔 보기

캐시 보관 경로는 **PVC로 연결한 볼륨**으로 유지합니다. 아래 순서대로 로더 설정을 바꾸고, 매번 **전체 실행**으로 GPU 단계의 결과까지 관찰하세요.

### 실행 A · 기본 공급 경로

- 반복 읽기 캐시: **사용 안 함**
- 작은 파일 묶음 읽기: **개별 객체 읽기**
- 예시 공급량: **30배치/초**
- 관찰 결과: GPU 소비 100에 비해 부족하여 데이터 대기 70%

### 실행 B · 캐시 적용

- 반복 읽기 캐시: **사용**
- 작은 파일 묶음 읽기: **개별 객체 읽기**
- 예시 공급량: **60배치/초**
- 관찰 결과: 데이터 대기는 40%로 줄지만 공급 목표에는 미달

### 실행 C · 캐시와 샤딩 적용

- 반복 읽기 캐시: **사용**
- 작은 파일 묶음 읽기: **샤딩**
- 예시 공급량: **120배치/초**
- 관찰 결과: 공급 목표를 충족하여 모델 보관 단계까지 진행

A → B는 앞에서 배운 **Cache**를 적용한 비교입니다. 반복해서 읽는 데이터를 가까운 공간에서 재사용합니다. B → C는 **Sharding**을 더한 비교입니다. 작은 파일을 묶어 요청 횟수와 지연 부담을 줄입니다.

이 시뮬레이터는 캐시와 샤딩을 각각 공급량 2배로 계산하며, GPU 활용 목표는 80%입니다. 공급 120은 GPU가 초당 120배치를 처리한다는 뜻이 아닙니다. 이 예시의 GPU 소비 능력은 100배치/초입니다. 실제 속도나 대기 비율은 저장소·CPU 전처리·전송 시간 등을 측정해야 알 수 있습니다.

앞에서 배운 병렬 로더와 Prefetch도 공급 개선 방법이지만 이 보드의 조절 항목에는 포함되지 않습니다. 이번 비교에서는 캐시와 샤딩의 효과를 구분해 설명하세요.

## 4. Object Storage 실습: 입력부터 결과 보관까지 추적하기

실행 C의 결과에서 각 노드를 선택해 입력과 출력을 확인합니다.

1. **Object Storage**: `train-v1`의 작은 이미지 객체 1,000개가 출발점입니다.
2. **데이터 로더**: 원본과 캐시 경로를 입력받아 준비된 배치를 만듭니다.
3. **GPU 학습**: 배치를 받아 학습하고 `model-v1`을 출력합니다.
4. **모델 보관**: 모델을 `models/model-v1.bin`이라는 객체 키로 보관합니다.

앞의 Object Storage 단원처럼 **어떤 원본으로 학습했고 어떤 모델을 남겼는지** 연결해서 설명해 보세요. 여기의 데이터 버전과 모델 키는 교육용 출력입니다. 실제 버킷 업로드나 객체 버전 관리 설정을 수행하지는 않습니다.

## 5. 다시 검증하기: 빠른 공급과 파일 보존은 같은 문제일까요?

캐시와 샤딩을 모두 켠 상태에서 **캐시 보관 경로만 Pod 임시 공간으로 되돌려** 전체 실행합니다. 공급을 개선하는 설정이 있어도 Pod 교체 시 캐시 손실로 로더가 실패하는지 확인하세요. 이후 다시 **PVC로 연결한 볼륨**을 선택하고 성공 실행을 끝까지 관찰합니다.

실패·성공 비교 기록을 보고 다음 세 가지를 정리한 뒤 실습 화면의 이해 확인과 완료 조건을 확인하세요.

- **보존**: 어떤 설정을 바꾸자 Pod 교체로 인한 캐시 손실이 해결되었나요?
- **공급**: 어떤 설정을 바꾸자 GPU의 데이터 대기가 줄었나요?
- **보관**: 원본·캐시·완성 모델은 각각 어디에 있으며 어떤 수명이 필요한가요?

노드 실행은 보존과 공급의 차이를 보여 주는 모의 실습입니다. 실제 Kubernetes의 바인딩·마운트, 노드 장애 복구, 다중 노드 공유나 백업까지 검증한 결과는 아닙니다. PVC는 저장 공간을 연결하는 요청이며 백업을 대신하지 않습니다.

<LessonSummary>

파일 수명과 공유 조건으로 필요한 저장 공간을 판단하고, 원본과 완성 모델은 Object Storage에 보관합니다. PV·PVC는 로더가 사용할 캐시 볼륨을 연결하며, 캐시와 샤딩은 GPU로 보내는 데이터 공급을 개선합니다.

- 원본 → 로더 → GPU → 모델 보관은 데이터가 이동하는 흐름입니다.
- PV → PVC → 로더는 캐시를 보관할 공간을 연결하는 관계입니다.
- 선을 연결한 뒤에도 보존 경로와 공급 설정을 각각 실행해 확인해야 합니다. 파일이 남는 것과 GPU가 기다리지 않는 것은 서로 다른 성공 조건입니다.

</LessonSummary>
