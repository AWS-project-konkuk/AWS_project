## 문제 상황

고성능 GPU로 모델을 학습하고 있지만 예상보다 학습 시간이 오래 걸립니다. 모니터링 결과 GPU 사용률이 계속 높게 유지되지 않고, 계산을 멈춘 채 기다리는 구간이 반복됩니다.

GPU 자체에 문제가 있는 것일까요?

모델 학습에서는 GPU가 계산을 시작하기 전에 다음 배치가 준비되어야 합니다. 저장소에서 데이터를 읽고 CPU에서 전처리한 뒤 GPU 메모리로 전달하는 과정이 느리면 GPU는 계산할 데이터가 없어 기다리게 됩니다.

## 개념과 동작 원리

### 1. 배치는 어떻게 GPU까지 이동할까요?

학습 데이터 한 배치는 보통 다음 단계를 거칩니다.

1. 저장소에서 원본 파일을 읽습니다.
2. 압축을 풀거나 이미지·텍스트를 디코딩합니다.
3. CPU에서 크기 조정과 변환 등의 전처리를 수행합니다.
4. 완성된 배치를 호스트 메모리에 준비합니다.
5. 배치를 GPU 메모리로 전송합니다.
6. GPU가 모델 계산을 수행합니다.

이 단계들은 하나의 공급 사슬처럼 이어집니다. 어느 한 단계라도 느리면 뒤의 단계는 기다리게 됩니다.

### 3. 공급 속도를 어떻게 개선할까요?

- **병렬 데이터 로더**는 여러 배치를 미리 읽고 전처리합니다.
- **Prefetch**는 현재 배치를 계산하는 동안 다음 배치를 준비합니다.
- **Cache**는 반복해서 읽는 데이터를 가까운 저장 공간에 보관합니다.
- **Sharding**은 많은 작은 파일을 큰 묶음으로 구성해 요청 횟수를 줄입니다.

이 방법들이 항상 성능을 높이는 것은 아닙니다. worker가 너무 많으면 CPU와 메모리 경쟁이 생기고, 캐시는 첫 읽기에는 도움이 되지 않습니다. 한 가지 설정을 바꾼 뒤 같은 조건에서 다시 측정해야 합니다.

### 4. PyTorch DataLoader 옵션 이해하기

앞에서 살펴본 데이터 공급 과정을 PyTorch 코드에서는 어떻게 구현할까요? **DataLoader는 Dataset에서 샘플을 가져와 학습에 사용할 배치로 묶어 주는 도구**입니다. 이미지 학습이라면 이미지 읽기와 크기 조정 등을 거친 샘플을 모아 한 배치씩 학습 코드에 전달합니다.

여기서는 **배치를 준비하는 일**과 **준비된 배치를 GPU로 보내는 일**을 나누어 생각하면 두 옵션을 이해하기 쉽습니다.

#### num_workers: 데이터를 준비할 CPU 작업자 수

학습을 진행하는 메인 프로세스가 파일 읽기와 전처리까지 혼자 맡으면 다음 배치 준비가 늦어질 수 있습니다. 이 일을 별도 작업자에게 나누어 맡기는 것이 **CPU 멀티프로세싱**입니다. 여기서 worker는 데이터를 읽고 전처리하는 별도 프로세스를 뜻합니다.

- `num_workers=0`: 별도 작업자 없이 메인 프로세스가 배치를 준비합니다.
- `num_workers=4`: worker 프로세스 4개가 데이터 준비를 나누어 맡습니다. GPU가 현재 배치를 계산하는 동안 다음 배치를 미리 준비할 수 있습니다.

앞서 배운 **병렬 데이터 로더와 Prefetch를 활용하는 설정**이라고 생각하면 됩니다. 이 숫자는 GPU 개수가 아니라 CPU 쪽 작업자 수입니다. 다만 저장소가 이미 읽기 한계에 도달했다면 작업자를 늘려도 효과가 작고, 너무 많이 늘리면 CPU·메모리 경쟁이 커집니다.

#### pin_memory: GPU로 보낼 배치를 RAM에 고정해 두기

worker가 준비한 배치는 먼저 CPU가 사용하는 메모리인 **호스트 메모리(RAM)**에 놓입니다. CUDA GPU가 계산하려면 이 배치를 GPU 메모리로 한 번 더 옮겨야 합니다.

운영체제는 일반 메모리의 일부를 필요에 따라 디스크로 내보낼 수 있습니다. **Pinned memory는 그렇게 내보내지 않도록 RAM에 고정한 메모리**입니다. `pin_memory=True`는 배치의 텐서를 이 메모리에 준비해 CUDA GPU로 더 빠르게 전송할 수 있도록 돕습니다.

GPU로 보내기 전에 배치를 올려 두는 **전송용 대기 공간**이라고 생각하면 됩니다. 이 설정만으로 GPU에 데이터가 옮겨지지는 않으며, 실제 전송은 코드에서 `.to("cuda")`로 요청합니다. 디스크 읽기를 빠르게 하는 옵션은 아니고, 고정 메모리를 과도하게 사용하면 시스템 메모리에 부담이 됩니다.

| 옵션 | 작용하는 구간 | 쉽게 기억하기 |
| --- | --- | --- |
| `num_workers` | 저장소 읽기 → CPU 전처리 → 배치 준비 | 준비할 작업자를 몇 명 둘까? |
| `pin_memory` | 호스트 메모리 → CUDA GPU로 보내기 전 | 전송할 배치를 RAM에 고정해 둘까? |

#### 코드에서 두 옵션 연결하기

아래는 `dataset`이 `(입력 텐서, 정답 텐서)`를 반환하는 학습 함수 예시입니다. `model`은 미리 CUDA GPU로 옮기고, 그 모델의 파라미터로 `optimizer`를 만든 뒤 전달합니다.

```python
from torch.utils.data import DataLoader

def train(dataset, model, optimizer, loss_fn):
    loader = DataLoader(
        dataset,
        batch_size=64,     # 샘플 64개를 한 배치로 묶기
        num_workers=4,    # CPU 작업자 4개가 읽기·전처리 담당
        pin_memory=True,  # GPU 전송을 위해 배치를 고정 메모리에 준비
    )
    for inputs, targets in loader:
        # 준비된 배치를 실제 GPU 메모리로 전송
        inputs = inputs.to("cuda", non_blocking=True)
        targets = targets.to("cuda", non_blocking=True)
        optimizer.zero_grad()
        loss = loss_fn(model(inputs), targets)
        loss.backward()
        optimizer.step()
```

함께 사용한 `non_blocking=True`는 전송 완료를 기다리는 CPU의 대기를 줄이는 데 도움을 줍니다. 다만 GPU 전송과 계산이 항상 동시에 실행된다는 뜻은 아닙니다.

먼저 같은 데이터로 `num_workers`를 0, 2, 4로 바꾸어 배치 대기 시간과 초당 샘플 수를 비교하세요. 그다음 worker 수를 고정하고 `pin_memory`를 켜고 끄며 전송 시간과 메모리 사용량을 비교하면 어느 단계에서 효과가 있는지 알기 쉽습니다.

Windows에서 worker를 사용한다면 Dataset 클래스는 모듈 최상위에 정의하고, 데이터·모델 생성과 `train(...)` 호출은 `if __name__ == "__main__":` 블록 안에 둡니다. 옵션의 자세한 의미는 [PyTorch DataLoader 문서](https://docs.pytorch.org/docs/stable/data.html)를 참고하세요.

### 5. 작은 파일 묶기와 압축은 다릅니다

여러 이미지를 tar 같은 shard로 묶으면 파일 열기나 객체 요청 횟수를 줄일 수 있습니다. 압축은 전송량을 줄일 수 있지만 CPU에서 압축을 푸는 비용이 추가됩니다. 이미 압축된 이미지에서는 이득이 작을 수 있으므로 **묶음 크기와 압축 여부를 따로 비교**해야 합니다. 분산 학습에서는 각 worker가 읽을 shard도 나누어 중복 읽기를 줄입니다.

## 비교와 한계

- 캐시 적중률이 낮으면 저장 공간만 사용하고 성능 이득은 작을 수 있습니다.
- shard는 요청 수를 줄이지만 일부 샘플만 임의로 읽는 작업은 불편해질 수 있습니다.
- 병렬 로더를 늘릴 때는 CPU, 메모리와 저장소가 감당할 수 있는지도 확인해야 합니다.

## 전체 과정과 연결

Object Storage는 원본 데이터를 보관하지만 GPU에 배치를 자동으로 공급하지는 않습니다. 저장소에서 로더를 거쳐 GPU까지 이어지는 전체 경로를 측정해야 합니다.

## 핵심 정리

GPU의 계산 속도보다 데이터 공급 속도가 느리면 **I/O starvation**이 발생합니다. GPU를 늘리기 전에 배치 대기 시간을 측정하고, 저장소 읽기·작은 파일 요청·CPU 전처리·GPU 전송 중 가장 느린 단계를 찾아 개선해야 합니다.
