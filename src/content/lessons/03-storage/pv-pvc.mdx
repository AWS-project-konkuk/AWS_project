## 문제 상황과 전체 맥락

## 개념 이해

PV는 클러스터가 다루는 스토리지 자원이고 PVC는 용량과 접근 조건을 요청하는 객체입니다. Pod는 PVC를 통해 볼륨을 사용합니다. 조건이 맞아 결합된 볼륨의 수명은 Pod 자체의 수명과 다를 수 있습니다.

> **연결 전에 예측하기** — 이 그림은 실행 순서가 아니라 참조·바인딩·저장소 대응 관계입니다. 데이터 파일과 저장소 요청을 구분하세요.

<NodeExample />

연결을 따라가며 확인한 자료는 **PVC 참조 · 볼륨 바인딩**입니다. Pod 삭제 후 자료 보존은 볼륨과 반환 정책에서 확인합니다. 분산 작업이라고 무조건 RWX를 선택하지 말고 실제 읽기·쓰기 주체와 노드 배치를 판단하세요.

## 관찰한 결과 해석하기

PVC는 백업이 아니며 실제 보존은 스토리지와 회수 정책 등에 달려 있습니다. RWO는 단일 노드의 읽기·쓰기 조건이지 항상 단일 Pod라는 뜻은 아닙니다. S3 버킷이 기본적으로 PVC에 직접 결합되는 것도 아닙니다.

## YAML 예제 · 저장소 요청과 마운트

아래 PVC는 기본 StorageClass가 있는 클러스터를 가정합니다. PVC만 만들면 Pod에 자동 마운트되지 않으며 Pod의 volumes와 volumeMounts에서 이 요청을 참조해야 합니다. 저장소 제공 조건이 맞지 않으면 Pending 상태를 조사합니다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: training-data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 10Gi
```

실행 예제에서 각 명령이 변경하는 파일 또는 실행 상태를 확인한 뒤, 위에서 설명한 흐름과 비교해 보세요.

## 적용 조건과 한계

영구 볼륨은 백업이 아닙니다. 공유 읽기만 필요한지 동시 쓰기도 필요한지 판단하고 저장소·드라이버의 지원을 확인합니다. 캐시는 반복 읽기를 돕지만 최초 읽기나 잘못된 데이터 자체를 해결하지 않습니다.

## 전체 과정과 연결하기

Pod가 PVC를 참조하면 PVC의 용량·접근 모드·스토리지 조건에 맞는 PV가 결합되어 사용됩니다. StorageClass는 동적 프로비저닝의 기준을 제공하며, 실제 지원 조건은 스토리지 구현에 달려 있습니다.
